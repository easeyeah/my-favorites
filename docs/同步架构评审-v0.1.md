## 1. 总体判断

**核心模型健全，不需要重写，也不需要引入 Redis、消息队列或 CRDT。**「库为唯一真相 + changes 单调游标 + 语义幂等 apply + 增量基线快照 diff + SSE 门铃 + 周期补偿」这套骨架适合单容器自建形态，D46–D79 十轮迭代已把书签级双向同步做到工程可用。

但对照「双向实时同步书签**及目录结构**」的最终目标，**补上管理台实时刷新和游标缺口检测还不能宣告达成**：目录移动（reparent）、空目录创建、失败事件恢复闭环、冲突处理与快照恢复协议，同样是必要条件。

值得保留的基础（不做的事见 §7）：

- changes 表（AUTOINCREMENT id 即游标）+ ChangeHub 门铃（丢事件不丢正确性）+ 1min/30s 三层兜底告警。
- 语义幂等 apply（create 按 canonical URL 绑定、update/move 比对现值、delete noop 安全）+ `runAsSyncDevice` ALS 防回环（D67）。
- 增量基线维护（D53/D75：基线 = 开局快照 ∪ 引擎动作 ∪ 成功回执，treesDiffer catch-up 补轮）。
- 删除保险丝（30 条/25% + 目录级 3 个/50%）与「豁免区必有命名收敛主人」的收纳盒模式（D51/D72/D78）。

## 3. 需要整改的四个架构问题

### A. 目录缺少稳定身份，无法可靠同步树结构（对应 D80 Tier1-A，为最终目标的必要条件）

名称、路径、URL 都是可变属性，不适合作为长期身份。书签已有 `bookmark_identity`，目录没有对应物：扩展侧靠 `fMap`（storage 临时映射）+ `ensurePath` 按名 find-or-create（store.ts:138–162）。由此派生整个 bug 族：同名目录跨端歧义、多端改名建重复目录（D79 已打 fMap 反查补丁）、悬空父、**reparent 无法表达**（父变了路径就变了，按名匹配下等于两个目录）。

整改：
1. 新增 `folder_identity(device_id, browser_folder_id, app_folder_id)`（迁移 v15），路径仅作初次导入匹配，绑定后按 ID 同步。
2. 补齐 `folder.create / rename / move / delete` mutation 与 `store.moveFolder`；移动校验父目录存在、禁止成环。
3. 显式定义浏览器「书签栏 / 其他书签」的根映射，避免无条件合并不同根下同名目录（D55 虚拟根穿透只解决路径污染，不解决身份）。
4. 扩展空目录创建进推送 diff（新目录不再依赖书签顺带 ensure）。

### B. 「推进游标」与「实际应用成功」没有形成可靠闭环

三类缺口（集中在 sync.ts）：

1. pull 单条失败仍推进游标（L588），错误又在整轮成功时清空（L872）——`treesDiffer` 只比浏览器与本地基线，**不能替代服务端事件重试**；失败事件可能永久跳过。
2. 部分浏览器写操作吞异常却继续更新基线（placeBookmark L265–277、pull-move L571–572）——乐观基线把失败动作当成已完成。
3. 库侧删除触发保险丝时删除未执行，但游标可能已存到该事件之后（L592–616 与 L872 的时序）——确认放行后无事件可重放。
4. 整轮失败不可观测（违反 D62③）：触发层 `.catch(() => undefined)`（sync.ts:1006、background.ts:557）且 `setInfoWrapped` 不执行 → SyncInfo 停留陈旧 "ok"，服务端宕机期间 options 显示假象。

整改：事件在「应用成功」或「已持久化进入本地待处理队列」后才允许推进接收游标；失败与待确认删除落本地持久队列，成功后移除；浏览器操作成功后才更新对应基线；同步状态区分正常/重试中/待确认/失败并在 options 呈现。

### C. 全量恢复缺少一致性边界（D80 Tier1-C 的强化版）

`doAlign` 先分批读数据、最后取 head 当游标（sync.ts:461–471）——对齐期间新增的服务端变更可能没进已读数据却被最终游标越过（S）。changes 裁剪后「关再开同步触发 align」不是可靠恢复：align 含浏览器→库合并写入，可能把旧状态重新带回（R）。`minAvailableId` 单独也不够：日志为空、数据库恢复、删除历史都需要明确语义。

整改：服务端提供带固定水位的同步快照（snapshot + watermark），快照完成后只拉水位之后的变更；pull 响应带日志保留边界与库代际标识，过期返回 `reset_required`；过期恢复保留本地未提交操作，快照重建后按冲突策略重放。

### D. 冲突处理与多写入通道缺少统一规则

「先 pull 再推送开局快照」不等于严格后发生效——没有版本比较就无法判断哪侧是较新的用户意图。同步引擎、镜像队列（`pending_browser_ops`）、收纳盒管线三写者交接靠时间窗协同：`isMirrorMove` 是 5 秒时间窗而非操作级作用域（device.ts:110–123）——窗口内用户真实 move 会被误抑制（收纳盒漏投递），镜像超 5s 则保护失效（回环）。

整改：
1. 同步开启的设备由一个执行器负责浏览器写入；收纳盒保留独立业务流程但执行动作统一排队。
2. 操作携带 `opId + entityId + baseRevision`，服务端事务内完成数据修改、变更日志与操作回执。
3. 第一阶段用简单规则：无版本冲突则应用，有冲突返回最新状态按明确策略处理；不宣称按用户实际操作时间「后发生效」。
4. 已同步设备停发镜像 ops（对应 D80 Tier2-D），`mirrorGuard` 对已同步设备整体退役。
5. 浏览器 URL 修改复用 D52 书签更新语义（canonical 重算 + 查重绑定：命中迁移身份、未命中原行更新），消灭孤儿与 align 复活（§2 第 2 行）。

## 7. 明确不做（不变量）

- 不重写统一 walk/diff——「豁免区 + 命名收敛主人」模式定型（每处豁免必须登记收敛通道）。
- 不做重复节点全量收养；本地映射表随 folder_identity 渐进吸收，不单独合并。
- 不改技术选型：不引入 Redis/消息队列/CRDT/外部向量库；NAS 资源红线与隐私红线在所有整改中继续生效（出站抓取仍走 guardedFetch + 隐私判定前置）。

## 8. 验收口径

完成验收不能只看「最终数量相同」，应比较**稳定身份、标题、URL、父子关系、约定排序**五个维度，并验证以下场景后自动收敛：

1. 在线双向秒级（增删改移 × 书签/目录 × 双向矩阵）。
2. 扩展 SW 被杀 / 服务端重启 / 断网 5 分钟内恢复——不丢事件、不假成功。
3. 保险丝触发 → 用户确认 → 删除仍能执行且另一端收敛。
4. 长离线 >14 天（越过裁剪边界）→ 明确 reset 语义，不静默跳事件。
5. 两端并发编辑同一条目 / 同名目录 / 目录搬家与改名竞态——结果确定、可撤销。
