### D90 · 提交信息规范：把既有惯例写成可执行规范，补上 PR 校验与破坏性标记（2026-11-24）

**背景**：仓库一直使用 Conventional Commits（commitlint + husky 已在位），但规范只存在于 AGENTS.md 一行「feat/fix/docs/chore/refactor/test/build」，执行上有三个洞：① CI 只在 push 时校验 `HEAD~1..HEAD`——PR 完全不校验，一次 push 多个提交时只查最后一条；② 52 条历史里 scope 使用率为 0，monorepo 从提交历史看不出改了哪一端；③ 无 `BREAKING CHANGE` 约定，而仓库已有 v1→v16 只前进迁移、`DEPLOY_MODE` 退役这类典型破坏性变更，历史里零标记；另有 `9fc005b feat: D43–D63 切片合流`（21 个功能一个提交，无法单独 revert、无法对应 changeset）。同时承认做得好的部分：标题平均 38.8 字符（最长 62）、正文普遍 5–10 行结构化说明，不需要推翻重来。

**决定**：不换工具链、不改格式，把既有事实写成 `docs/开发规范/提交与发版规范.md`，并让门禁覆盖全文——① **受控词表**：type 11 种（feat/fix/refactor/perf/test/docs/build/ci/chore/revert/style，显式写入 commitlint 防 update/wip 自由发挥）、scope 12 个（server/extension/web/shared/ai/e2e/docs/ci/docker/deps/release/repo，可省略但写了必须在集合内）；② **标题规则**：`type(scope): 摘要`、≤72 字符（含前缀）、不加句号、写结果而非文件名、D 编号放尾部（历史最长 62，规则不破坏存量）；③ **正文三段式**（动机 / 关键实现 2–5 条 / 验证与影响），并规定「一个提交一件事、跨端按端拆、禁止切片大合流」；④ **破坏性改动必须写 `BREAKING CHANGE:` 页脚**（DB 迁移、API·鉴权·配置不兼容、扩展权限变更、导出格式变化）；⑤ **门禁闭环**：本地 husky `commit-msg` 不变；CI 改为全范围校验——PR 用 `merge-base origin/<base>..HEAD`，push 用 `before..after`（首次推送/force push 回退 `HEAD~1`），多提交一并检查；正文/页脚关闭 100 列折行限制（中文按段落写，按列宽折行会把整段判错）。

**理由**：commit 是「怎么改的」，决策记录是「为什么这么定」，changeset 是「用户感知到什么」——三者粒度不同、不可互替；规范化的收益是**可 revert、可追溯、可自动生成 CHANGELOG**，不是为了整齐好看。scope 设为可选而非强制：强制会让 docs/ci 提交别扭，但完全不约束会让 server/后端/api 混用。

**验收**：新规则对 52 条历史全量通过（exit 0，不改写历史）；坏样例被拒（`update:` 类型、`fix(后端):` 非法 scope、超 72 字符标题）；好样例通过（含 scope 与 `BREAKING CHANGE` 页脚）；CI YAML 语法校验通过；AGENTS.md 与 docs/README.md 文档地图同步。历史提交不追溯改写——改写会破坏 CHANGELOG 中已引用的 commit 哈希。

### D89 · 书签目录右键管理 + 目录级重整理 + 内容页转资料（失败建议丢弃）+ 正常状态角标（2026-11-24）

落地：**A 目录右键菜单**——沿用 D52 手写轻量浮层（零新依赖，同一套 window mousedown/Esc/视口钳制与 stopPropagation 修法），真实目录给「打开/新建子目录/重命名/移动到…（复用 D81 弹窗）/AI 重新整理此目录/提取资料/删除目录…」七项，收纳盒行只给「打开 / AI 归位」；删除从「仅空目录 hover 小图标」升级为全目录可删 + 二次确认（文案给出将连带删除的子树书签数，服务端仍是 D73 树删）；开合计入 D82 blocked。**B 目录级重整理**——新增 `POST /organize/folder`：范围 = `folderSubtreeIds` 含自身 + `listBookmarks({folderIds})` 子树 IN 查询；**目标目录限定子树内**、允许 AI 在该目录下新建子目录（`createFolder.parentFolderId`，apply 内同父 find-or-create 并继承 parent.root），永不跨出子树、永不删除/归档；复用 session/apply/rollback 内核与 D76 目录上下文（路径+代表书签），版本可整批撤销。**C 内容页转资料**——新增 `GET /materials/scan/stream`（SSE）：串行抓取（并发闸 ≤1，D62）、逐条 item 事件、断开即停、单次上限 30（1–60，done 回 remaining 供续扫）；视频/图片按 URL 规则直接物化，文章候选 `crawlOne({skipMaterialize:true})` 补抓（**抓取成功 ≠ 资料**：crawlOne 默认物化会让「正文 ≥200 字的工具页」灌满资料库），≥200 字后按批判定内容型页面（≤10 条/次，标题+URL+前 400 字；无 LLM 或判定失败按正文 ≥800 字兜底），判定为否 → not_content（书签保持不动）；**抓取失败 → done.failed 清单 → UI「建议丢弃」区（默认全选，归档推荐/删除显式二次确认，系统永不自动删除——红线③）**；隐私/私密跳过且永不抓取、也不进清单。**D 正常角标**——正常书签移除行尾「正常」文字徽章，改为 favicon 左上角 6px 绿点（ring-background 分隔），失效/疑似/已归档徽章保持醒目。

设计判断：**目录级操作必须「就地」**——用户点的是这个目录，AI 把书签搬到目录外会破坏他对该目录的预期；跨目录调整仍走全库重分类。**「提取」与「抓取」必须分开**——抓正文是资料化的前提，不是资料化的证据（D70 的 material=false 判定同源）。**失败≠该删但值得被看见**——抓取失败多半意味着链接已坏，列表化 + 一键归档/删除让用户低成本收尾，但绝不自动执行。**状态噪音要收敛到异常侧**——正常是绝大多数，满屏「正常」是负价值；角标挂 favicon（有辨识度的真实图标）而非挤占标题。另：markPrivate 隔离动作是子树边界的唯一例外（供应商内容审核拒收属安全动作，仍移「私人收藏」，版本可撤销）。

验收：server 300 全绿（新增 `dir-organize-scan.test.ts` 6 例：子树限定+版本撤销、新目录挂父级、404、内容页/非内容页/失败清单/隐私跳过、失败原因落 cache、includeSubfolders 与 limit/remaining）；web typecheck + build 绿；?mock 走查截图（目录右键菜单/收纳盒菜单/重整理 toast 与「AI 精选」子目录/扫描进度与建议丢弃清单/删除确认/正常绿点）。**复核整改（同日 code review，不新增编号）**：P1×1——`ensureFolder`/apply 的目录级复用此前只查**直接子级**，模型返回孙级已有目录名（如 `工作/开发/前端` 的「前端」）会在父级下建出**重复目录**（D55/D71 病灶复发）；改为按 `allowedFolderIds` 在子树任意深度先解析同名现有目录、命中即复用 id，仅子树内确实不存在才在 `createParentId` 下新建，补「深层同名复用不新建」回归。P2×3——删 `handleMessage` 重构残留的死 `sessionId`；`reclassifyFolder` 的 `subtreeIds.includes` O(n²) 改 Set；补「已归档书签不参与目录级整理」回归。P3×6——store 三处 D83 注释笔误改 D89、`buildSubtreeContext.pathOf` 加环守卫、扫描弹窗「停止」态单独文案 + 用本运行次计数估算 remaining（中止后「继续扫描」仍可见）、`moveFolderTo` 显式处理 mock `{error}`、SSE 解析抽 `lib/sse.ts` 供死链检测与资料扫描共用、`listBookmarks({folderIds})` >500 截断加 warn。整改后 server 302 全绿（+2 回归）/web typecheck+build 绿。状态：已交付。

### D93 · 容器开发与更新规范：不更新到运行中的容器不算交付（2026-11-24）

**用户决定**：「我们采用容器开发，因此每次功能开发完成之后要记得更新容器重新构建。」要求写成开发规范。

**背景**：D92 交付时只重建了管理台产物、没有重启服务端。开发容器只读挂载 `apps/web/dist`，构建一完成，用户真实实例的界面就换成了新版；而 `tsx watch` 对 bind mount 失效，服务进程仍是旧代码。结果用户实机点整理报 `HTTP 404`，交付说明却写着「未部署到真实库」。原有的提示只写了一句「改 server 需 docker restart」，没有说清「web 构建会立刻改变真实实例」这层后果，也没有把收尾固化成必须执行的步骤。

**规范**（全文见 `docs/开发规范/容器开发与更新规范.md`）：

1. 按「改了什么」决定「做什么」：web → 构建（立即生效）；server / packages → 重启容器；依赖 / Dockerfile → 重建镜像；扩展 → 构建并在浏览器重新加载。拿不准就全做一遍。
2. 交付收尾固定顺序：类型检查 → 测试 → 构建 → 重启 → 验证 → 交付说明。跑端到端测试会触发 web 构建，之后同样要收尾。
3. **构建与重启成对**，禁止半部署；做不到时必须在交付说明第一段写清实例处于什么状态、用户要执行什么命令。
4. 重启会自动应用待执行的迁移并逐库备份；交付说明必须报告迁移范围与完整性检查结果，不手动改真实库。
5. 验证以事实为准：健康检查、进程启动时长、启动日志、界面产物与服务端下发的文件名一致——不拿「跑过构建命令」当证据；不为了验证而造令牌登录真实实例。
6. 交付说明必填五项：真实实例状态、执行过的命令、数据库迁移情况、用户还要做的事、没验证的内容。

**落地**：AGENTS.md 把「不更新容器不算交付」列为硬性红线第 6 条，「常用命令」补齐三类更新命令，文档入口指向本规范；文档地图登记。本规范对人和 AI 会话同样生效。

### D95 · 目录整理的粒度控制：新目录至少 3 条同类才建（2026-11-25）

**用户反馈**：「分类太细了，基本上一个目录一个网址，而且硬件目录下的购物导购是什么意思？明显不合适啊，还有子目录里的 C01、C02、C03、C04 这几个为什么要加前缀呢」——D94 放开落点之后再次实机整理「C 硬件」。随后追问：「如果目录下面的书签明显不适合放到当前目录怎么办？会不会移动到别的大分类下面？」

**先查事实**（只读查看真实库与任务记录，不读书签内容）：

- 第二次任务（49 条，移动 7 条）新建了 7 个目录，**每个只有 1 条书签**：来源目录下 6 个 + 顶级 1 个（「3D建模平台」）。第一次任务留下的「智能硬件」「手工纸模」同样是 1 条。
- 「辣品导购平台」第二次仍在「C 硬件 / 购物导购」——那是第一次整理建出来的目录。任务记录只存最终落点、不存模型原始回答，无法区分是模型选中、同名兜底还是被判成「已在合适位置」；但这三条路径在代码里都成立，都要堵。
- C01–C05 这类编号前缀不是整理功能加的：这批目录来源为 `imported`，创建于 2026-11-17 首次导入，与另外 47 个带编号的子目录、13 个字母前缀的根目录（A AI、B 开发、C 硬件……）同时出现——**前缀随书签数据一起导入**。

**判断**：D92 把「建不建目录」完全交给模型（新目录总数上限 64 只防爆炸、不防过细），D94 又放开了落点，模型按「一主题一目录」尽忠职守，结果就是一条书签一个目录。粒度是产品规则，不能寄望于提示词。另外，D92 的同名兜底是为「模型漏答」准备的，却分不清「用户建的目录」和「上一次自动整理放错的目录」，也不区分「没答」和「答了不复用」。

**规则**：

1. **成组门槛**：新目录直接承接不足 3 条同类就不建（`MIN_NEW_FOLDER_ITEMS = 3`），在用途与资料判定之后按「真的会搬进去的条数」统计。二级新目录不足 → 撤销，条目回流一级主题；一级新目录直接承接不足时：没有保住的子目录 → 不建、条目保留原位；只保住一个 → 连它一起撤销（三条书签占两层同样过细），由一级主题承接；保住两个及以上 → 保留为归组目录。顶级数量闸（D94）与新建总数上限都排在成组之后。
2. **复用现有目录不受限**：一条书签归入已有的合适目录照常移动，门槛只管「新建」。
3. **小主题先并入更宽主题**：归纳与合并两个阶段的提示词都要求把只有一两条的小主题并入含义更宽的主题，确实独立的才保留原名。
4. **放错的小目录不再是候选**：来源目录里由自动整理建的、不足 3 条的目录，不进入映射候选（模型选不到，同名兜底也取不到），里面的书签随本次整理重新归位。来源之外的小目录、来源内已成组（≥3 条）的自动整理目录照常是候选并带 `aiCreated:true` 标记，提示词提醒模型「主题与来源目录无关时别因为名字对得上就复用」；模型明确选中时照常复用。模型**明确回答「不复用」时同名兜底不再覆盖它**，兜底只用于漏答。落点兜底判断「主题是否与来源目录相关」时只看用户自己的目录名。旧目录本身不删除（删除永不自动执行）。
5. **如实呈现**：保留原位的条目原因码 `too_few_to_group`，界面显示「同类书签太少，未单独建目录，保留原位」；终态说明写「N 条同类太少，未单独建目录」，零变更时是「有 N 条同类太少……本次未调整」，不再说成「位置都合适」。
6. **明显放错的不留在原地**（追问后补）：与来源目录无关的主题如果同类太少、不值得建目录，归入模型指定的最接近的顶级大类（书签直接放在那个大类下面，不新建目录），不再因为「数量少」留在不相关的目录里。属于来源目录主题的子方向（本来就该在这里，只是不够建目录）仍然保留原位。大类指回来源目录自己、它的子目录或不存在的目录时忽略（宁可保留原位，也不做没有意义的移动）；模型给不出大类时保留原位。

**教训**：① 「建不建」这类粒度问题要写成确定性规则，提示词只能引导；「给模型更多自由」的改动（放开落点）要同时想到粒度会不会跟着放开。② 兜底逻辑要分清「用户建的 / 系统放错的」「没答 / 答了不复用」——为漏答准备的善意兜底，会把上一次的错误原样复制一次，而且复制之后显示为「已在合适位置」。③ 测试替身里的静默异常会让一整条分支长期没有被真正测到：替身的解析错误被业务代码的容错吞掉时，测试仍然全绿。④ 「不让它建目录」和「让它留在放错的地方」是两件事：收紧粒度时要复查被收紧的条目去了哪里——明显放错的书签应该有退路（归入最接近的大类），而不是被门槛一起留在原地。
