## 1. 产品定位

### 1.1 一句话定位

**当你收藏了几百个网址却再也没打开过它们时，my-favorites 用 AI 把这堆书签变成一个能天天用的个人导航主页。**

### 1.2 唯一核心任务（JTBD）

用户雇佣本产品只做一件事：**"把我失控的书签堆，变成我有掌控感的、每天使用的入口。"**

由此推导出产品各部分的角色：

| 部分 | 角色 | 定性 |
|---|---|---|
| AI 聊天整理 + 内容缓存 | **楔子**（用户为什么选我们而不是别的书签工具） | 核心 |
| 导航站生成 | **产出物**（整理结果的可视化落地，也是日活阵地） | 核心 |
| 一键收藏/收件箱自动归位 | **留存钩子**（让 AI 介入每一次书签流入） | 核心 |
| 定期死链/查重维护 | **回访理由** + 信任构建 | P1 |
| 多端同步、私密书签、模板商城 | 服务于闭环的配套 | P2，坚决后置 |

**判断标准**：任何新功能提案，必须能回答"它让整理更准、让导航站更有用、或让用户更常回来"三者之一，否则不进路线图。

### 1.3 为什么不是 Raindrop.io（竞争壁垒声明）

Raindrop.io 是最强书签管理器（集合、建议、死链检测、永久快照），但它是**管理工具**：产出是"一个更好的书签库"，用户依然要自己动手整理。我们：

1. 产出物不同——我们落地为**每天实际使用的导航主页**（占据新标签页），Raindrop 的产出没人每天看；
2. 交互范式不同——我们以**聊天指令 + 内容理解**完成整理（"把开发文件夹里 2023 年以前的链接按内容重新分类"），Raindrop 是手动为主+被动建议；
3. 数据资产复利——缓存的内容摘要/快照随时间越积越多，整理偏好持续学习用户习惯，**用得越久越准**，形成切换成本。

## 2. 竞品分析

### 2.1 第一梯队（直接竞对）

**Raindrop.io**（百万级用户，成熟商业产品）
- 强项：全平台、集合/嵌套标签、死链检测（付费）、永久副本（付费）、公开集合、AI 建议分类
- 弱项（我们的机会）：整理以手动为主；无导航站产出；无聊天式整理；云托管不可自建
- **对我们的启示**：死链检测/快照是"付费级价值"已被验证；其 AI 建议是"推荐你确认"而非"对话式执行"，交互代差是我们的窗口期

**Flomo / Cubox 类内容收藏**：收藏对象是"内容片段"而非"网址入口"，不构成直接竞争，但验证了"AI 辅助整理"的付费意愿。

## 3. 用户画像与旅程

### 3.1 核心画像（M1 只服务前两个）

- **P1 失控的收藏者**（主力）：书签 200–2000 条，"存了=学会/用到"的心理安慰，实际从不回访。痛点：找不到、不敢删、没面子。付费意愿：中。
- **P2 效率门户用户**：想要美观的个人起始页，书签是素材库。痛点：手工建导航站太费时。付费意愿：高。
- **P3 自托管极客/NAS 用户**：数据主权敏感。付费意愿：低（倾向买断/自建），但是口碑传播节点与自建方案的验证者。

### 3.2 用户旅程与 Aha Moment

```
安装扩展 → 一键导入全部书签（30 秒，无需任何配置）
   → 阶段1「快整理」：60 秒内看到第一版整理结果 + 导航站    ← ★ Aha Moment
   → diff 一键采纳 → 设为新标签页
   → 阶段2「精修」：后台内容级整理完成，提示"AI 已根据网页内容
     精修 43 条分类，查看变更"                              ← 二次惊喜
   → 此后：随手丢进收件箱自动归位、每次收藏即时建议、每周维护报告
```

**Aha 定义：导入后 60 秒内看到整理结果和导航站**（两阶段整理，见 §5.2）。注册和 BYOK 都必须放在 Aha 之后——这是激活率的生命线。

## 4. 核心体验闭环（留存引擎）

```
        ┌─ ① 收藏钩子：一键收藏即时建议归位（域名映射缓存命中 <50ms，零 AI 成本）
日活 ←──┤  ② 收件箱钩子：随手丢进「自动整理」文件夹，AI 流水线归位（懒人主路径）
        │  ③ 新标签页：导航站就是起始页，每天天然曝光
        └─ ④ 周报钩子：每周维护报告（死链/重复/本周归档数）→ 点进处理 → 再体验 AI
```

四个钩子覆盖书签的**全部流入路径**（主动收藏 / 被动堆积）与**两类回访理由**（每日入口 / 每周维护）。M1 至少交付 ③ + ① + ②。

## 5. 功能架构

```
┌────────────────────────────────────────────────────┐
│                浏览器扩展（用户唯一入口）             │
│  收藏按钮 · 收件箱监听 · 侧栏聊天整理                │
│  新标签页(导航站) · 周报角标                         │
└──────────────┬─────────────────────────────────────┘
               │ 同一套 API
┌──────────────▼─────────────────────────────────────┐
│      服务端：官方云（SaaS） ≡ 自建服务端（Docker）    │
│  · 书签/目录服务        · 内容缓存引擎（双通道↓）     │
│  · AI 整理编排（LLM）   · 导航站生成与托管            │
│  · 定时维护调度         · 同步与账号                 │
└────────────────────────────────────────────────────┘
```

### 5.1 内容缓存引擎 —— 双通道设计

| 通道 | 触发 | 覆盖 | 说明 |
|---|---|---|---|
| **A. 扩展端就地捕获（主）** | 用户收藏瞬间 / 收件箱书签被打开时 | 登录墙✅ 内网✅ 反爬✅ | 扩展在当前标签页提取正文（Readability），随书签提交；质量最高、零额外抓取 |
| B. 服务端补漏抓取 | 存量导入 / 周期刷新 | 公开页 | 队列限速、robots 尊重；失败降级为"仅元数据" |

缓存分级：L1 摘要+标签（AI）→ L2 正文文本 → L3 完整快照（一键快照功能，详见 §6.2；云端默认只存 L1+L2，L3 按用户主动触发与配额提供，自建端不限）。

### 5.2 两阶段整理（激活提速的关键设计）

```
阶段1「快整理」(<15s)：不抓网页，只用已有信号
  → 目录结构语义 + URL 域名模式 + 标题关键词 + 添加时间
  → 规则引擎立即产出第一版整理结果和导航站
阶段2「内容级精修」(后台)：
  → 抓正文、生成摘要、embedding 聚类，完成后提示用户查看变更
```

阶段1 是确定性本地规则引擎（零 LLM 成本、零延迟）；阶段2 复用 diff 确认流，是二次惊喜而非等待门槛。

## 6. 功能模块（带优先级）

优先级：**P0** = M1 必须；**P1** = M2；**P2** = M3/远期。

### F1 书签获取与管理
- **F1.1 [P0]** 一键导入浏览器全部书签（保留目录结构与时间）；Netscape HTML 文件导入
- **F1.2 [P0]** 一键收藏（快捷键/右键），提交时扩展端就地捕获内容（§5.1 通道 A）
- **F1.3 [P0]** 树形目录管理
- **F1.4 [P0]** 收藏时 AI 即时建议归位：域名→分类映射缓存表，命中 <50ms 零成本返回；未命中异步调 LLM 并写回缓存。高频用户 90%+ 收藏走缓存
- **F1.5 [P0] 自动分类收件箱（懒人模式）** ★ v0.3 新增，详见 §6.1
- **F1.6 [P0]** 导入导出：JSON 全量备份 / Netscape 导出（数据可迁移承诺）
- **F1.7 [P1]** 多端同步（官方账号或自建端）
- **F1.8 [P2]** 私密书签二次验证
- **F1.9 [P2]** 常用/备用分层归档

### 6.1 F1.5 自动分类收件箱（懒人模式）详细设计

**概念**：在书签栏创建一个特殊文件夹「📥 自动整理」（Inbox）。用户把任何书签丢进去（或收藏时直接落入），AI 自动分类并归位到正确目录。源自 GTD 的 Inbox 思想——**降低使用门槛到"随手一丢"**。

**书签进入收件箱的三种方式**：
1. 浏览器原生拖拽/移动到该文件夹
2. 右键菜单"收藏到自动整理"（不想思考归哪类的场景）
3. 一键收藏的默认目的地可设为收件箱（全懒模式）

**触发与流水线**：
- 扩展监听收件箱新增（bookmarks API 事件），逐条触发整理流水线：
  `域名规则即时初判 → 内容捕获（通道A优先）→ AI 内容级分类 → 自动归位`
- 支持定时批量清扫（每小时/每天，自建端与云端均可调度）——覆盖离线期间堆积的书签

**两种模式**：
- **确认模式（默认）**：归位后轻量提示"已归位 3 条 ✦ 查看"，可一键撤销
- **全自动模式**：静默直接归位；所有移动动作自动进版本快照，随时整体回滚

**歧义与安全规则**：
- 分类置信度不足（多类目相近）时**留在收件箱不强行移动**，积攒后在聊天整理中一次性向用户询问——收件箱永不丢书签
- 用户手动从收件箱移出的书签记为"用户已确认"，AI 永不再动它
- 移动动作全部进版本快照（与 F3.5 回滚体系共用）

**与 F1.4 的关系**：F1.4 是主动收藏路径的即时建议；F1.5 是被动堆积路径的自动归位。两者共用同一套分类引擎与缓存，互补覆盖。

### F2 内容缓存引擎
- **F2.1 [P0]** 扩展端正文捕获（Readability）：正文/标题/描述/og:image/favicon
- **F2.2 [P0]** 服务端补漏抓取队列：限速、重试、robots、失败标记；favicon 优先 Google s2 / DuckDuckGo 图标接口兜底（导航站图标覆盖率决定首屏观感）
- **F2.3 [P0]** L1 摘要生成（AI）+ 关键词/标签
- **F2.4 [P0] 一键快照**：手动一键 / 收藏时可选生成完整页面快照，原页失效后仍可回看（v0.3 升级为一等公民功能，详细设计见 §6.2）；批量与服务端补漏快照为 P1
- **F2.5 [P0]** 隐私域名排除清单：名单内只存 URL 不抓内容、不送 AI
- **F2.6 [P2]** embedding 向量索引（语义搜索前置）

### 6.2 F2.4 一键快照（防失效回看）详细设计

**动机**：链接失效（link rot）是书签工具最大的长期痛点——收藏的页面几个月后可能下线、改版或被付费墙挡住。快照让"收藏"真正等于"留住"。Raindrop 的"永久副本"（付费）与 HamHome 的本地快照均验证了该价值；本产品将其升级为一等公民交互，并与死链检测形成"失效 → 有出路"的闭环。

**触发方式（四条）**：
1. **收藏瞬间**：一键收藏时可选"同时保存快照"（全局开关可配置）；扩展端就地生成，零额外抓取
2. **手动一键**：书签详情页 / 扩展右键菜单 / 导航站卡片上的「快照」按钮——对任何已收藏书签随时补拍
3. **聊天指令**："给这个书签拍个快照"、"把整个学习目录都做快照"（批量走服务端/自建端队列）
4. **失效联动**：死链检测判定失效且无快照时，在周报与书签详情中提示"该页已失效且无快照"（有快照则直接给"查看快照"入口）

**技术形态**：
- **扩展端（主通道）**：`chrome.pageCapture.captureMHTML` 对当前标签页一键生成 **MHTML 单文件**——浏览器原生保真（含图片/样式/排版），Edge/Chrome 可直接渲染，实现成本极低
- **服务端/自建端（补漏）**：SingleFile 式资源内联的净化 HTML（图片转 dataURL 或代理缓存），用于批量快照与存量补拍
- **查看**：扩展内置快照查看器（新标签打开）；导航站上失效书签自动显示「快照可用」标识，一键回看

**存储策略**：

| 形态 | 存储 | 限制 |
|---|---|---|
| 本地模式 | 扩展 IndexedDB/OPFS | 随设备容量 |
| 云端 Free | 对象存储 | 小配额（如 200MB / 100 份） |
| 云端 Pro | 对象存储 | 2GB，保留最近 N 个版本 |
| 自建 | 本地磁盘 | 不限，含历史版本 |

**安全与边界**：私密书签快照加密存储；隐私域名清单内不做快照；公开导航站**永不展示快照内容**，仅显示"有快照"状态（版权红线，与 §9 一致）。

**优先级**：手动一键 + 收藏时快照为 **P0**（M1，扩展端就地生成 + 本地/试用额度存储）；批量与服务端补漏为 P1；失效联动提示随 M2 死链任务上线。

### F3 AI 聊天整理（核心）
- **F3.1 [P0]** 对话入口（扩展侧栏）
- **F3.2 [P0]** 自然语言圈定范围："把开发文件夹 2023 年前的链接按内容重新分类"
- **F3.3 [P0]** 整理原子操作：自动分类（基于缓存正文而非标题）/ 改名与摘要 / 合并重复 / 新建目录结构 / 建议删除清单（删除永不自动执行）
- **F3.4 [P0]** **diff 预览 → 确认 → 应用**：按目录分组折叠展示；键盘 J/K 逐条浏览、空格切换接受/保留；每条可单独否决
- **F3.5 [P0]** 整理快照版本，一键撤销（收件箱自动归位共用此体系）
- **F3.6 [P0]** **"不满意→修正"闭环**：diff 页"哪里不满意？"输入框，一句话变成下一轮整理指令

## 7. 商业模式与成本

### 7.1 收费结构

| 层 | 定价 | 内容 |
|---|---|---|
| Free | ¥0 | 收藏/收件箱归位/整理/导航站基础能力；**AI 走 BYOK 完全免费**；云端 L1+L2 缓存配额 + 快照小配额（本地模式快照不限）；免费额度采用**行为配额**（如每月 3 次全库整理）而非容量配额——容量限制会劝退重度用户，而重度用户是付费转化主力 |
| Pro（订阅） | 年费 ¥99 早鸟价起（常规 ¥15–25/月 或 ¥128/年） | 无 BYOK 也能用 AI；快照配额；每周自动维护；无限版本历史；公开导航站去水印 |
| 自建 | **完全开源免费**（决策 D12） | 全功能自持；开源版与云端 Pro 的差异仅在于托管与配额、不做功能阉割，商业价值由云端 SaaS 承载 |

**原则：BYOK 用户永远有完全免费的完整体验。**

### 7.2 成本红线

- 云端默认只存 L1+L2，不存 L3 快照；Pro 快照配额上限（如 2GB）；正文截断 20KB/条
- 大规模整理走 F3.9 聚类策略；收藏即时归位走域名缓存（F1.4），AI 成本趋近于零
- 服务端抓取队列限速；死链分层探测降低请求量

## 8. 成功指标

**North Star：周活跃导航站（本周至少 3 天通过导航站/新标签页访问书签的用户数）**

**最小埋点集（9 事件）**：
`install → import_completed(条数) → stage1_result_viewed → diff_accepted(采纳率) → nav_generated → ntp_enabled → inbox_auto_sorted(收件箱归位数) → snapshot_created(快照数) → weekly_report_clicked`

| 指标 | 目标 |
|---|---|
| 导入→Aha 转化率（60s 内看到整理+导航站） | ≥ 40% |
| Aha 中"设为新标签页"比例 | ≥ 25% |
| diff 采纳率 | ≥ 70% |
| 收件箱归位采纳率（归位后无撤销比例） | ≥ 80% |
| W4 留存 | ≥ 20% |
| 周报点击率 | ≥ 30% |

**起手 A/B 实验**：① 体检报告前置 vs 直接导入；② 60s 快整理 vs 等待全量；③ diff 默认全选 vs 全不选。

> 「书签体检报告」获客钩子（安装首屏免费体检：死链/重复/久未访问统计，可分享卡片）随 M2 死链能力成熟后作为独立落地页投放。

## 9. 风险与合规

| 风险 | 等级 | 对策 |
|---|---|---|
| 商店审核：书签+网络抓取属高敏权限 | 高 | 权限最小化（就地捕获走 activeTab，无需全站 host permission）；隐私政策与数据说明页**提审前就绪**；Edge 先提审 |
| 抓取与快照版权 | 中 | 快照仅用户私有可见；公开导航站只展示元数据+摘要；robots 尊重；"仅元数据"开关 |
| 云端隐私悖论 | 中 | 明确数据边界；维护任务在自建端本地执行；内置常见敏感域隐私清单（银行/内网段） |
| 公开导航站滥用 | 中 | 敏感词过滤+举报入口；仅随机链接不做公开检索 |
| 死链误判伤信任 | 中 | 三级判定保守策略；疑似失效只标注；周报措辞用"建议" |
| AI 整理质量翻车 | 中 | diff 确认+版本回滚；收件箱歧义不强移；采纳率持续监控 |
| token/存储成本失控 | 中 | §7.2 红线；域名缓存+聚类策略；配额硬限 |

## 10. 路线图（功能里程碑制）

> 本项目采用 **AI 辅助开发模式**，不使用工期估算与传统项目管理工具。里程碑按**功能完整度**定义，以实际验证结果驱动节奏。

| 里程碑 | 交付（功能完整度定义） | 明确不做 |
|---|---|---|
| **M1 验证核心闭环** | 扩展（Edge+Chrome）+ 导入 + 一键收藏就地捕获与即时归位（F1.4）+ **自动分类收件箱（F1.5）** + **一键快照（F2.4，扩展端就地生成）** + 两阶段整理与聊天整理（分类/改名/合并/diff/回滚/修正闭环）+ 宫格导航站（1 模板）+ 新标签页 + 本地模式 + 全文搜索 + 云端试用额度支撑 Aha | 同步、死链任务、批量快照、语义搜索、私密书签、模板商城 |
| **M2 托管与维护** | 正式云端 SaaS 与订阅制 + 多端同步 + 死链/查重周任务与周报 + 体检报告获客页 + 模板扩至 4 套 + 发布控制 + BYOK 完善与偏好记忆 | — |
| **M3 自建生态** | Docker 自建服务端 + 全离线（Ollama）+ 私密书签 + 语义搜索 + 快照配额体系 + 迁移工具 + lite 镜像 | 模板 DSL 视验证结果决定 |

**M1 验证假设**：① 内容级整理采纳率 ≥ 70%；② 用户愿意设为新标签页；③ 收件箱归位采纳率 ≥ 80%（懒人模式成立）；④ 完成 Aha 用户 W4 留存显著更高。任一不成立，后续方向重估。

## 11. 决策记录

### 已定决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | 扩展先行，不做独立 Web 应用起步 | 书签源头在浏览器；零摩擦导入；新标签页阵地只有扩展能占据 |
| D2 | AI 用量 BYOK 优先，SaaS 代付型 Pro 后置 | M1 无商业化压力；BYOK 是极客圈信任信号 |
| D3 | 死链保守三级判定，疑似失效只标注 | 误删不可逆；标注-观察周期自然过滤误判 |
| D4 | 云端默认不存 L3 快照 | 存储成本红线；快照价值在付费/自建场景再开 |
| D5 | 公开导航站仅随机链接分享，不做公开广场 | 合规成本与冷启动价值不成比例 |
| D6 | 首发 Edge + Chrome 双上架，Edge 优先 | 参考竞品均在 Edge 生态；MV3 代码基本同源 |
| D7 | LLM 生态国产优先 | 目标用户在国内；BYOK 不支持 DeepSeek/智谱等端点则形同虚设；国产 token 成本约 1/10 |
| D8 | **新增自动分类收件箱为 P0 懒人主路径** | 补全被动堆积路径，与 F1.4 共用引擎；把使用门槛降到"随手一丢"，直接服务 JTBD |
| D9 | **AI 开发模式，不做工期管理** | 项目采用 AI 辅助开发；路线图以功能里程碑定义，按验证结果驱动节奏 |
| D10 | **一键快照升级为 P0 一等公民功能** | 产品负责人即目标用户，自证需求；扩展端 MHTML 一键生成实现成本极低；Raindrop 付费版验证过付费意愿；与死链检测构成"失效→有出路"闭环 |
| D11 | **产品名暂用 my-favorites 代号** | 正式名后续另议，不阻塞开发 |
| D12 | **自建端完全开源免费** | NAS 社区口碑优先；开源版与云端 Pro 的差异只在托管与配额、不做功能阉割，商业价值由云端 SaaS 承载 |
| D13 | **Pro 定价确认为 ¥99 早鸟 / ¥128 年费** | 对标 Raindrop Pro（$28/年）与 Cubox（¥198/年），处于该品类合理区间 |
| D14 | **开发路线采用"AI 深度打磨 → 自用 → 发布观察 → 反馈迭代"，不以全面调研为前置** | AI 降低实现与迭代成本，风险在缺少完成边界而非调研不足；按验收门槛推进，每轮只推进一个主要目标（2026-11-17 确认，来源：产品打磨与落地方案 §1） |
| D15 | **本轮只打磨"扩展 + 单用户 Docker 自建端"，不同时完善三种部署形态** | 完整纯本地模式与官方云端 SaaS 均为后续独立交付项；已有接口/配置预留不表述为"云端已就绪"（2026-11-17 确认） |
| D16 | **应用库是主数据；浏览器书签是导入源和可选镜像** | 以 `device_id + browser_bookmark_id ↔ app_bookmark_id` 显式映射定位，不用标题/URL 代替稳定身份；不承诺完整双向同步（2026-11-17 确认） |
| D17 | **导航是可选入口，资料找回是长期核心价值；不强制更换新标签页** | 用户可通过侧栏、管理台搜索获得价值；以真实任务完成与持续自用为主观察信号，导航曝光为辅（2026-11-17 确认） |
| D18 | **新标签页本地缓存 ≠ 完整纯本地模式，分开验收与宣传** | 缓存只做离线可用的首屏与标题/URL 基础搜索；正文/语义搜索仍依赖服务端时明确提示（2026-11-17 确认） |
| D19 | **私密书签在具备二次验证、客户端加密前标记为实验性** | 当前显示控制不等于加密保险箱；不宣传为"加密保险箱"，成熟前不作为卖点（2026-11-17 确认） |
| D20 | **收件箱"自动归位"正式实现镜像模式：同步移动浏览器节点，支持两端可理解的撤销** | 既然界面提示"归位"，浏览器侧书签必须真的移动，否则降级为误导；通过持久待执行记录同步浏览器状态，不与数据库共用事务（2026-11-17 确认，A2-4 选定正式实现） |
