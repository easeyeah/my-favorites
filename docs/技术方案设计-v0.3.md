## 1. 技术选型总览

### 1.1 选型原则

1. **NAS 约束优先**：自建镜像内存 <300MB、单文件存储、ARM64 可构建——所有选型先过这道闸
2. **AI 开发友好**：单一语言栈、强类型、约定清晰——降低 AI 辅助编码的上下文切换成本
3. **一套代码三种形态**：官方云 / 自建服务端 / 纯本地，共享同一套领域逻辑与 API 契约

### 1.2 选型结论

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | **TypeScript 全栈** | 扩展、服务端、管理台、导航站同语言；类型/领域模型/校验逻辑全栈共享；AI 编码工具对 TS 生态支持最好 |
| 扩展 | **Manifest V3 + Vite + React + WXT** | WXT 是目前 MV3 开发体验最好的框架（HMR、自动 manifest）；UI 组件与 Web 端复用 |
| 服务端 | **Hono（Node runtime）** | 轻量、Web 标准 API、中间件生态好；同一份代码可跑 Node（云端）与 Bun/Node 容器（自建） |
| ORM/DB | **Drizzle ORM**；自建 **SQLite（libsql）**，云端 **PostgreSQL** | Drizzle 对两者同一套 schema 风格；自建零外部依赖（无 Redis/无独立 DB 进程），内存占用低 |
| 任务队列 | 自建：**SQLite 表实现的进程内队列**；云端：**pgboss（Postgres）** | 刻意不引入 Redis——NAS 单容器是硬约束；两端实现同一 `JobQueue` 接口 |
| DOM 解析 | **linkedom** + **@mozilla/readability** | 比 jsdom 轻 10 倍量级，正文提取足够 |
| LLM 接入 | 自研轻量 `packages/ai`：OpenAI 兼容协议客户端 + Provider 适配 | DeepSeek/智谱/通义/Kimi/OpenAI/Anthropic/Ollama 全走 OpenAI 兼容端点（Anthropic 单独适配）；流式 SSE |
| 向量（P2） | 自建 **sqlite-vec**；云端 **pgvector** | 暂不做，接口先留 |
| 对象存储 | 云端 **S3 兼容**（快照/图标）；自建 **本地磁盘** | 同一 `BlobStore` 接口 |
| 共享包 | **pnpm monorepo + turbo** | 见 §2 |
| 组件 | **shadcn/ui**（扩展 + Web 管理台） | 组件源码复制进仓库、无运行时依赖；CSS 变量主题天然支持导航模板的深浅色/主题色定制（F4）；react-hook-form + zod 与 shared 包校验同线；AI 生成质量最稳 |
| 样式 | Tailwind CSS v4 | 三端复用；公开导航站页面（/s/:slug）用自定义轻量组件 + 原生 CSS，不引入 shadcn，保证首屏轻量与模板自由度 |

**备选说明**：Go 单二进制在内存上更优（<50MB），但会牺牲与扩展/UI 的类型共享与 AI 开发效率；Node+SQLite 实测可控制在 150–250MB，满足红线，权衡后选 TS 全栈。

### 1.3 实施偏离说明（正式决策，追加记录）

| 项 | 基线 | 实际 | 偏离原因与结论 |
|---|---|---|---|
| SQLite 驱动 | libsql（@libsql/client） | **node:sqlite**（Node ≥22 内置 `node:sqlite`） | 实施时 node:sqlite 已 stable（Node 22+），零原生依赖、免编译工具链、esbuild bundle 兼容，容器镜像与 ARM64 构建风险更低；libsql 的边缘复制等能力本项目不用。**Drizzle ORM 同步推迟**：当前 SQL 集中在 `store.ts` 仓储层、路由不摸 SQL，迁移成本可控；云端阶段引入 PostgreSQL 时再统一评估 ORM。此偏离不改变"自建 SQLite 单文件 + 无独立 DB 进程"的基线约束（2026-11-17 追加，A3-1） |

## 2. Monorepo 结构

```
my-favorites/
├── apps/
│   ├── extension/          # MV3 扩展（WXT + React）：popup / sidepanel / newtab / background / offscreen
│   ├── server/             # Hono API 服务端（云端与自建同构，按 env 区分形态）
│   └── web/                # Web 管理台 + 公开导航站渲染（SSG/SSR）
├── packages/
│   ├── shared/             # 领域模型、类型、zod schema、URL 规范化、分类规则引擎（域名映射表）
│   ├── ai/                 # LLM Provider 适配、整理编排 prompt、embedding 客户端
│   └── ui/                 # 三端共享 React 组件（导航站模板、diff 视图等）
├── docker/
│   └── Dockerfile          # 多阶段构建；buildx 支持 linux/arm64 + amd64
└── docs/
```

关键复用点：**分类规则引擎、URL 规范化、diff 计算、快照查看器**全部放 packages/shared 或 ui，扩展与服务端共用——这是"一套代码三种形态"的落地抓手。

## 3. 系统架构（三形态）

```
形态A 云端 SaaS（后续独立交付）：
  [扩展] → HTTPS → [API (Hono)] → [PostgreSQL] + [S3] + [pgboss 队列]
                        ↓                     ↓
                  [LLM Provider]        [爬虫/维护 Worker（独立进程，可水平扩）]

形态B 自建服务端（**当前交付**）：单容器
  [扩展] → HTTP(S) → [API + 进程内队列 + Worker] → [SQLite 文件] + [本地磁盘 /data]
                        ↓
                  [LLM：Ollama 或任意兼容端点（可全离线）]

形态C 纯本地（后续独立交付，D15/D35）：无服务端
  [扩展 IndexedDB/OPFS] 内置：规则引擎、本地整理（BYOK 直连 LLM）、
  快照本地存储、静态 HTML 导航导出
```

当前交付形态：**形态B 自建单容器**（D15）——扩展连接自建端，未连接时降级受限本地缓存（离线首屏 + 基础搜索，D18）。架构上从第一天就按"扩展可与三种后端对话"设计，切换后端只改 baseURL 与认证方式。

## 4. 数据模型（核心表）

> 所有表含 `user_id`（云端多用户）或归属单一 admin（自建），下述省略。

```ts
folder      { id, parent_id, name, sort, source, is_system_inbox }
            // source: imported | ai_created | user；收纳盒是 is_system_inbox 的系统目录
            // 命名说明：is_system_inbox 为内部标识（D36 暂保留），UI 文案一律显示「收纳盒」

bookmark    { id, folder_id, url_raw, url_canonical, title, description,
              status,          // normal | dead | suspect | archived
              site_type,       // site_tool | site_reference | content（站点化分析输出，D30/D31，可由投影重建）
              favicon_url, cover_url, visit_freq, added_at,
              last_checked_at, pinned }
            // 索引：url_canonical 唯一（查重基础）；folder_id；status；site_type；FTS 虚表(title/description/url)

content_cache { bookmark_id PK, l1_summary, l1_tags json, keywords,
                l2_text, lang, fetched_via,   // extension_capture | server_crawl
                fetched_at, fail_reason }     // null=成功

snapshot    { id, bookmark_id, format,        // mhtml | clean_html
              storage_key, size, version, created_at, via }
            // via: extension_mhtml | server_batch；云端走 S3，自建/本地走磁盘与 OPFS

organize_version { id, diff json, created_at, reverted }   // 整理/收纳盒共用回滚体系

domain_cache   { domain PK, category_path, hits, updated_at }  // F1.4 即时归位缓存
privacy_domain { id, pattern }                                 // 内置默认 + 用户自定义
job / job_run  { type, payload json, status, scheduled_at, … } // 死链/抓取/批量快照/清扫
maintenance_report { id, type, findings json, created_at }
nav_site    { id, template, config json, visibility, share_slug, password_hash }
usage       { period, ai_tokens, storage_bytes }               // 行为配额计量
hook        { id, url, events json, payload_level, secret_hash, allow_lan, enabled }
            // 集成 Hook（D33 预留，暂不排产）：payload_level: meta | meta+content；隐私命中永不外发
```

**设计要点**：
- `url_canonical` 生成规则：去 tracking 参数（utm_* 等）、统一 https 与末斜杠、小写域名——查重（F5.2）与唯一约束共用
- `organize_version.diff` 记录移动/改名/合并前的完整旧状态，回滚 = 逆放 diff，收纳盒自动归位与聊天整理共用，不另建体系
- 暂不建 tag 表（tags 以 json 存于 content_cache.l1_tags），语义搜索需要时再提升

## 5. API 设计（v1 摘要）

统一约定：`/api/v1`，JSON，云端 JWT Bearer；自建首次安装设 admin 密码 → 发 long-lived token。聊天与任务进度走 **SSE**。

| 域 | 端点 | 说明 |
|---|---|---|
| 认证 | `POST /auth/register` `POST /auth/login` | 自建无 register，安装向导建 admin |
| 书签 | `POST /bookmarks/ingest`（批量导入）`GET/POST/PATCH /bookmarks` `POST /bookmarks/check-dup` | ingest 返回导入统计 |
| 收纳盒 | `POST /inbox/process` `GET /inbox/items` `GET /inbox/count` `POST /inbox/assign`（rememberDomain 域名记忆）`POST /inbox/retry` | 状态机 pending/placed/ambiguous/privacy_hold/retry（inbox_state 表，原型 06）；每小时定时清扫兜底 |
| 站点化 | `POST /nav/projection/rebuild` `GET /nav/projection(/list)` | D30/D31 投影：classifySiteSignal 规则信号 + L1 摘要 AI 信号；site_type 标注不改目录（D16） |
| 点击 | `POST /bookmarks/:id/click` `GET /bookmarks/top` | D29 最常访问（bookmark_click 计数表） |
| Hook | `GET/POST/DELETE /settings/webhooks(/:id/test)` | D33 出站：HMAC-SHA256 签名 + guardFetchTarget SSRF 防护 + 退避重试 ×3；隐私命中永不外发 |
| 偏好 | `GET/PATCH /settings/prefs` | notifyStyle（D28 三档）+ organizeRules（原型 12 整理偏好，注入整理 LLM prompt） |
| 内容 | `POST /content/capture` `{bookmark_id, l2_text, favicon?}` | 扩展端就地捕获结果上行 |
| 快照 | `POST /snapshots`（multipart/binary）`GET /snapshots/:id` `DELETE` | MHTML 直传；本地模式不走此 API |
| 整理 | `POST /organize/sessions`（一次调用直接生效）`GET /organize/versions` `POST /organize/rollback/:versionId` | **D27 act + undo（切片 A 落地）：计划 + 提交在同请求内完成，返回 `status/versionId/applied/actions`（只读明细）；旧 `/apply`、`/proposal` 端点已移除**；rollback 逆放 diff 生成新版本 |
| 搜索 | `GET /search?q=&filters=` | 全文（FTS5） |
| 维护 | `POST /maintenance/links/run` `GET /maintenance/reports` | 分层探测 + 周报聚合 |
| 导航 | `POST /nav-sites` `PATCH /nav-sites/:id` `GET /s/:slug` | 公开渲染走 web 端 |
| 同步 | `GET /sync/pull?cursor=` `POST /sync/push` | 后续交付；游标增量 |
| 流式 | `GET /stream/:channel`（SSE） | 聊天 token 流、整理/任务进度 |
| Hook（预留） | `GET/PUT /settings/hooks` `POST /settings/hooks/test` | D33：出站 Webhook 配置与测试；触发事件与 payload 粒度按 Hook 配置；隐私命中永不外发 |

**错误与幂等**：写操作带 `Idempotency-Key`（扩展端 SW 可能重试）；AI 调用失败返回结构化错误码（`llm_unavailable` 等），前端据此引导 BYOK 设置。

## 6. 扩展端架构（MV3）

```
background (service worker)     —— 常驻事件中枢
  · bookmarks.onCreated/onMoved 监听收纳盒（系统事件可唤醒 SW，天然适合）
  · 右键菜单、快捷键、pageCapture 编排、与后端同步
offscreen document              —— DOM 密集任务（SW 无 DOM）
  · Readability 正文提取、净化 HTML 生成
sidepanel                       —— 聊天整理面板（React）
newtab                          —— 新标签页：默认「极简档」（搜索 + 最常访问），三档密度可自定义（D29）
popup                           —— 顶部标签页：快速收藏 / 收纳盒 / 整理入口（窄容器统一顶部标签导航）
options                         —— 服务端连接与端侧偏好（BYOK 归管理台 D35；扩展不持有 Key）
```

**MV3 约束对策**：
- SW 会被杀死 → 收纳盒监听依赖 bookmarks 事件（事件唤醒可靠）；长流水线下放到服务端或 offscreen，SW 只做编排与重试
- `activeTab` 权限在用户点击收藏瞬间注入捕获脚本，**不申请全站 host_permissions**（审核友好）
- 快照查看：`chrome-extension://` 页内嵌 iframe 加载 MHTML blob；IndexedDB 申请 `unlimitedStorage` 权限

**配置主场：管理台 → 设置 → AI 模型 · BYOK 管理主场（D35，交互复刻 ZCode 选择器）**：
- 左栏：已配置供应商列表，带状态点（实心=测试通过 / 半=未验证 / 灰=最近失败）+ 默认供应商标记
- 右栏「添加供应商」：分组预设（国内/国际/本地/自定义）→ 表单（BaseURL 预填可改、API Key、「拉取模型列表」——`supports_models_api` 为真时拉 `GET /models`，失败降级手动填）→「测试连接」（发一次最小补全请求）→ 保存
- **按用途分配模型**：整理 / 摘要 / embedding 三个用途分别指定（embedding 必须用专门模型，不能复用对话模型——域名缓存与聚类依赖它）
- **扩展端不持有 Key（D35）**：options 仅显示服务端连接与模型配置的只读状态；本地模式（后续交付）时此交互整体复用进扩展 options

**Key 存储**：本地模式存扩展 `chrome.storage.local`（加密）；服务端模式存 `provider_config` 表（`{user_id, provider_id, base_url, api_key_enc, models_cache, enabled}`，密钥加密落库）。API：`GET/PUT /settings/providers`、`POST /settings/providers/test`。

**运行时解析顺序**（`packages/ai` 统一出口）：按用途取用户指定模型 → 未指定则用默认供应商默认模型 → 均无则报 `llm_unavailable`（前端引导到设置页）。本地模式 BYOK 直连厂商，不经过任何服务端。

## 7. 关键流程设计



**① 收藏即时归位（<50ms 路径）**
```
popup 收藏 → 隐私校验（强制）→ 内容识别三级（D32：文章/视频/图片差异化处理）→ url_canonical → 查 domain_cache
  ├─ 命中 → 返回目标目录（<50ms，零 AI 成本）→ 用户点选确认 → 落库 + 异步内容捕获
  └─ 未命中 → 先落收纳盒目录 → 异步 LLM 分类 → 写回 domain_cache → 通知用户"已归位，可撤销"
```

**② 收纳盒流水线**
```
bookmarks 事件（收纳盒新增）→ SW 防抖聚合 → POST /inbox/process
  → 服务端流水线：域名规则初判 → 无缓存则补抓取 → AI 分类（正文上下文）
  → 置信度足 → 自动归位（写 organize_version）
  → 置信度不足 → 留在收纳盒 → 聚合进下次整理会话询问
  → SSE 推送结果 → 默认全自动（D28）：静默归位 + 轻提示可撤销；歧义留盒聚合询问
```

**③ 两阶段整理（首次导入）**
```
ingest（N 条）→ 阶段1：规则引擎（域名模式+目录语义+时间）<15s → 直接应用（D27 无确认流）+ 导航站生成
  → 后台阶段2：补抓取 → embedding 聚类（k≈√n）→ LLM 仅做簇命名与边界调整 → 逐条归属
  → 完成通知："AI 已按网页内容精修 43 条" → 通知卡（撤销 / 只读明细）
```

**④ 一键快照**
```
扩展端：pageCapture.captureMHTML(当前 tab) → OPFS/上传 POST /snapshots
  失败降级链：captureMHTML（部分 chrome:// 页不可用）→ offscreen 净化 HTML → 仅元数据
导航站渲染：status=dead 且有 snapshot → 卡片显示「快照可用」→ 查看器打开
```

**⑤ 死链分层探测**
```
job 调度 → DNS 解析（失败即判死）→ HEAD（2xx/3xx 判活）→ 异常 → GET 复验
  → 三级状态写入 bookmark.status → 周报聚合 → SSE/角标通知
```

**⑥ 整理与回滚（D27 无确认流）**
```
变更集(diff) → apply：乐观锁校验通过 → 直接生效 → 落库 + 新 organize_version + 通知（撤销 / 只读明细）
  → rollback：逆放 diff → 新 version（不删历史）；撤销亦生成新版本（D25 事务内核）
```

**⑦ 书签导入（双通道，F1.1 详细化）**

```
通道1 直接读取（主，扩展内一键完成，无需导出文件）：
  chrome.bookmarks.getTree() —— bookmarks 权限，一次调用读全树
  → 树形映射：浏览器目录结构 1:1 映射为 folder 树（保留层级与 sort）
  → bookmark.added_at 沿用浏览器记录的添加时间（排序与"久未访问"统计依赖它）
  → 逐条 url_canonical 化 → 与库内已有书签去重
通道2 文件导入（兜底）：
  Netscape HTML 书签文件解析（Firefox/Safari 手动导出、或用户不想授权 bookmarks 权限时）
  → 解析器放 packages/shared，Web 端与扩展共用
```

**导入策略细节**：
- **去重**：与库内 `url_canonical` 撞车的书签默认跳过；导入预览页展示"新增 N / 重复跳过 M"，重复项可勾选"仍导入为副本"（默认不勾）
- **幂等**：`ingest` 带 `Idempotency-Key`（首次导入生成并缓存在扩展 storage），SW 中断重试不会造成重复导入
- **收纳盒不入导入范围**：导入结果直接落在映射后的目录树中，不进自动收纳；随后自动触发两阶段整理（§7③）
- **隐私清单联动**：导入时即对 privacy_domain 清单内域名只存 URL（不触发任何抓取/捕获）
- **进度与体量**：千级书签导入分批上行（每批 100 条）+ SSE 进度；单批失败可续传
- **审核注意**：`bookmarks` 权限属高敏权限，上架说明需明确"仅导入，不做后台监控"（§9 风险表联动）

**⑧ 站点化分析与导航投影（D30/D31）**
```
站点识别：规则信号（URL 路径深度 / 文章路径模式 / 域名映射表分类）+ AI 信号（L1 摘要三类判定）
  → 三类输出：官网·工具（入导航投影）/ 资料站（默认不入：开关 + 自定义卡例外）/ 内容页（不入）
  → 同站归并：同域内容页 → 单站点卡（首页直达）；无首页域名 → 域名根升级（默认开启可撤销）
  → 排序：应用内点击频次 + 分组权重 + 最近使用 → 渲染 newtab / 公开导航站
投影可随时重建，不改书签数据（D16）；公开范围仍受 D23 显式发布集合约束；书签库按 site_type 筛选
```

**⑨ 集成 Hook（D33，契约预留，暂不排产）**
```
出站：收藏/整理/失效事件 → 隐私校验（命中永不外发）→ payload（仅元数据 / 含正文+分类）
  → HMAC-SHA256 签名 → POST 用户配置端点（SSRF 防护：内网目标需显式白名单；失败退避重试 ×3）
入站：外部工具 POST /api/v1/bookmarks（Idempotency-Key）→ 收纳盒流水线
护栏：产品不内置任何下载器预设模板——工具用户自备、责任自负
```

## 9. 安全设计

- 传输：全 TLS（自建文档化 Caddy 反代方案）
- 私密书签（后续交付）：客户端密钥派生（argon2）加密，服务端只存密文——自建端密钥用户自持
- 扩展最小权限：`bookmarks` + `activeTab` + `contextMenus` + `storage` + `unlimitedStorage`；不申请 tabs 全量权限（用 activeTab 查询当前页）
- LLM 数据边界：隐私域名清单在**发送 AI 前置校验**（架构上 impossible to bypass：校验在 packages/shared 分类引擎内，非可选步骤）
- Hook 数据边界（D33）：隐私域名命中**永不外发**（与 LLM 前置校验同一引擎）；不内置下载器模板；出站走 SSRF 守卫
- 公开导航站：slug 不可枚举（nanoid）、可选密码、内容只含元数据+摘要

## 11. 版本管理规范

> 项目将完全开源（决策 D12），git 历史即公开门面；同时 AI 辅助开发会产生大量提交，规范必须让"机器写的提交"也可读、可回溯。

### 11.1 Git 仓库与分支

- **Trunk-based**：`main` 为唯一主干（已初始化，首提交 `8a83aed`）；功能用短生命周期分支或直接主干 + feature flag，避免长期分支堆积冲突——AI 开发小步快跑模式下 trunk-based 冲突成本最低
- **Conventional Commits** 强制（`feat/fix/docs/chore/refactor/test/build`）：既是人读的，也是 changelog 自动生成的数据源；AI 生成的提交按此格式校验（CI 加 commitlint）
- 仓库即将托管到远端（GitHub，配合开源与 CI），`main` 设分支保护

### 11.2 版本号策略（SemVer + changesets）

- **各 app 独立版本**：`apps/extension`（extension manifest version，受商店约束）、`apps/server`、`apps/web` 各自 semver；`packages/*` 用 workspace 协议内部引用、不独立发 npm，版本跟随所属 app
- **changesets** 管理版本与 CHANGELOG：功能合入时顺手写一条 changeset（AI 提交时一并生成），发布时自动汇总 bump 版本——monorepo 标准方案
- **版本对应关系**：扩展与 server 大版本保持同步节奏（协议兼容矩阵记录在 `packages/shared`）；`/api/v1` 路径版本独立于 app 版本， breaking 才升 `/v2`

### 11.3 发布制品与 tag

| 制品 | 版本来源 | 说明 |
|---|---|---|
| Docker 镜像（自建端） | git tag（如 `server-v0.3.0`）+ 短 sha 双 tag | buildx 双架构；Release 附 SHA256 |
| 扩展（商店包） | manifest version = extension 包版本 | 商店审核周期长，版本先行占位 |
| GitHub Release | `git tag` + changesets 生成的 CHANGELOG | 开源后即公开 |

- tag 规范：`<app>-vX.Y.Z`（`server-v0.3.0` / `extension-v0.3.0`），CI 按 tag 前缀触发对应制品构建
- **DB 迁移与发布绑定**：Drizzle 迁移只前进不回滚；自建端启动时自动执行迁移，**迁移前自动备份 SQLite**（复用 §8 备份机制）——版本升级永远可回退到旧镜像 + 备份文件
  - **A3-1 落地（2026-11-17）**：`apps/server/src/migrate.ts` 实现有序带版本号迁移（`schema_migrations` 表），基线 = M1/M2/M3 全量 schema（版本 1，幂等重放兼容旧库），此后每个变更一个版本（v2 整理修订/软归档、v3 设备身份映射/待执行操作）。迁移前用 `VACUUM INTO` 做在线一致性备份（WAL 活跃下安全，等效 SQLite backup API）；单版本事务执行，失败回滚不留半套。实测：旧库升级、WAL 备份一致性、备份恢复演练见 `migrate.test.ts`
- registry（供应商预设/域名映射表）变更走普通 PR + changeset，随版本发布，不热更新

### 11.4 文档版本约定

- 产品文档（功能文档/技术方案）随代码同仓库管理（`docs/`），功能变更必须回写文档并递增小版本（如功能文档 v0.3 → v0.3.1）
- 技术方案的"决策记录"（功能文档 §11）新增只追加不修改；被推翻的决策标记 superseded 并指向新决策

### 12.2 出站网络守卫（DEV-04，`fetch-guard.ts`）

- 请求前：scheme 白名单 + 字面 IP/全部 DNS 地址判定（`parseIpv6` 完整支持压缩/IPv4-mapped/NAT64/fe80::/10/fc00::/7/ff00::/8）；allowlist 仅覆盖字面内网 IP 时放行。
- 连接：`pinnedRequest` 直连**已校验地址**（保留 Host 头与 TLS SNI），消除 DNS 校验与连接之间的 rebinding 窗口；多地址按序 fallback，保留底层错误原因（ECONNREFUSED 等）。
- 资源：每跳连接/响应头超时；`readBody(maxBytes)` 读取期强制字节上限（超限抛 `BodyTooLargeError` 并销毁连接）；`totalTimeoutMs` 覆盖全部跳；重定向跳立即 dispose。
- 重定向：手动跟随、每跳重新校验；跨主机剥离 authorization/cookie 等敏感头。
- 维护探测（死链检测）与抓取（crawl）同走该守卫；隐私域书签不自动探测（探测即向第三方发送"在册"信号），部署显式 allowlist 覆盖的字面内网 IP 例外。
- 模型端点（`packages/ai`）：管理员显式配置不套 SSRF 规则（Ollama 内网可用）；重定向手动跟随、跨主机剥离 Authorization（Key 不外送）、总超时覆盖。

### 12.3 统一整理提交内核（DEV-08，`organize.ts` / `pipeline.ts`）

- 提案：move 动作携带 `plannedFolderId`（稳定 ID，同名目录可区分）；createFolder 在 apply 事务内解析 planned→actual 映射（同名存在即复用）。
- 提交：短事务内逐项 `commitCheck`（存在性/revision/隐私策略/私密/目标目录存在/inbox 归属），失败项记原因码（`modified_after_proposal`/`privacy_changed`/`target_missing`/`not_in_inbox`）；镜像操作（`pending_browser_ops`）与实体/版本同事务入队；任意异常 ROLLBACK。
- 幂等：会话已 applied 时重试返回原版本（`getVersionBySession`），不产生第二份版本。
- 撤销：生成新 undo 版本（`reverts_version_id` 指向原版本），逐项检查后续修改（revision 不符跳过并报告）；反向镜像同事务入队并取消待执行旧操作（避免晚到覆盖）；原历史保留并标记 reverted。
- 收纳盒两阶段：规则移动（事务 A）→ LLM 事务外计算 → 提交事务 B（重查规则修订/私密/归属，过期项丢弃 `stale_*` 原因码）。

### 12.4 令牌与首启（DEV-05）

- 令牌：32 字节随机 base64url，仅 SHA-256 摘要落库；`token_id` 为随机非密 ID（列表/撤销用）；默认 30 天到期；`last_used_at` 记录；logout/改密撤销。
- 首启：生产语义（MF_ENV 非 dev/test）setup 需 `x-mf-setup-token`（来源 MF_SETUP_TOKEN 或自动生成的 `/data/bootstrap-token.txt`，600 权限）；settings 主键原子 INSERT 保证并发 setup 至多一个成功；成功后引导凭据立即删除。
- 限速：内存滑窗 5 次/分钟/key，key 区分 `admin-env:<ip>` / `admin-db:<ip>` / `nav:<slug>:<ip>`；表容量上限 + 过期清理；仅 `MF_TRUST_PROXY=1` 时采信 X-Forwarded-For。
- CORS：`MF_ALLOWED_ORIGINS` 白名单；非生产语义放行 localhost/扩展开发源；CORS 不代替认证。

### 12.5 可见性边界（DEV-02）

- `AccessContext`：管理面（鉴权后 + `X-MF-Private: 1` 显式开关）可见私密；公开面（/s/*）只可见显式发布集合内的非私密、非软归档项。
- `/content/:id` 先鉴权书签对象再读缓存；不存在与不可读同响应 404（不泄露存在性）。
- 旧 `/api/v1/snapshots/:id` 直读封堵为 410（受控下载 /download、净化查看 /view 为唯一通道）。
- 关键词/语义/导出同边界；语义搜索追加软归档过滤（E03 修复）。

### 12.6 隐私失效策略（DEV-03）

- 扩展端规则缓存状态机：unknown/fresh/stale/error；仅 fresh 允许五动作；stale 时旧规则仍用于拒绝（命中即 `privacy_domain`），未命中也拒绝（`policy_not_loaded`）；缓存按服务端实例隔离（切换服务器回 unknown）。
- 服务端：所有模型入口（摘要/整理/embedding）走 `checkPrivacy`；LLM 等待返回后提交前重读规则修订与实体状态，过期结果丢弃（`stale_policy_discarded`）。
- 规则变更清理：游标分页全量扫描（含软归档）；清空正文/摘要/关键词/向量；快照文件删除失败入 `pending_snapshot_deletions` 台账重试；永不删除原书签（红线 3）。
