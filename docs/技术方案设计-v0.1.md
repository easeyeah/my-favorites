# my-favorites 技术方案设计（v0.1 草案）

> 依据：功能文档 v0.3（权威版）。本文档覆盖 M1 范围为主，M2/M3 仅预留扩展点。
> 状态：待评审。评审通过后据此搭建 monorepo 骨架。

---

## 1. 技术选型总览

### 1.1 选型原则

1. **NAS 约束优先**：自建镜像内存 <300MB、单文件存储、ARM64 可构建——所有选型先过这道闸
2. **AI 开发友好**：单一语言栈、强类型、约定清晰——降低 AI 辅助编码的上下文切换成本
3. **一套代码三种形态**：官方云 / 自建服务端 / 纯本地，共享同一套领域逻辑与 API 契约

### 1.2 选型结论

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | **TypeScript 全栈** | 扩展、服务端、管理台、导航站同语言；类型/领域模型/校验逻辑全栈共享；AI 编码工具对 TS 生态支持最好 |
| 扩展 | **Manifest V3 + Vite + React + WXT** | WXT 是目前 MV3 开发体验最好的框架（HMR、自动 manifest）；UI 组件与 Web 端复用 |
| 服务端 | **Hono（Node runtime）** | 轻量、Web 标准 API、中间件生态好；同一份代码可跑 Node（云端）与 Bun/Node 容器（自建） |
| ORM/DB | **Drizzle ORM**；自建 **SQLite（libsql）**，云端 **PostgreSQL** | Drizzle 对两者同一套 schema 风格；自建零外部依赖（无 Redis/无独立 DB 进程），内存占用低 |
| 任务队列 | 自建：**SQLite 表实现的进程内队列**；云端：**pgboss（Postgres）** | 刻意不引入 Redis——NAS 单容器是硬约束；两端实现同一 `JobQueue` 接口 |
| DOM 解析 | **linkedom** + **@mozilla/readability** | 比 jsdom 轻 10 倍量级，正文提取足够 |
| LLM 接入 | 自研轻量 `packages/ai`：OpenAI 兼容协议客户端 + Provider 适配 | DeepSeek/智谱/通义/Kimi/OpenAI/Anthropic/Ollama 全走 OpenAI 兼容端点（Anthropic 单独适配）；流式 SSE |
| 向量（P2） | 自建 **sqlite-vec**；云端 **pgvector** | M1 不做，接口先留 |
| 对象存储 | 云端 **S3 兼容**（快照/图标）；自建 **本地磁盘** | 同一 `BlobStore` 接口 |
| 共享包 | **pnpm monorepo + turbo** | 见 §2 |
| 组件 | **shadcn/ui**（扩展 + Web 管理台） | 组件源码复制进仓库、无运行时依赖；CSS 变量主题天然支持导航模板的深浅色/主题色定制（F4）；react-hook-form + zod 与 shared 包校验同线；AI 生成质量最稳 |
| 样式 | Tailwind CSS v4 | 三端复用；公开导航站页面（/s/:slug）用自定义轻量组件 + 原生 CSS，不引入 shadcn，保证首屏轻量与模板自由度 |

**备选说明**：Go 单二进制在内存上更优（<50MB），但会牺牲与扩展/UI 的类型共享与 AI 开发效率；Node+SQLite 实测可控制在 150–250MB，满足红线，权衡后选 TS 全栈。

## 2. Monorepo 结构

```
my-favorites/
├── apps/
│   ├── extension/          # MV3 扩展（WXT + React）：popup / sidepanel / newtab / background / offscreen
│   ├── server/             # Hono API 服务端（云端与自建同构，按 env 区分形态）
│   └── web/                # Web 管理台 + 公开导航站渲染（SSG/SSR）
├── packages/
│   ├── shared/             # 领域模型、类型、zod schema、URL 规范化、分类规则引擎（域名映射表）
│   ├── ai/                 # LLM Provider 适配、整理编排 prompt、embedding 客户端
│   └── ui/                 # 三端共享 React 组件（导航站模板、diff 视图等）
├── docker/
│   └── Dockerfile          # 多阶段构建；buildx 支持 linux/arm64 + amd64
└── docs/
```

关键复用点：**分类规则引擎、URL 规范化、diff 计算、快照查看器**全部放 packages/shared 或 ui，扩展与服务端共用——这是"一套代码三种形态"的落地抓手。

## 3. 系统架构（三形态）

```
形态A 云端 SaaS（M2）：
  [扩展] → HTTPS → [API (Hono)] → [PostgreSQL] + [S3] + [pgboss 队列]
                        ↓                     ↓
                  [LLM Provider]        [爬虫/维护 Worker（独立进程，可水平扩）]

形态B 自建服务端（M3）：单容器
  [扩展] → HTTP(S) → [API + 进程内队列 + Worker] → [SQLite 文件] + [本地磁盘 /data]
                        ↓
                  [LLM：Ollama 或任意兼容端点（可全离线）]

形态C 纯本地（M1 就绪）：无服务端
  [扩展 IndexedDB/OPFS] 内置：规则引擎、本地整理（BYOK 直连 LLM）、
  快照本地存储、静态 HTML 导航导出
```

M1 实际形态：**形态C 为主 + 云端试用额度（形态A 的最小版：账号 + L1/L2 缓存 + AI 代理额度）支撑 Aha**。架构上从第一天就按"扩展可与三种后端对话"设计，切换后端只改 baseURL 与认证方式。

## 4. 数据模型（核心表）

> 所有表含 `user_id`（云端多用户）或归属单一 admin（自建），下述省略。

```ts
folder      { id, parent_id, name, sort, source, is_system_inbox }
            // source: imported | ai_created | user；收件箱是 is_system_inbox 的系统目录

bookmark    { id, folder_id, url_raw, url_canonical, title, description,
              status,          // normal | dead | suspect | archived
              favicon_url, cover_url, visit_freq, added_at,
              last_checked_at, pinned }
            // 索引：url_canonical 唯一（查重基础）；folder_id；status；FTS 虚表(title/description/url)

content_cache { bookmark_id PK, l1_summary, l1_tags json, keywords,
                l2_text, lang, fetched_via,   // extension_capture | server_crawl
                fetched_at, fail_reason }     // null=成功

snapshot    { id, bookmark_id, format,        // mhtml | clean_html
              storage_key, size, version, created_at, via }
            // via: extension_mhtml | server_batch；云端走 S3，自建/本地走磁盘与 OPFS

organize_version { id, diff json, created_at, reverted }   // 整理/收件箱共用回滚体系

domain_cache   { domain PK, category_path, hits, updated_at }  // F1.4 即时归位缓存
privacy_domain { id, pattern }                                 // 内置默认 + 用户自定义
job / job_run  { type, payload json, status, scheduled_at, … } // 死链/抓取/批量快照/清扫
maintenance_report { id, type, findings json, created_at }
nav_site    { id, template, config json, visibility, share_slug, password_hash }
usage       { period, ai_tokens, storage_bytes }               // 行为配额计量
```

**设计要点**：
- `url_canonical` 生成规则：去 tracking 参数（utm_* 等）、统一 https 与末斜杠、小写域名——查重（F5.2）与唯一约束共用
- `organize_version.diff` 记录移动/改名/合并前的完整旧状态，回滚 = 逆放 diff，收件箱自动归位与聊天整理共用，不另建体系
- M1 不建 tag 表（tags 以 json 存于 content_cache.l1_tags），语义搜索需要时再提升

## 5. API 设计（v1 摘要）

统一约定：`/api/v1`，JSON，云端 JWT Bearer；自建首次安装设 admin 密码 → 发 long-lived token。聊天与任务进度走 **SSE**。

| 域 | 端点 | 说明 |
|---|---|---|
| 认证 | `POST /auth/register` `POST /auth/login` | 自建无 register，安装向导建 admin |
| 书签 | `POST /bookmarks/ingest`（批量导入）`GET/POST/PATCH /bookmarks` `POST /bookmarks/check-dup` | ingest 返回导入统计 |
| 收件箱 | `POST /inbox/process` `{bookmark_ids}` | 触发归位流水线；扩展监听事件后调用 |
| 内容 | `POST /content/capture` `{bookmark_id, l2_text, favicon?}` | 扩展端就地捕获结果上行 |
| 快照 | `POST /snapshots`（multipart/binary）`GET /snapshots/:id` `DELETE` | MHTML 直传；本地模式不走此 API |
| 整理 | `POST /organize/sessions`（聊天）`GET /organize/sessions/:id/proposal` `POST .../apply` `POST .../rollback` | proposal 即 diff；apply 前强校验版本连续性 |
| 搜索 | `GET /search?q=&filters=` | M1 全文（FTS5） |
| 维护 | `POST /maintenance/links/run` `GET /maintenance/reports` | M2 |
| 导航 | `POST /nav-sites` `PATCH /nav-sites/:id` `GET /s/:slug` | 公开渲染走 web 端 |
| 同步 | `GET /sync/pull?cursor=` `POST /sync/push` | M2；游标增量 |
| 流式 | `GET /stream/:channel`（SSE） | 聊天 token 流、整理/任务进度 |

**错误与幂等**：写操作带 `Idempotency-Key`（扩展端 SW 可能重试）；AI 调用失败返回结构化错误码（`llm_unavailable` 等），前端据此引导 BYOK 设置。

## 6. 扩展端架构（MV3）

```
background (service worker)     —— 常驻事件中枢
  · bookmarks.onCreated/onMoved 监听收件箱（系统事件可唤醒 SW，天然适合）
  · 右键菜单、快捷键、pageCapture 编排、与后端同步
offscreen document              —— DOM 密集任务（SW 无 DOM）
  · Readability 正文提取、净化 HTML 生成
sidepanel                       —— 聊天整理面板（React）
newtab                          —— 导航站（复用 packages/ui 模板渲染）
popup                           —— 一键收藏 + 即时归位建议
options                         —— BYOK、服务端地址、隐私清单、快照开关
```

**MV3 约束对策**：
- SW 会被杀死 → 收件箱监听依赖 bookmarks 事件（事件唤醒可靠）；长流水线下放到服务端或 offscreen，SW 只做编排与重试
- `activeTab` 权限在用户点击收藏瞬间注入捕获脚本，**不申请全站 host_permissions**（审核友好）
- 快照查看：`chrome-extension://` 页内嵌 iframe 加载 MHTML blob；IndexedDB 申请 `unlimitedStorage` 权限

### 6.1 模型供应商管理（BYOK，交互参考 ZCode 供应商选择器）

**注册表即数据**：供应商预设全部为 `packages/ai/providers.json` 纯数据（新增供应商 = 加一条 JSON，不动代码）：

```ts
// packages/ai/src/registry.ts
{ id, name, icon, group,          // group: "国内" | "国际" | "本地"
  api_style,                      // openai-compatible | anthropic
  base_url,                       // 预填默认值，可改
  key_url,                        // "获取 API Key" 跳转链接
  models: [...],                  // 推荐模型预填列表
  supports_models_api }           // 支持 GET /models 则可在线拉取
```

**内置预设**（BaseURL 以各官方文档为准，随 registry 维护；Coding Plan/Token Plan 类订阅端点不纳入，仅内置 API 变体）：

| 分组 | 预设 | API 风格 | 默认 BaseURL（预填） |
|---|---|---|---|
| 国内 | DeepSeek | OpenAI 兼容 | `https://api.deepseek.com/v1` |
| 国内 | 智谱 BigModel | OpenAI 兼容 | `https://open.bigmodel.cn/api/paas/v4` |
| 国内 | 阿里云百炼（中国） | OpenAI 兼容 | `https://dashscope.aliyuncs.com/compatible-mode/v1` |
| 国内 | Kimi（Moonshot 国内） | OpenAI 兼容 | `https://api.moonshot.cn/v1` |
| 国内 | MiniMax | OpenAI 兼容 | 官方文档核对后预填 |
| 国内 | 火山方舟 | OpenAI 兼容 | `https://ark.cn-beijing.volces.com/api/v3` |
| 国内 | 腾讯 TokenHub | OpenAI 兼容 | 官方文档核对后预填 |
| 国内 | 小米 MiMo | OpenAI 兼容 | 官方文档核对后预填 |
| 国际 | OpenAI / Anthropic / Z.ai / Kimi 国际 / 阿里云百炼（国际） | OpenAI 兼容 / Anthropic | 对应官方端点 |
| 本地 | Ollama | OpenAI 兼容 | `http://localhost:11434/v1` |
| — | 自定义供应商 | OpenAI 兼容 | 用户自填 |

**设置页交互（options，复刻 ZCode 选择器）**：
- 左栏：已配置供应商列表，带状态点（绿=测试通过 / 橙=未验证 / 红=最近失败）+ 默认供应商标记
- 右栏「添加供应商」：分组卡片（国内/国际/本地/自定义）→ 点选预设 → 表单（BaseURL 预填可改、API Key、「获取模型列表」按钮——`supports_models_api` 为真时拉 `GET /models`，失败降级为手动填模型 ID）→「测试连接」（发一次最小补全请求）→ 保存
- **按用途分配模型**：整理 / 摘要 / embedding 三个用途可分别指定模型（embedding 必须用专门模型，不能复用对话模型——域名缓存与聚类阶段依赖它）

**Key 存储**：本地模式存扩展 `chrome.storage.local`（加密）；服务端模式存 `provider_config` 表（`{user_id, provider_id, base_url, api_key_enc, models_cache, enabled}`，密钥加密落库）。API：`GET/PUT /settings/providers`、`POST /settings/providers/test`。

**运行时解析顺序**（`packages/ai` 统一出口）：按用途取用户指定模型 → 未指定则用默认供应商默认模型 → 均无则报 `llm_unavailable`（前端引导到设置页）。本地模式 BYOK 直连厂商，不经过任何服务端。

## 7. 关键流程设计



**① 收藏即时归位（<50ms 路径）**
```
popup 收藏 → url_canonical → 查 domain_cache
  ├─ 命中 → 返回目标目录（<50ms，零 AI 成本）→ 用户点选确认 → 落库 + 异步内容捕获
  └─ 未命中 → 先落收件箱目录 → 异步 LLM 分类 → 写回 domain_cache → 通知用户"已归位，可撤销"
```

**② 收件箱流水线**
```
bookmarks 事件（收件箱新增）→ SW 防抖聚合 → POST /inbox/process
  → 服务端流水线：域名规则初判 → 无缓存则补抓取 → AI 分类（正文上下文）
  → 置信度足 → 自动归位（写 organize_version）
  → 置信度不足 → 留在收件箱 → 聚合进下次整理会话询问
  → SSE 推送结果 → 扩展角标/toast
```

**③ 两阶段整理（首次导入）**
```
ingest（N 条）→ 阶段1：规则引擎（域名模式+目录语义+时间）<15s → 产出 proposal → 用户采纳
  → 后台阶段2：补抓取 → embedding 聚类（k≈√n）→ LLM 仅做簇命名与边界调整 → 逐条归属
  → 完成通知："AI 已按网页内容精修 43 条 → 查看 diff"
```

**④ 一键快照**
```
扩展端：pageCapture.captureMHTML(当前 tab) → OPFS/上传 POST /snapshots
  失败降级链：captureMHTML（部分 chrome:// 页不可用）→ offscreen 净化 HTML → 仅元数据
导航站渲染：status=dead 且有 snapshot → 卡片显示「快照可用」→ 查看器打开
```

**⑤ 死链分层探测（M2）**
```
job 调度 → DNS 解析（失败即判死）→ HEAD（2xx/3xx 判活）→ 异常 → GET 复验
  → 三级状态写入 bookmark.status → 周报聚合 → SSE/角标通知
```

**⑥ 整理与回滚**
```
proposal(diff) → apply：服务端校验 base_version 一致（乐观锁）→ 落库 + 新 organize_version
  → rollback：逆放 diff → 新 version（不删历史）
```

**⑦ 书签导入（双通道，F1.1 详细化）**

```
通道1 直接读取（主，扩展内一键完成，无需导出文件）：
  chrome.bookmarks.getTree() —— bookmarks 权限，一次调用读全树
  → 树形映射：浏览器目录结构 1:1 映射为 folder 树（保留层级与 sort）
  → bookmark.added_at 沿用浏览器记录的添加时间（排序与"久未访问"统计依赖它）
  → 逐条 url_canonical 化 → 与库内已有书签去重
通道2 文件导入（兜底）：
  Netscape HTML 书签文件解析（Firefox/Safari 手动导出、或用户不想授权 bookmarks 权限时）
  → 解析器放 packages/shared，Web 端与扩展共用
```

**导入策略细节**：
- **去重**：与库内 `url_canonical` 撞车的书签默认跳过；导入预览页展示"新增 N / 重复跳过 M"，重复项可勾选"仍导入为副本"（默认不勾）
- **幂等**：`ingest` 带 `Idempotency-Key`（首次导入生成并缓存在扩展 storage），SW 中断重试不会造成重复导入
- **收件箱不入导入范围**：导入结果直接落在映射后的目录树中，不进自动分类收件箱；随后自动触发两阶段整理（§7③）
- **隐私清单联动**：导入时即对 privacy_domain 清单内域名只存 URL（不触发任何抓取/捕获）
- **进度与体量**：千级书签导入分批上行（每批 100 条）+ SSE 进度；单批失败可续传
- **审核注意**：`bookmarks` 权限属高敏权限，上架说明需明确"仅导入，不做后台监控"（§9 风险表联动）

## 8. 部署与运维

- **自建**：单容器 `docker compose up`；volume 挂 `/data`（SQLite + 快照 + 图标）；env：`ADMIN_PASSWORD`、`LLM_BASE_URL`、`LLM_API_KEY`、`PORT`；buildx 双架构；镜像目标 <200MB；健康检查 `/healthz`
- **云端**：API 无状态多副本；Worker 独立部署可扩；Postgres + S3；配额计量入 `usage` 表
- **备份**：自建内置定时 `VACUUM INTO` 生成 SQLite 单文件快照到 `/data/backups`（NAS 用户可直接再同步到群晖 Hyper Backup）
- **迁移**：云端↔自建走 JSON 全量导出/导入（复用 F1.6）

### 8.1 本地开发与测试环境（Docker 优先）

**原则：服务端一律在本地 Docker 里运行和测试**——开发环境即自建端形态，M1 起持续验证镜像内存/体积红线（对应 §10 风险表）。

```yaml
# docker/docker-compose.dev.yml（草案）
services:
  server:            # 自建端形态：Hono API + 进程内队列 + Worker + SQLite
    build: { context: .., dockerfile: docker/Dockerfile, target: dev }
    volumes:
      - ../apps/server:/app/apps/server        # 源码挂载 + watch 模式热重载
      - ../packages:/app/packages
      - server-data:/data                      # SQLite / 快照 / 图标
    ports: ["3000:3000"]
    environment:
      LLM_BASE_URL: http://llm-mock:8080/v1    # 默认 mock；联调真实模型时改端点
  llm-mock:          # 轻量 mock：可脚本化返回固定分类/摘要/SSE 流（CI 稳定、零 token 成本）
    image: node:22-alpine
    # 或切 profile 接本机 Ollama（host.docker.internal:11434）
volumes: { server-data: {} }
```

**开发工作流**：
- 服务端：`docker compose -f docker/docker-compose.dev.yml up`（容器内 watch 热重载）
- 扩展：宿主机 `pnpm --filter extension dev`（WXT HMR）；MV3 dev manifest 加 `host_permissions: ["http://localhost:3000/*"]`，扩展设置里服务端地址填 `http://localhost:3000`
- LLM 三档切换：`llm-mock`（日常开发/CI）→ 本机 Ollama（离线联调）→ 真实端点（DeepSeek/智谱等，验证 prompt 质量），只改 `LLM_BASE_URL` 不改代码

**测试分层**：
| 层 | 工具 | 跑在哪 |
|---|---|---|
| 单元（规则引擎/URL 规范化/diff） | vitest | 宿主机 |
| API 集成 | vitest + supertest，对 Docker 内 server | Docker |
| E2E | Playwright 加载未打包扩展 + Docker server | Docker + 宿主机 Chromium |
| 镜像冒烟 | 构建生产镜像 → 容器内存峰值/体积断言（<300MB / <200MB） | Docker（CI 同款） |

- 种子数据：`pnpm seed` 生成含边界情况的书签集（重复 URL、死链、隐私域名、超长标题、千级目录树），供导入与整理流程测试

## 9. 安全设计

- 传输：全 TLS（自建文档化 Caddy 反代方案）
- 私密书签（M3）：客户端密钥派生（argon2）加密，服务端只存密文——自建端密钥用户自持
- 扩展最小权限：`bookmarks` + `activeTab` + `contextMenus` + `storage` + `unlimitedStorage`；不申请 tabs 全量权限（用 activeTab 查询当前页）
- LLM 数据边界：隐私域名清单在**发送 AI 前置校验**（架构上 impossible to bypass：校验在 packages/shared 分类引擎内，非可选步骤）
- 公开导航站：slug 不可枚举（nanoid）、可选密码、内容只含元数据+摘要

## 10. 技术风险与验证点

| 风险 | 影响 | 验证/对策 |
|---|---|---|
| captureMHTML 兼容性（chrome:// 页、部分 CSP 页面失败） | 快照覆盖率 | M1 首周做兼容性探针清单；降级链已设计（§7④） |
| linkedom 对复杂页面的 Readability 提取质量 | L1 摘要质量 | 用 100 条真实书签建评测集，提取失败率 >15% 则换 jsdom |
| Node 容器内存超 300MB 红线（并发抓取时） | NAS 口碑 | 队列并发默认 2、抓取流式处理；CI 加内存冒烟测试 |
| MV3 SW 生命周期导致收件箱事件丢失 | 懒人模式可靠性 | 事件唤醒验证 + 服务端定时清扫兜底（每小时） |
| SQLite 并发写瓶颈（自建多设备同步时） | M3 同步体验 | WAL 模式；写队列单线程化；上限内足够 |
| LLM 分类质量不达 70% 采纳率 | 核心假设 | M1 用评测集先离线跑通 prompt 与聚类策略，再接 UI |
