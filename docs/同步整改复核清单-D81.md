## 3. 逐项整改与验收

### SYNC-R01：过期恢复绕过目录删除保险丝

**位置：** `apps/extension/src/lib/sync.ts:715–735`，`doAlign({ recover: true })`。

**问题：** 恢复时逐条书签删除经过保险丝，但消失目录随后直接生成 `folder.deleteTree`，未执行目录级保险丝。浏览器目录大量消失且日志过期时，已挂起的书签删除可能被树删路径绕过。

**整改要求：**
- tick/recover 共用删除计划与保险丝判定。
- 树删及其覆盖的叶子删除作为一个确认单元，禁止通过另一条路径执行。
- 确认前持久保留操作与范围，成功后才清除。

**验收：**
- [x] 基线至少 5 个目录，离线删除超过 3 个且超过一半，再制造日志过期；恢复后库目录和书签保留，状态为待确认。
- [x] 挂起后重启 SW，仍保持待确认，无自动树删。
- [x] 用户确认后按确认范围删除；失败的子操作仍可重试。

### SYNC-R02：目录基线提前更新吞掉失败操作

**位置：** `apps/extension/src/lib/sync.ts:885、1202–1240`，`doTick` / `consumeResults`。

**问题：** `base.folders = { ...snapshot.folders, ...walk.snapshot.folders }` 在服务端确认前覆盖目录基线。单条创建、改名或移动返回 `failed/skipped` 后，整轮仍可能保存新基线，下一轮 diff 不再包含该操作。

**整改要求：**
- 区分扫描观察值与已确认基线。
- 目录创建、改名、移动仅在成功回执后更新对应基线；失败保留旧基线或持久待处理操作。
- 为 `skipped` 定义终态与可重试分类，不能一律当成功或无限静默重试。

**验收：**
- [x] 分别让 folder.create / rename / move 首次返回失败；恢复后无需再次手动修改目录即可收敛。
- [x] 失败期间界面不报正常，SW 重启不丢操作。
- [x] 保留 D75 目录删除检测能力，不能为了延后基线提交再次漏登记目录。

### SYNC-R03：绑定既有书签时目录身份使用旧值

**位置：** `apps/server/src/sync-apply.ts:96–122`，`applyOne → bookmark.create`。

**问题（已定向验证）：** `existing` 记录先读取，随后 `moveBookmark` 改变目录，但身份绑定与返回回执仍使用旧对象 `row.folder_id`。实际书签在 B，回执和浏览器目录身份却指向 A。

**整改要求：** 使用最终目标目录 ID 或重新读取移动后的记录，使书签落点、folder_identity 与回执一致。绑定前优先核验已有稳定目录身份，避免路径回退覆盖正确映射。

**验收：**
- [x] 库中 URL 位于 A，浏览器在已存在的 B 中新增同 URL 节点；回执、实际 folder_id、B 的 folder_identity 均指向 B。
- [x] 后续改名或删除 B 不得作用到 A。
- [x] 请求重放不改变已经正确的目录身份。

### SYNC-R04：跨浏览器根移动未更新 root

**位置：** `apps/server/src/sync-apply.ts:219–245`；`apps/server/src/store.ts:190–209`，`moveFolder`。

**问题（已定向验证）：** 协议解析 `root`，但仓储只更新 `parent_id`。bar 根目录移到 other 根时两端 parent_id 都为 null，被当作 noop，接口返回成功但 root 仍为 bar。

**整改要求：**
- 将父目录与根归属纳入同一个移动操作和无变化判定。
- 明确子目录 root 的继承规则；若逐行存储，子树跨根移动时事务内一致更新。
- 变更事件、回执、扩展路径索引都使用更新后的根归属。

**验收：**
- [x] bar → other → bar，目录 ID 和浏览器节点 ID 保持不变，root 正确。
- [x] 带嵌套目录与书签的子树跨根移动，两侧不残留旧壳、不新建重复目录。
- [x] 两根下已有同名目录时，移动仍按身份作用于正确目录。

### SYNC-R05：修订缓存未随成功回执更新，连续编辑自冲突

**位置：** `apps/extension/src/lib/sync.ts:1060–1104、1147–1176`；`apps/server/src/sync-apply.ts:133–159`。

**问题：** 扩展从 pull 更新修订缓存，但自身写入被防回环过滤，成功回执不返回新修订号。缓存 N 的第一次编辑成功后服务端变 N+1，第二次编辑仍带 N，触发冲突并回退用户修改。同一轮标题修改与移动也可能自冲突。反过来，若使用本轮 pull 更新后的版本提交开局旧意图，又会绕过原本应有的并发冲突检测。

**证据边界：** 临时库已验证旧版本连续提交会返回 ok/conflict；扩展缓存未更新为静态确认，完整浏览器交互需补回归。

**整改要求：**
- 成功回执返回最新实体与修订号，并更新已确认基线。
- baseRevision 固定绑定操作生成时的基线，不能临提交时换成最新 pull 版本。
- 同一实体复合编辑合并提交，或显式串行承接前一回执的新版本。
- 首次对齐与恢复从实际快照初始化修订缓存。

**验收：**
- [x] 无其他写入者时连续两次修改标题均成功，不回退。
- [x] 同一轮改标题并移目录，两项都生效。
- [x] 两端修改同一实体时按约定策略处理真实冲突，不因 pull 刷新版本而掩盖冲突。

### SYNC-R06：恢复未完整保留意图，失败回执可能被清除

**位置：** `apps/extension/src/lib/sync.ts:672–743、858–862`。

**问题：** recover 未完整保存目录新建、改名、搬家；书签移入未绑定新目录时会跳过移动；部分失败回执被忽略后继续重建基线。确认恢复期挂起删除时，调用 apply 后不检查逐条结果就清空队列。此外，快照返回的目录和书签未被消费，仅取水位与代际后再次分页查询，尚未落实文档描述的一致快照重建。

**整改要求：**
- 恢复前持久化完整本地操作计划及依赖（先目录、后书签）。
- 使用快照实体数据和水位建立同边界基线，明确新代际下旧身份的处理策略。
- 仅清除成功确认的操作，失败继续持久保留；恢复失败不得把未完成操作吞进新基线。
- 与 R01 的删除确认、R05 的版本策略及 R07 的 outbox 共用契约。

**验收：**
- [x] 离线新建空目录、改名、搬家、把书签移入新目录，再触发 reset，全部意图按策略保留。
- [x] 恢复期注入单条失败、SW 中断，重新恢复后能继续，不丢操作。
- [x] 确认挂起删除时让服务端返回 failed，队列仍保留该操作。
- [x] 快照读取后并发修改目录和书签，水位后事件能补齐最终状态。

### SYNC-R07：opId 未持久化，响应丢失后无法识别原操作

**位置：** `apps/extension/src/lib/sync.ts:1157–1176` 及 `applyMutations` 调用链。

**问题：** 普通 push 每轮新建 UUID，未发送前落盘。服务端已经提交但响应丢失时，下轮生成新 opId，服务端回执表无法识别为同一次操作。服务端支持幂等回执不等于客户端已获得端到端幂等保障。

**整改要求：**
- 增加持久化出站队列，发送前保存 opId、载荷、baseRevision 和依赖。
- 网络重试和 SW 重启复用原 opId；成功回执后才出队。
- 失败结果与永久拒绝结果分类处理，明确回执保留期之后的恢复方式。
- 目录操作同样纳入队列，避免只覆盖书签。

**验收：**
- [x] 服务端提交成功后丢弃响应，再重试，opId 不变，返回原回执，不重复副作用。
- [x] 响应丢失后另一端修改同一记录，再重放原操作，不覆盖后续修改。
- [x] 出站待处理期间重启 SW，操作及依赖仍完整存在。
