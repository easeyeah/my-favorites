# 容器开发与更新规范（D93）

> 生效范围：本仓库全部涉及代码改动的开发任务（人做的和 AI 代做的都一样）。
> 起因：2026-11-24 目录整理任务（D92）交付时只重建了管理台产物、没有重启服务端，开发实例成了「新界面 + 旧服务端」，用户实机点整理直接报 `HTTP 404`，而交付说明还写着「未部署」。
> 配套：提交与发版见 [提交与发版规范.md](提交与发版规范.md)；命令清单见根 `AGENTS.md`「常用命令」。

## 0. 一句话

**代码改完不等于功能交付；更新到正在运行的容器并验证生效，才算交付。**

## 1. 容器开发的四个事实（规范为什么这样定）

开发实例由 `docker/docker-compose.dev.yml` 编排，容器名 `my-favorites-server`，服务端一律跑在容器里（本机不起第二个服务端）。它的挂载方式决定了「改了什么要做什么」：

| 事实 | 后果 |
|---|---|
| `apps/server`、`packages` 是**源码 bind mount** 进容器的 | 改完文件容器里能看到，但不会自动生效 |
| 容器里是 `tsx watch`，可 **macOS Docker 的 bind mount 不传播文件变化事件**，watch 实际失效 | 服务端代码改完必须 `docker restart`，进程才会加载新代码 |
| 管理台产物目录 `apps/web/dist` 是**只读挂载**（`/web-dist`），`index.html` 每次请求都读 | 跑一次 `pnpm --filter @mf/web build`，正在运行的真实实例界面**立刻**换成新版——不需要、也不会等你决定部署 |
| `node_modules` 在**镜像里**（构建时 `pnpm install`），宿主的依赖目录不进容器 | 增删依赖后只重启不够，必须重建镜像 |

把第三、第四条放在一起看就是上次的坑：为了跑端到端测试做了一次 web 构建，真实实例的界面当场更新；服务端没重启，新界面调用的接口在旧进程里不存在。

## 2. 改了什么 → 必须做什么

| 改动位置 | 要做的事 | 生效方式 |
|---|---|---|
| `apps/web/src`（管理台） | `pnpm --filter @mf/web build` | 立即生效。**同一次交付若还动了服务端，必须接着重启**（见 §4） |
| `apps/server/src`、`packages/*/src` | `docker restart my-favorites-server` | 冷启动约 10–30 秒 |
| `package.json` / `pnpm-lock.yaml` / 新增 workspace 包 / `docker/Dockerfile` | `docker compose -f docker/docker-compose.dev.yml up -d --build server` | 重建镜像并替换容器；数据在命名卷 `server-data`，不受影响。判断方法：`docker inspect -f '{{.Created}}' "$(docker inspect -f '{{.Image}}' my-favorites-server)"` 看镜像构建时间是否早于依赖改动 |
| `docker/docker-compose.dev.yml` 的环境变量、端口、挂载 | `docker compose -f docker/docker-compose.dev.yml up -d server` | 配置变化时 compose 会重建容器 |
| `apps/extension`（扩展） | `pnpm --filter @mf/extension build`，再到浏览器扩展管理页**重新加载** | 扩展不跑在容器里，重启容器对它无效 |
| 仅文档、测试、`apps/e2e` | 无需更新容器 | 但跑端到端测试会用到 web 构建产物，见 §4 |
| 带数据库迁移（`apps/server/src/migrate.ts` 新增版本） | 随重启自动应用，见 §5 | 只前进，不回滚 |

拿不准改了哪几处时，按「全都做一遍」处理：web 构建 + 重启。多做没有副作用，少做就是半部署。

第二实例（`--profile multi-instance`，端口 3100，容器名 `my-favorites-server-secondary`）如果在跑，同样要更新；它是完全同形态的副本，改法相同，只是容器名不同。

## 3. 交付收尾的固定顺序

功能代码写完之后、向用户报告之前，按这个顺序做完：

```bash
pnpm -r typecheck                                   # 1. 类型检查（vite build 不做类型检查，必须先跑）
pnpm test                                           # 2. 单元 + 集成测试
pnpm --filter @mf/web build                         # 3. 管理台产物
docker restart my-favorites-server                  # 4. 服务端加载新代码（动了 server / packages 时）
pnpm --filter @mf/extension build                   # 5. 动了扩展时构建，并提醒用户在浏览器里重新加载
```

然后验证（§6），最后写交付说明（§7）。

端到端测试（`apps/e2e`）的夹具不用容器，直接用 Node 启动 `apps/server/dist/index.js` 并托管 `apps/web/dist`，所以跑之前要先构建这两样：

```bash
pnpm --filter @mf/server build                      # E2E 夹具用；容器开发模式不读它，重启容器时不需要
pnpm --filter @mf/web build                         # 这一步会立刻更新真实实例的界面
pnpm --filter @mf/e2e test
```

注意第二条：**跑端到端测试本身就可能把真实实例的界面更新掉**。所以 E2E 放在 web 构建之后、最终验证之前，且 E2E 通过后的那一版产物就是最终交付的版本；E2E 之后如果又改了代码，重新构建、重跑、再验证。

## 4. 禁止半部署

**构建与重启成对出现。** 以下都算违反：

- 动了服务端，只跑了 web 构建。
- 只为跑 E2E 做了 web 构建，之后没有重启服务端，也没有告诉用户「你的实例界面已经变了」。
- 构建完之后又改了代码，没有重新构建就交付。
- 交付说明写「未部署」「本地验证通过」，而实际上容器里的界面已经被更新。

做不到成对更新时（比如没有权限重启容器、或 Docker 不可用），必须**在交付说明的第一段**写清楚：当前实例处于什么状态、哪一半是新的、用户自己要执行哪条命令。

## 5. 数据库迁移

- 重启时如有待应用的迁移会自动执行，并在应用前对每个库做一份备份（`backups/pre-migrate-v<版本>-<时间>.db`，主库和每个用户库各一份）。
- 迁移只前进不回滚。**不手动改真实库的表结构，不为了「先看看」而在真实库上试跑迁移。**
- 重启会连带升级真实开发库，所以交付说明里必须如实写出（§7），不能只说「已重启」。
- 需要回退时用对应的 `pre-migrate` 备份恢复，不要写「反向迁移」。

## 6. 验证真的生效了

不要用「我跑过构建命令」当证据。至少做下面前三项：

```bash
# 1. 服务健康
curl -s -m 5 http://localhost:3000/healthz

# 2. 进程确实是新启动的（etime 应该是刚重启的时长，而不是几小时）
docker exec my-favorites-server sh -c 'ps -o etime,args | grep "src/index.ts" | grep -v grep'

# 3. 启动日志没有报错；有迁移时会逐库打印 migrated 行
docker logs --since 5m my-favorites-server 2>&1 | grep -iE 'error|unhandled|migrated|listening'

# 4. 界面产物与服务端实际下发的是同一份（两边文件名要一致）
ls apps/web/dist/assets/ | grep '^index-.*\.js$'
curl -s http://localhost:3000/ | grep -o 'assets/index-[^"]*\.js'
```

接口需要登录时，不为了验证而造令牌或用管理员密码登录真实实例；改为请用户点一次，或从日志里确认该请求的状态码不再是 404。新功能本身是否正确，由隔离环境（单测、夹具服务端的 E2E）证明，真实实例上只验证「部署到位、没有报错」。

## 7. 交付说明必须写清

每次涉及代码改动的交付，说明里要有这几项，缺一项视为没写完：

1. **真实实例现在的状态**：已更新 / 未更新 / 半更新（哪一半）。
2. **执行过的命令**：构建、重启、重建镜像、扩展构建。
3. **数据库**：有没有迁移；从几到几；多少个库；完整性检查结果。
4. **用户还要做的事**：比如在浏览器里重新加载扩展、刷新页面。
5. **没验证的**：哪些只在隔离环境验过、哪些完全没验（例如真实模型效果、镜像体积）。

## 8. 返工判定

以下任一情况，交付退回：

- 用户在真实实例上用到的是旧行为，而交付说明声称已完成。
- 界面是新的、接口是旧的（或反过来），出现 404 / 字段缺失一类错误。
- 重启了但没有检查迁移和完整性，或没有在说明里报告。
- 声称「未部署」，但容器里的产物或代码实际已经变了。
