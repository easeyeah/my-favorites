# 提交与发版规范（D90）

> 生效范围：本仓库全部提交。**可执行版本**在 `commitlint.config.js`（本地 `husky commit-msg` + CI 双层拦截），本文解释「为什么」与「怎么写才不返工」。
> 规范自 D90 起对新提交生效；历史提交不追溯改写（52 条存量已全量通过新规则校验）。

## 0. 一句话

**一个提交 = 一件能独立撤销的事 + 一句能进 CHANGELOG 的话 +（必要时）一条 changeset。**

## 1. 三层记录，别混用

| 层 | 落在哪 | 回答的问题 | 粒度 |
|---|---|---|---|
| commit | git 历史 | **怎么改的**（改了哪些文件、实现取舍） | 最细，一个 PR 可含多条 |
| 决策记录 | `docs/决策记录.md` | **为什么这么定**（产品/架构判断） | 最粗，一条管一个方向 |
| changeset → CHANGELOG | `.changeset/*.md` → 各包 `CHANGELOG.md` | **用户能感知到什么变化、这次发哪个版本** | 中间，一句话一条 |

三层互补：commit 里不要复述决策全文（给 D 编号即可），决策记录里不要写实现细节，changeset 里不要写内部重构。

## 2. 标题：`type(scope): 摘要`

### 2.1 type（受控 11 种）

| type | 用于 | 与 changeset 的关系 |
|---|---|---|
| `feat` | 用户可感知的新能力 | 必须附 changeset（`minor`） |
| `fix` | 用户可感知的缺陷修复 | 必须附 changeset（`patch`） |
| `perf` | 有体感的性能优化 | `patch` |
| `refactor` | 不改行为的内部重构 | 一般不附；对使用方有影响时 `patch` |
| `docs` | 文档、注释、AGENTS.md | 不附 |
| `test` | 测试与夹具 | 不附 |
| `build` | 构建、打包、依赖 | 依赖安全修复时 `patch` |
| `ci` | CI/门禁/脚本 | 不附 |
| `chore` | 杂务（发版、清理、配置） | 发版提交不附（`[skip changeset]`） |
| `style` | 纯格式（无逻辑变化） | 不附 |
| `revert` | 回滚既有提交 | 视被回滚内容而定 |

判断口径：**用户能不能感知**。能 → `feat`/`fix`；不能 → 其余类型。拿不准时选「用户视角最接近的那个」，并在正文写清边界。

### 2.2 scope（受控 12 个，可省略）

| scope | 对应范围 |
|---|---|
| `server` | `apps/server` |
| `extension` | `apps/extension`（含 `entrypoints/`） |
| `web` | `apps/web` |
| `shared` | `packages/shared` |
| `ai` | `packages/ai` |
| `e2e` | `apps/e2e` |
| `docs` | `docs/`、`AGENTS.md`、根 `README.md` |
| `ci` | `.github/`、`scripts/` |
| `docker` | `docker/` |
| `deps` | 依赖升级（`package.json` / `pnpm-lock.yaml`） |
| `release` | 版本号、CHANGELOG、tag |
| `repo` | 跨模块杂项（`.gitignore`、`.editorconfig` 等） |

规则：能落到具体包就写包名；跨端改动写「主改的那一端」，其余在正文列出；纯流程提交（如 `chore: 更新 .gitignore`）可省略 scope。

### 2.3 摘要五条

1. **写结果与动机，不写文件名**——「修收纳盒空态看不到历史」优于「改 library.tsx」。
2. **≤72 字符**（含 `type(scope): ` 前缀，中文按字符计）——细节搬进正文。
3. **不加句号**（中英文都不要）。
4. **D 编号放摘要末尾**（`…（D82）`）或正文首行，不要顶在开头挤占信息位。
5. **中文优先，技术名词保留原文**（SSE / MCP / SQLite / favicon）。

### 2.4 正反例（均为本仓库真实提交风格）

```text
✅ fix: 收纳盒空态下归位历史不可见——历史区提升至列表容器外
✅ feat(web): 管理台书签实时更新——三层守卫与恢复闭环（D82）
✅ fix(extension): 新标签页 401/403/连接故障区分提示
❌ update: 一些修改                       （type 不在集合、摘要无信息）
❌ fix(后端): 修 bug                      （scope 不在集合、摘要无信息）
❌ feat: 改 library.tsx 的 if 分支         （描述实现而非结果）
```

## 3. 正文：三段式（门禁不强制，评审按此看）

```text
<问题/动机：用户看到什么现象、为什么现在做>

<关键实现：只写「读代码的人必须先知道」的 2–5 条，不复述 diff>

<验证：跑了什么、结果如何；已知限制与后续>
```

- 好的样子：`0bd795b feat: M-A 可信基础——隐私链路/身份映射/整理事务/安全默认值`，正文按 ① 隐私 ② 身份映射 ③ 事务内核分条，每条一句结论。
- 反例：`9fc005b feat: D43–D63 切片合流`——21 个功能一个提交，无法单独 revert、无法对应 changeset、评审只能看总量。规范后禁止此类合流。

## 4. 页脚：追溯与破坏性

```text
Refs: D82, docs/功能设计文档/管理台书签实时更新.md
BREAKING CHANGE: 同步快照新增 generation 字段，未升级的扩展会被判定 reset_required
```

必须写 `BREAKING CHANGE:` 的场景：

- DB 迁移（本仓库迁移只前进、不回滚）；
- API 响应/鉴权方式不兼容；
- 环境变量更名或删除（如 `DEPLOY_MODE` 退役）；
- 同步协议/扩展权限变更，要求用户重装或重登；
- 导出格式变化（Netscape/JSON 导入不兼容）。

## 5. 粒度：一个提交一件事

- 判据：**能独立 revert 的才是一个提交单位**。
- 一个功能跨三端时，按端拆 2–3 条提交（引用同一 D 编号），不要合成一条巨型提交。
- 禁止把「功能 + 全仓格式化 + 依赖升级 + 文档」混在一起——diff 无法评审，也会污染 `git blame`。
- 提交前至少跑 `pnpm typecheck`；动服务端的跑 `pnpm --filter @mf/server test`（CI 会跑全量）。
- 功能提交随附 `pnpm changeset`（门禁见 §7）。

## 6. 发版提交与 tag

- 发版提交固定为 `chore(release): 0.2.0`，由 `pnpm run version` 产出，提交信息带 `[skip changeset]`。
- 发版提交**只包含**版本文件与 CHANGELOG，不混功能改动。
- tag 格式 `<app>-vX.Y.Z`（CI 监听 `server-v*` / `extension-v*` / `web-v*`）；`shared`/`ai` 随应用发布，不单独打 tag。

## 7. 门禁与豁免

| 层 | 时机 | 检查内容 | 失败后果 |
|---|---|---|---|
| 本地 husky `commit-msg` | `git commit` | commitlint（本文 §2 全部规则） | 提交被拒 |
| CI（PR） | 每个 PR | `merge-base origin/<base>..HEAD` 全量 + changeset 门禁 | PR 红 |
| CI（push main / tag） | 每次推送 | `before..after` 全量（多提交一并校验） | 流水线红 |

豁免：

- 发版 PR 用提交信息 `[skip changeset]`；
- `git commit --no-verify` 只在本地临时 WIP 用，推上去仍会被 CI 拦；
- 历史提交不追溯改写（改写历史会破坏 CHANGELOG 里的 commit 引用）。

## 8. 常见问题

- **修 bug 顺带重构，用 `fix` 还是 `refactor`？** 拆两条；实在拆不开用 `fix`（用户感知优先），正文写明重构范围。
- **只改文档要不要 changeset？** 不要，门禁对纯文档放行。
- **忘了写 scope 会失败吗？** 不会（scope 可选）；但写了必须在 §2.2 集合内，代码改动建议写。
- **标题超过 72 字符怎么办？** 把细节搬进正文，标题只留结论。
- **多个包一起改，scope 写哪个？** 写主改端；其余在正文列「影响面：server / shared」。
