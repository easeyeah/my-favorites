## 1. 产品定位

### 1.1 一句话定位

**当你收藏了几百个网址却再也没打开过它们时，my-favorites 用 AI 把这堆书签变成一个能天天用的个人导航主页。**

### 1.2 唯一核心任务（JTBD）

用户雇佣本产品只做一件事：**"把我失控的书签堆，变成我有掌控感的、每天使用的入口。"**

由此推导出产品各部分的角色：

| 部分 | 角色 | 定性 |
|---|---|---|
| AI 一键整理 + 内容缓存 | **楔子**（用户为什么选我们而不是别的书签工具） | 核心 |
| 导航站生成 | **产出物**（整理结果的可视化落地，也是日活阵地） | 核心 |
| 一键收藏/收纳盒自动归位 | **留存钩子**（让 AI 介入每一次书签流入） | 核心 |
| 定期死链/查重维护 | **回访理由** + 信任构建 | P1 |
| 多端同步、私密书签、模板商城 | 服务于闭环的配套 | P2，坚决后置 |

**判断标准**：任何新功能提案，必须能回答"它让整理更准、让导航站更有用、或让用户更常回来"三者之一，否则不进路线图。

### 1.3 为什么不是 Raindrop.io（竞争壁垒声明）

Raindrop.io 是最强书签管理器（集合、建议、死链检测、永久快照），但它是**管理工具**：产出是"一个更好的书签库"，用户依然要自己动手整理。我们：

1. 产出物不同——我们落地为**每天实际使用的导航主页**（占据新标签页），Raindrop 的产出没人每天看；
2. 交互范式不同——我们以**一键 AI + 内容理解**完成整理（功能点即跑、直接生效、随时撤销），Raindrop 是手动为主+被动建议；
3. 数据资产复利——缓存的内容摘要/快照随时间越积越多，整理偏好持续学习用户习惯，**用得越久越准**，形成切换成本。

## 2. 竞品分析

### 2.1 第一梯队（直接竞对）

**Raindrop.io**（百万级用户，成熟商业产品）
- 强项：全平台、集合/嵌套标签、死链检测（付费）、永久副本（付费）、公开集合、AI 建议分类

### 3.1 核心画像（当前优先服务前两个）


**Aha 定义：导入后 60 秒内看到整理结果和导航站**（两阶段整理，见 §5.2）。注册和 BYOK 都必须放在 Aha 之后——这是激活率的生命线。

### 5.1 内容缓存引擎 —— 双通道设计

| 通道 | 触发 | 覆盖 | 说明 |
|---|---|---|---|
| **A. 扩展端就地捕获（主）** | 用户收藏瞬间 / 收纳盒书签被打开时 | 登录墙✅ 内网✅ 反爬✅ | 扩展在当前标签页提取正文（Readability），随书签提交；质量最高、零额外抓取 |
| B. 服务端补漏抓取 | 存量导入 / 周期刷新 | 公开页 | 队列限速、robots 尊重；失败降级为"仅元数据" |

缓存分级：L1 摘要+标签（AI）→ L2 正文文本 → L3 完整快照（一键快照功能，详见 §6.2；云端默认只存 L1+L2，L3 按用户主动触发与配额提供，自建端不限）。

### 5.2 两阶段整理（激活提速的关键设计）

```
阶段1「快整理」(<15s)：不抓网页，只用已有信号
  → 目录结构语义 + URL 域名模式 + 标题关键词 + 添加时间
  → 规则引擎产出整理结果并直接应用（D27：无确认流）+ 导航站生成
阶段2「内容级精修」(后台)：
  → 抓正文、生成摘要、embedding 聚类，完成后通知「已精修 N 条」
```

阶段1 是确定性本地规则引擎（零 LLM 成本、零延迟）；阶段2 是二次惊喜而非等待门槛——变更经通知呈现，可一句话修正或整体撤销（D27/D28）。

### 5.3 站点化分析与导航投影（D30/D31 · 新增）

**导航站 = 站点投影**：只收「网站首页/主页面」，文章/详情类书签不占导航位；资料类站点（文档/wiki/教程首页）默认也不入导航——资料是"去读的"，不是"每天点进去的"。

```
书签库（全量 · D16 主数据）
  ├─ ① 规则信号：URL 路径深度 / 文章路径模式 / 域名映射表分类
  ├─ ② AI 信号：L1 摘要判断三类——官网·工具 / 资料站 / 内容页
  └─ ③ 同站归并：同域内容页 → 一个站点卡（首页直达）；
        只收藏过文章的域名 → 域名根升级为站点卡（默认开启可撤销）
  → ④ 个性化排序：应用内点击频次（D29 数据源）+ 分组权重 + 最近使用
  → ⑤ 渲染：新标签页 / 公开导航站
```

- 分析是**投影**，不改书签数据，可随时重建（D16：应用库是主数据）
- 书签库新增「🛠 官网·工具 / 📚 资料站 / 📄 内容页」筛选
- **自定义卡片**是唯一允许任意 URL 的手动例外；高频深链只提示引导建卡，不自动放行
- 管理台提供「包含资料站」开关（默认关，开启后以「📚 资料」分组沉底）
- 公开导航站同样只展示站点级入口（红线④天然覆盖；公开范围仍受 D23 显式发布集合约束）

### 6.1 F1.5 自动收纳（懒人模式）详细设计

**概念**：在书签栏创建一个特殊文件夹「📥 收纳盒」（Stash）。用户把任何书签丢进去（或收藏时直接落入），AI 自动分类并归位到正确目录。源自 GTD 的收集盒（Stash）思想——**降低使用门槛到"随手一丢"**。

**书签进入收纳盒的三种方式**：
1. 浏览器原生拖拽/移动到该文件夹
2. 右键菜单"收藏到收纳盒"（不想思考归哪类的场景）
3. 一键收藏的默认目的地可设为收纳盒（全懒模式）

**入口的技术边界（已确认）**：浏览器原生文件夹下拉无法被扩展定制、文件夹无角标 API——文件夹只做**物理投递口**（原生下拉自然列出未处理项）；管理界面入口 = **扩展工具栏图标（角标 = 待处理数，chrome.action.setBadgeText）→ popup 顶部标签「收纳盒」**（窄容器统一顶部标签页导航）；书签右键菜单可加「立即归位 / 查看建议」（contextMenus 支持 bookmark 上下文）。

**触发与流水线**：
- 扩展监听收纳盒新增（bookmarks API 事件），逐条触发整理流水线：
  `隐私校验 → 域名规则即时初判 → 内容捕获（通道A优先）→ AI 内容级分类 → 自动归位`
- 支持定时批量清扫（每小时/每天，自建端与云端均可调度）——覆盖离线期间堆积的书签
- **镜像模式（D20 正式实现）**：归位 = 同步移动浏览器书签节点（持久待执行队列，不与数据库事务耦合）

**两种模式（D28：全自动为默认）**：
- **全自动模式（默认）**：静默直接归位 + 轻提示一闪而过（可撤销）；置信度低于阈值（建议 80% 起步，按回滚率调整）时留在收纳盒不强移
- 确认模式：降为设置项，给不放心的人（归位后轻量提示，可一键撤销）

**歧义与安全规则**：
- 分类置信度不足（多类目相近）时**留在收纳盒不强行移动**，积攒后（≥3 条）在 popup 收纳盒视图集中询问（D42：此前在侧栏聊天中询问，侧栏下线后并入收纳盒）——收纳盒永不丢书签
- 用户手动从收纳盒移出的书签记为"用户已确认"，AI 永不再动它
- 移动动作全部进版本快照（与 F3.5 回滚体系共用）；隐私域名条目仅存 URL，只人工归位（可按域名记本地规则）

**与 F1.4 的关系**：F1.4 是主动收藏路径的即时建议；F1.5 是被动堆积路径的自动归位。两者共用同一套分类引擎与缓存，互补覆盖。

### F2 内容缓存引擎

- **F2.2 [P0]** 服务端补漏抓取队列：限速、重试、robots、失败标记；favicon 优先 Google s2 / DuckDuckGo 图标接口兜底（导航站图标覆盖率决定首屏观感）

### 6.2 F2.4 一键快照（防失效回看）详细设计

**动机**：链接失效（link rot）是书签工具最大的长期痛点——收藏的页面几个月后可能下线、改版或被付费墙挡住。快照让"收藏"真正等于"留住"。Raindrop 的"永久副本"（付费）与 HamHome 的本地快照均验证了该价值；本产品将其升级为一等公民交互，并与死链检测形成"失效 → 有出路"的闭环。

**触发方式（四条）**：
1. **收藏瞬间**：一键收藏时可选"同时保存快照"（全局开关可配置）；扩展端就地生成，零额外抓取
2. **手动一键**：书签详情页 / 扩展右键菜单 / 导航站卡片上的「快照」按钮——对任何已收藏书签随时补拍
3. **批量快照**：整目录批量走管理台多选批量操作或服务端/自建端队列（原「聊天指令」入口随 D42 下线；单条快照仍在收藏时开关控制）
4. **失效联动**：死链检测判定失效且无快照时，在周报与书签详情中提示"该页已失效且无快照"（有快照则直接给"查看快照"入口）

**技术形态**：
- **扩展端（主通道）**：`chrome.pageCapture.captureMHTML` 对当前标签页一键生成 **MHTML 单文件**——浏览器原生保真（含图片/样式/排版），Edge/Chrome 可直接渲染，实现成本极低
- **服务端/自建端（补漏）**：SingleFile 式资源内联的净化 HTML（图片转 dataURL 或代理缓存），用于批量快照与存量补拍
- **查看**：扩展内置快照查看器（新标签打开）；导航站上失效书签自动显示「快照可用」标识，一键回看

**存储策略**：

| 形态 | 存储 | 限制 |
|---|---|---|
| 本地模式 | 扩展 IndexedDB/OPFS | 随设备容量 |
| 云端 Free | 对象存储 | 小配额（如 200MB / 100 份） |
| 云端 Pro | 对象存储 | 2GB，保留最近 N 个版本 |
| 自建 | 本地磁盘 | 不限，含历史版本 |

**安全与边界**：私密书签快照加密存储；隐私域名清单内不做快照；公开导航站**永不展示快照内容**，仅显示"有快照"状态（版权红线，与 §9 一致）。

**优先级**：手动一键 + 收藏时快照为 **P0**（扩展端就地生成 + 本地/试用额度存储）；批量与服务端补漏次优先；失效联动提示随死链检测交付。

### F3 AI 整理（功能点 · 核心；D42 起聊天对话下线）
- **F3.1 [P0]** 整理入口 = **管理台功能点行式列表**（点了就跑，结果/过程弹窗化；规范第 7 条）——扩展侧栏聊天整理已于 D42 整体删除（真用 AI 者用外部工具；对话入口招支持负担、且有被当通用 AI 网关接入的风险），扩展端不再暴露任何自由对话面

## 7. 商业模式与成本

### 7.1 收费结构

| 层 | 定价 | 内容 |
|---|---|---|
| Free | ¥0 | 收藏/收纳盒归位/整理/导航站基础能力；**AI 走 BYOK 完全免费**；云端 L1+L2 缓存配额 + 快照小配额（本地模式快照不限）；免费额度采用**行为配额**（如每月 3 次全库整理）而非容量配额——容量限制会劝退重度用户，而重度用户是付费转化主力 |
| Pro（订阅） | 年费 ¥99 早鸟价起（常规 ¥15–25/月 或 ¥128/年） | 无 BYOK 也能用 AI；快照配额；每周自动维护；无限版本历史；公开导航站去水印 |
| 自建 | **完全开源免费**（决策 D12） | 全功能自持；开源版与云端 Pro 的差异仅在于托管与配额、不做功能阉割，商业价值由云端 SaaS 承载 |

**原则：BYOK 用户永远有完全免费的完整体验。**

### 7.2 成本红线

- 云端默认只存 L1+L2，不存 L3 快照；Pro 快照配额上限（如 2GB）；正文截断 20KB/条
- 大规模整理走 F3.9 聚类策略；收藏即时归位走域名缓存（F1.4），AI 成本趋近于零
- 服务端抓取队列限速；死链分层探测降低请求量
