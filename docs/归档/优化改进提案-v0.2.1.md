# my-favorites 可落地优化改进提案（基于 v0.2）

> 定位：执行层补充，不改变 v0.2 的定位与路线图框架。
> 每条优化给出：**做什么 / 为什么可行 / 怎么落地**。
> 按主题分 7 节，末尾附 30/60/90 天行动清单。

---

## 一、激活提速：两阶段整理（本次最重要的单条优化）

**问题**：v0.2 的 Aha 流程依赖"AI 后台抓取+整理 3 分钟"。真实场景里千级书签的抓取+整理可能要 5–15 分钟，用户等不到 Aha 就流失了。

**优化**：整理拆成两个阶段，先给结果、后台精修：

```
阶段1「秒级快整理」(<15s)：不抓网页，只用已有信号
  → 目录结构语义、URL 域名模式（github.com→开发、bilibili.com→视频）、
    标题关键词、添加时间
  → 用规则+轻量分类模型立即产出第一版整理结果和导航站
阶段2「内容级精修」(后台 5–15min)：
  → 抓正文、生成摘要、embedding 聚类，完成后提示
    "AI 已根据网页实际内容精修了 43 个书签的分类，查看变更"
```

**为什么可行**：域名→类目的映射表冷启动只需几十条常见站点，规则版准确率即可达 60–70%；阶段2 变成二次惊喜而非门槛。
**怎么落地**：阶段1 做成确定性的本地规则引擎（无 LLM 成本、无延迟）；阶段2 的 diff 复用 F3.4 的确认流。**Aha 定义相应修订为"导入后 60 秒内看到整理结果和导航站"。**

## 二、增长获客：三个零成本传播杠杆

1. **「书签体检报告」作为获客钩子**
   - 做什么：安装扩展第一屏先免费跑一次"书签体检"：死链 N 条、重复 N 组、2000+ 天未访问 N 条、零碎目录 N 个，生成一张可分享的报告卡片。
   - 为什么可行：体检不需要用户做任何配置，是天然的价值展示；"你的书签 37% 是死链"这种结论自带传播性；分享卡片带产品标识回流。
   - 怎么落地：死链检测 M2 才有云端任务，但**单次体检可以先做**（导入时顺带跑一轮 HEAD 探测），报告页脚"用 AI 一键整理 →"直接导向 Aha 流程。获客与激活串成一条链。

2. **公开导航站页脚水印**
   - 做什么：所有分享出去的导航站页脚默认带"⚡ 由 my-favorites 生成"（Pro 可关）。
   - 为什么可行：参考竞品的"书签变主页"形态，导航站天然会被分享给同事朋友；这是产品形态自带的免费分发渠道，每一份公开导航站都是一个落地页。
   - 怎么落地：模板加一行链接即可，M1 就做，成本≈0。

3. **渠道打法按人群分层投放**
   - 极客/NAS 圈：V2EX、少数派、恩兔社区、Unraid/群晖论坛——先发"自建服务端"技术贴攒口碑（M3 前用 lite 镜像预热）。
   - 效率工具圈：即刻、Product Hunt、B 站效率工具测评人——主推"AI 整理 + 导航站"演示视频（Aha 流程录屏即素材）。
   - 商店 ASO：标题堆核心关键词（书签/AI/导航/起始页），首图用"整理前后对比"截图。

## 三、交互落地优化：把"确认负担"降到最低

1. **diff 预览的效率设计**：按目录分组折叠展示变更；键盘 J/K 逐条浏览、Enter 确认、空格切换"接受/保留"；每条 diff 可单独否决。"整包确认"太粗，逐条手点太累，分组+快捷键是千级书签唯一可用的粒度。
2. **"不满意→修正"对话闭环**：diff 页顶部放"哪里不满意？"输入框，用户一句"游戏类拆开，单机和网游分开"直接变成下一轮整理指令——把否决成本变成产品交互，而不是让用户流失。
3. **整理失败的兜底体验**：抓取失败（反爬/登录墙）的书签明确标注"未读取内容，仅按标题分类"，并给出"在浏览器中打开过该页后收藏可补全内容"的引导——把局限变成用户教育。
4. **删除类操作永不自动执行**：AI 只做"建议删除清单"，用户勾选确认——这是数据信任的底线（与 v0.2 D3 一致，落到交互细节）。

## 四、技术与成本落地优化

1. **收藏时"即时归位"不用 LLM（成本+延迟双杀）**：维护一张"域名→分类"映射缓存表；新收藏先查表命中则 <50ms 零成本返回，未命中才异步调 LLM 并写回缓存。高频用户 90%+ 收藏走缓存，AI 成本趋近于零。
2. **死链检测分层探测（省 80% 请求成本）**：DNS 解析失败→直接判死；HEAD 请求 2xx/3xx→判活；4xx/5xx/超时才升级 GET 复验。多数死链在第一层就出局。
3. **favicon 兜底不用抓取**：优先 Google s2 / DuckDuckGo 图标接口，失败才抓页面——导航站图标覆盖率是"看起来专业"的第一观感，这条决定首图质量。
4. **LLM 供应商本土化（面向中文市场的硬前提）**：三个参考竞品全是中文产品，目标用户在国内。BYOK 必须原生支持 DeepSeek / 通义 / 智谱 / Kimi 等 OpenAI 兼容端点，不能只有 OpenAI/Anthropic——否则 BYOK 对国内用户形同虚设。官方云端 token 采购同样以国产模型为主（成本约为 GPT 级的 1/10）。
5. **自建镜像资源约束**：NAS 用户机器多为低功耗设备，自建镜像设计上限 内存 <300MB、含 SQLite 单文件存储、支持 ARM64（群晖多为 ARM/低端 x86）。镜像体积和内存是 NAS 社区口碑的硬指标。
6. **MV3 扩展端落地要点**：就地捕获走 `activeTab` 权限（点击收藏瞬间注入，无需全站 host permission，审核压力小）；新标签页用 `chrome_url_overrides`；service worker 生命周期短，长任务（体检/整理进度）全部放在服务端或本地模式下的 offscreen document。

## 五、商业化落地优化

1. **定价锚点参考**：Raindrop Pro $28/年、Cubox ¥198/年——v0.2 的 ¥128–258/年 区间成立，建议首发年费 ¥99 早鸟价拉首批口碑用户。
2. **自建端"买断"具体化**：License key 激活制（核心开源、Pro 功能 license 解锁），客单价 ¥68–99 买断——NAS 用户对订阅极度排斥，买断制是这个人群的唯一可行形态；license 校验放本地，不做在线强制（尊重自托管精神，否则社区反噬）。
3. **免费额度用"行为配额"而非"容量配额"起步**：先不限书签条数（容量限制劝退重度用户=最有价值用户），限制的是云端 AI 整理次数（如每月 3 次全库整理）——重度用户恰好是付费转化主力。

## 六、数据与实验（最小埋点集）

上线即埋、不多不少 8 个事件：
`install → import_completed(条数) → stage1_result_viewed → diff_accepted(采纳率) → nav_generated → ntp_enabled → bookmark_saved(含缓存命中) → weekly_report_clicked`
配套三个 A/B 起手实验：① 体检报告前置 vs 直接导入；② Aha 时机 60s 快整理 vs 等待全量；③ diff 默认全选 vs 全不选（确认成本与掌控感权衡）。

## 七、合规前置清单（避免返工）

- 隐私政策与数据说明页**提审前就绪**（Edge/Chrome 高敏权限必查）；模板可直接参考 HamHome 的"数据不出本地"披露写法。
- 国内若自建云端：AI 整理不存用户正文原文超过配置期限；公开导航站准备敏感词过滤与举报入口再开分享。
- 商店素材：截图突出"一键导入→整理→导航站"三步，避免出现"读取你的所有书签数据"类吓人措辞的场景。
