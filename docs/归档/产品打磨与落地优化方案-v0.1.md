# my-favorites 产品打磨与落地优化方案（v0.1）

> 日期：2026-11-17。
> 依据：`功能文档-v0.3.md`、`技术方案设计-v0.1.md`、`开发报告-M1.md`及当前核心代码静态检查。
> 适用对象：独立开发者 + AI 辅助开发。
> 定位：可执行优化提案，不代表本文列出的能力已经完成；本轮仅新增方案文档，不修改代码。
> 权威边界：功能文档 v0.3 仍是当前产品基线。本文涉及定位、优先级和指标的调整均为建议；实施时同步升级产品/技术文档，决策记录仅追加，不覆盖旧决策。

## 1. 总体结论与开发路线

**继续做，但从“功能覆盖”转向“核心体验、可靠性和可交付性”。**

本项目采用以下独立开发路线，而不是把完整市场调研作为开发前置：

```text
开发者真实需求与判断
  → AI 辅助深入打磨
  → 自用完成真实任务
  → 发布可独立体验的版本
  → 观察使用与接收反馈
  → 小步修正产品假设
```

这条路线是合理的。AI 可以降低实现、测试和迭代成本，让独立开发者先做出有完成度的产品，再获得现实反馈。它的风险不是“没有先做足调研”，而是缺少明确的完成边界，以致持续开发却始终没有交付和观察。

因此约定：

1. **不要求**先完成问卷、系统访谈、竞品全量研究或统计显著的 A/B 实验。
2. **不把**功能数量、测试数量、AI 给出的评价当作产品价值证明。
3. **先打磨一个有明确边界的优秀版本**，不等待所有部署形态和远期功能齐全。
4. **先验证可用，再观察是否有用**：阻断任务的问题直接修；偏好和方向问题通过实际使用逐渐判断。
5. 按验收门槛推进，不承诺固定工期；每轮只推进一个主要目标。

## 2. 本轮要兑现的产品承诺

### 2.1 对外表达建议

主表达建议：**收藏时不用纠结，找回时不用重搜。**

辅助表达：AI 帮你整理书签，生成个人导航，并保存重要页面。

这不是取消导航主页，而是把它从“所有用户必须接受的最终形态”调整为一个高频入口。用户也可以通过侧栏、管理台搜索获得价值，不强迫更换新标签页。

### 2.2 先服务的使用情境

优先围绕开发者本人能够持续复现的工作流打磨：

- 反复使用工具、文档和项目入口；
- 收藏技术文章、案例和解决方案，之后需要找回；
- 不想每次收藏都决定目录；
- 希望重要网页失效后仍可回看；
- 希望数据可导出、操作可撤销。

开发者自用是起点，不等于所有人的需求。没有自用证据的新需求先记入候选，不因 AI 能快速实现就自动进入当前版本。

### 2.3 五条必须兑现的承诺

| 承诺 | 用户能够观察到的结果 |
|---|---|
| 放得进 | 收藏有明确成功状态；失败不假装成功，重复有清楚解释 |
| 找得到 | 已捕获内容可搜索，能够打开正确原页或已有快照 |
| 不乱动 | 批量整理先预览；自动移动可解释、可撤销；手工归类优先 |
| 不泄露 | 隐私内容在设备端就被阻止捕获/上传，而非只在服务端丢弃 |
| 带得走 | 导出、恢复包含承诺的数据；限制和缺失项明确展示 |

## 3. 控制范围：一个可靠版本，而不是三套产品同时完善

### 3.1 建议的交付顺序

**首个打磨对象：扩展 + 单用户 Docker 自建端。** 这是当前实现基础最完整的路径，适合先自用和小范围发布。

- 继续使用已确定的 TS、WXT、Hono、SQLite 等技术方向，不重写技术栈。
- 先为扩展补导航缓存和待发送操作，不把它宣传为完整纯本地模式。
- 完整本地模式保留为后续独立交付项。
- 官方云服务另设上线门槛，不将“已有接口/配置预留”表述为“云端已就绪”。

代价：第一批反馈会偏向技术用户。接受这个局限；它不证明大众用户愿意配置 Docker 或 BYOK。若反馈反复指向安装门槛，再在完整本地模式与托管体验中选择一个主方向，不同时铺开。

### 3.2 本轮暂缓

- 新模板、模板 DSL、商城、公开广场；
- 增加大量模型供应商，而不是修好已有连接路径；
- 复杂多 Agent 整理、通用知识库聊天；
- 为未来规模提前拆微服务、引入 Redis、重写数据库层；
- 在使用样本不足时建设复杂分析平台或做多组 A/B；
- 未经权限、恢复验证的完整双向浏览器书签同步。

已有功能不因暂缓而随意删除；不成熟能力可标记实验性或默认关闭。

## 4. 当前基线与需要诚实披露的差距

以下来自静态检查和仓库报告，实施前应针对对应链路复现，不能把推断当作已完成的运行审计。

| 项目 | 当前证据 | 本轮处理 |
|---|---|---|
| 纯本地模式 | 开发报告 §4 明确未实现 | 不对外承诺无服务端完整可用 |
| 云端能力 | `db.ts` 为单用户 SQLite 模型，未包含核心租户归属字段 | 明确云端是后续工程，不只是部署运营 |
| 隐私边界 | `background.ts` 先读取正文、上传，`pipeline.ts` 再校验 | 在捕获前和上传前增加设备端策略 |
| 收件箱联动 | 扩展提交浏览器书签 ID，服务端按库内 ID 查询 | 复现后建立显式映射和可恢复流程 |
| 内容精修 | `organize.ts` 域名规则命中后跳过后续模型分类 | 域名作为粗判，不锁死最终归类 |
| 数据恢复 | 整理逐项执行；缓存表存在级联删除 | 事务、冲突检查、关联数据恢复必须补齐 |
| 新标签页 | `newtab/main.tsx` 依赖实时 `/nav/data` | 本地缓存先显示，后台更新 |
| 私密书签 | 当前显示控制不等于二次验证或客户端加密 | 不以“加密保险箱”宣传；成熟前标实验性 |

## 5. 执行包 A：先守住数据、隐私和一致性

### A1. 完整隐私策略链路【发布阻断】

**做什么**：在共享包提供统一策略判定，扩展和服务端都调用，但不只依赖分类函数间接保证安全。

- 策略返回可解释的允许/禁止结果，分别控制读取正文、上传正文、调用模型、服务端抓取、快照。
- 扩展捕获前读取本地隐私规则；用户自定义规则按修订版本同步到设备。
- 策略未加载或失效时，敏感内容路径保守降级为仅元数据，不先上传后补校验。
- 服务端对正文、摘要、向量、快照等入口再次校验；不得信任客户端声明。
- 对服务端抓取单独定义网络访问策略：云端禁止私网/回环/链路本地等目标；自建内网抓取显式开启或配置允许范围；重定向后重新检查目标。
- 已缓存内容在隐私规则变化后如何清理，必须向用户说明；已发送给第三方的数据不能承诺追回。

**验收**：隐私测试域的页面读取函数未被调用；正文/快照网络请求未发出；服务端直接调用同样被拒绝；日志、埋点无正文、完整 URL 和密钥。

### A2. 明确主数据与收件箱映射【发布阻断】

**决策建议**：应用库为主数据，浏览器书签作为导入源和可选镜像；当前不承诺完整双向同步。

- 使用持久设备 ID，不用所有设备共享的固定字符串代替。
- 建立 `device_id + browser_bookmark_id ↔ app_bookmark_id` 映射；不能按标题或 URL 代替稳定身份。
- 浏览器收件箱事件先映射/幂等入库，再提交应用书签 ID。
- 保存待处理操作；成功后确认，失败可重试；SW 重启后可以恢复。
- 当前既然承诺浏览器内自动归位，就必须同步移动浏览器节点，并提供可理解的两端撤销；否则明确降级为“仅应用库归类”，不能只显示已归位。
- 外部浏览器状态不能与数据库共用事务，使用持久待执行记录与完成状态；重试不得重复移动或形成监听循环。
- 全面扫描用于恢复漏掉的事件，不只依赖内存防抖计时器。

**验收**：原生拖入、扩展收藏、重复事件、服务端离线、SW 重启、用户手动移出六种场景均有确定结果；不丢数据，不误处理别的书签。

### A3. 事务、冲突与真正可恢复【发布阻断】

- 提案记录稳定实体 ID、原始状态和修订版本，不按目录名称定位目标。
- 在事务中完成应用校验、数据变更、版本记录、变更日志。
- 提案产生后用户已手改的项目提示冲突，不静默覆盖。
- 回滚生成新的历史记录；对后来又被修改的项目跳过或要求确认。
- 合并优先软归档，保留来源书签、正文缓存、快照关联和隐私属性；不通过简单删除完成合并。
- 增加有序、带版本号的数据库迁移；迁移前用 SQLite 支持的备份机制，不能在 WAL 活跃时简单复制主文件。
- 不悄悄替换整个数据层；对当前 `node:sqlite` 与技术基线的偏离追加正式决策说明。

**验收**：中途注入异常后没有半套修改；旧提案不会覆盖新修改；合并再恢复后关联内容仍可用；旧版本数据升级和备份恢复均实测。

### A4. 安全默认值与快照闭环【发布阻断】

- 非开发部署首次启动必须设置管理员凭据，不以未设密码默认开放全部 API。
- 限制可信访问来源；登录增加适度速率限制，令牌可撤销。
- Provider Key 脱敏展示不等于加密落库；明确威胁模型，至少用数据文件之外的部署密钥加密保存，禁止进入日志和导出。
- 校验原生 `pageCapture` 的实际返回类型、权限与生命周期，不能只测上传接口。
- 在真实 Chrome/Edge 中走完捕获 → 存储 → 查看；MHTML 展示不能只依赖 iframe/blob 能直接渲染的假设。
- 快照查看禁脚本、禁表单等主动行为，限制外部联网；不可安全内嵌时提供受控下载/打开路径并明确局限。
- 上传限制体积、格式、配额；快照下载执行鉴权和隐私检查。

**验收**：普通页、需登录页、捕获失败页都有清楚结果；重启后快照仍可打开；失败文件不计为成功；未授权不能读取。快照查看不能执行原页脚本或悄悄访问原站。

## 6. 执行包 B：把核心体验打磨到愿意长期自用

### B1. 新标签页离线优先

- 首屏先显示上次有效导航数据，再后台刷新。
- 断网时保留可点击链接，显示轻量离线状态，不以错误页替代导航。
- 已有缓存支持标题/URL 基础搜索；正文搜索需要服务端时明确提示。
- 首次无缓存展示连接指引和示例，不伪装成已导入的个人数据。
- 退出登录、切换服务端时隔离或清除缓存，避免跨账户展示旧数据。

**验收**：刷新离线新标签页仍可使用已缓存入口；连续打开不等待远程请求才显示内容；服务器切换不串数据。缓存读取到列表显示的本机目标为 300ms 内，记录测试设备与数据规模，不宣传为所有设备保证。

### B2. 导航与资料库分视图，不分数据库

- 复用现有 `pinned` 能力，主页优先展示用户固定的入口。
- 首次无固定项时提供有限候选并允许调整，不一次铺满全部书签。
- 全量资料放到搜索/目录浏览中，保留进入资料库的明显入口。
- 原始导入目录保持可用，AI 先给提案，不为展示效果强行重排。
- 暂不引入额外“工作空间”模型和复杂推荐算法。

**验收**：用户能够区分常用入口与全部收藏；能够在不接受任何 AI 修改的情况下使用产品；不启用新标签页也能完成收藏和找回。

### B3. 让内容理解真的优于域名粗分

- 域名规则用于首轮推荐，广泛内容站不能永久锁定为“视频/阅读”。
- 优先级：用户固定归类/明确规则 > 用户确认过的纠正 > 内容语义 > 域名粗判。
- 收件箱模型输入包含可用摘要，缺内容时明确标注“仅按标题/URL 判断”。
- 自动移动默认保守；不把模型自报置信度直接解释为准确率。
- 用户修正后先记为可见的偏好候选，可选择“仅本条”或“记住此规则”；不自动把单次纠正推广到整个域名。
- 千级整理分批、可取消、显示处理范围；如本轮只处理 500 条，必须明确告知，不称为全库完成。

**验收**：同一网站不同主题可以进入不同目录；用户手动固定项不再被重排；无模型和内容失败时仍可使用；任务进度和实际扫描数一致。

### B4. 找回优先于复杂聊天

- 先完善标题、URL、备注、正文搜索，给出命中片段及来源。
- 补 FTS5 前先跑真实规模基准；中文分词/子串命中单独验证，不能因启用 FTS 就假设中文效果改善。
- 语义搜索只在已有向量时启用，不为一次搜索触发全库向量化。
- 模糊查询展示匹配依据；无结果提供清空筛选、关键词搜索等退路。
- 聊天优先支持少量可靠命令，展示本轮范围、预览和确认，不伪装成任意自然语言都能执行。
- URL 去重采用保守策略：原始 URL 永久保留；协议、hash 路由和业务参数不能无条件丢弃；相似 URL 先建议，不自动合并。

**验收**：能通过标题记忆、正文关键词、模糊语义找到样本目标；正确打开原始可访问地址；不同 hash 路由和业务参数页面不会被误吞。

## 7. 执行包 C：交付给别人，而不是要求别人理解开发环境

### C1. 安装与首次体验

- 首发说明只突出一条推荐安装路径，其余列为高级选项。
- 扩展设置提供连接检测：地址、权限、认证、模型故障分别提示，不统一报“连接失败”。
- 导入后立即能浏览原始资料和导航候选；AI 设置不是基础价值的门槛。
- 模型配置只推荐少数已验证路径，其他供应商放高级设置；连接测试标明会发送最小测试请求。
- Docker 资源目标必须标明范围：server 容器与 Ollama 模型服务分开计量，不能让用户误以为整套离线 AI 小于 300MB。
- README 对“同步”“私密”“备份”“云端”“纯本地”使用与实现一致的措辞。

**验收**：从干净浏览器与新数据目录按文档完成安装、登录、导入、搜索、一次整理撤销；不需要临时 SQL、隐藏环境变量或开发者口头补充。

### C2. 完整备份与恢复

- 区分“书签交换导出”和“完整备份”，不能以 JSON 元数据导出冒充全部数据备份。
- 完整备份列明书签、目录、缓存、快照文件与索引、偏好、版本历史的覆盖范围。
- 导出凭据默认排除；私密数据处理方式显式确认。
- 备份包包含格式版本、文件清单与校验信息；导入前显示恢复范围与冲突策略。
- 先做好空实例恢复，再考虑复杂增量合并。

**验收**：真实数据导出到全新实例；数量、关键内容、隐私状态和快照打开结果一致。保留一份可重复执行的恢复演练记录。

## 8. 用 AI 深度打磨的方法：评测集替代臆测，不替代用户

### 8.1 建立一份可重复使用的样本库

从开发者自己的真实书签提取脱敏样本，先建 100–200 条即可，覆盖：

- 同域不同主题、多级目录、同名目录；
- 中文、英文、长标题、无标题；
- hash 路由、业务参数、相似但不同的页面；
- 需登录、内网、隐私域、正文提取失败；
- 重复事件、断网重试、过期提案、关联快照恢复。

分类允许多个合理答案；搜索样本记录“想找什么、目标链接是什么”；安全与一致性样本必须有确定结果。样本不提交真实隐私正文和凭据。

### 8.2 每轮 AI 工作单

每轮只给 AI 一个边界清晰的目标，包含：

```text
目标：解决哪个用户任务/缺陷
范围：允许修改哪些模块
不做：明确排除的扩张项
约束：隐私、回滚、资源和技术基线
验收：具体输入、操作、预期结果
证据：测试结果、截图/记录、已知限制
文档：需要同步更新的产品/技术说明和 changeset
```

AI 必须区分：已实现、自动化测试通过、真实浏览器验证通过、尚未验证。不能把 mock 测试通过写成真实分类质量达标，也不能为了完成任务私自降低原验收标准。

### 8.3 两套回归

- **确定性回归**：mock LLM，验证失败处理、数据一致性、隐私和协议，每次修改运行。
- **真实质量抽查**：固定脱敏样本，按需调用真实模型，记录模型版本、成本、输入来源和结果差异；不要求每次提交都消耗真实 API。

分类质量先比较规则版与内容版是否明显改善；没有改善就先查输入质量和策略，不继续叠加 Agent。搜索先看目标能否找到，再考虑答案生成。

## 9. 自用 → 发布 → 反馈：轻量观察，不建立研究负担

### 9.1 自用记录只写三件事

每次真实使用遇到明显问题，记录：

1. 我当时要完成什么？
2. 哪里卡住、改用什么办法？
3. 是否愿意下次继续用？

用单一 Markdown 文件或 GitHub Issue 即可，不再维护第二套项目管理系统。不要为了完成测试指标虚构日常需求。

### 9.2 发布反馈入口

- 设置页提供反馈链接和手动导出诊断摘要。
- 模板仅要求：想做什么、实际发生什么、期望怎样；版本/部署模式自动填入可复制文本。
- 默认不上传书签、URL、正文、截图、Key 或 token。
- 不使用产品也可能有价值的反馈：“安装太麻烦”“不愿替换新标签页”“配置模型就放弃了”。

### 9.3 数据采集最小化

首阶段不为观察而额外建设云端埋点服务：自建可只在本地保存计数和错误摘要，用户自愿导出；纯本地能力未来默认不外发使用数据。

如需远程统计，必须显式说明并允许关闭。事件只记录任务与结果，不带内容：

| 事件 | 用途 |
|---|---|
| `bookmark_save_completed/failed` | 收藏是否可靠 |
| `search_submitted`、`search_result_opened` | 搜索后是否打开结果；不是成功找回的绝对证明 |
| `bookmark_opened`（记录入口来源） | 区分主页曝光和真实使用 |
| `organize_applied/reverted` | 观察整理使用和撤销 |
| `classification_corrected` | 发现规则与内容分类问题 |
| `snapshot_created/opened/failed` | 验证快照全链路 |

优先修正现有语义错误：自动展示周报角标不应记录为 `weekly_report_clicked`；打开新标签页不应等同于启用操作或有效使用。

### 9.4 小样本怎么做决策

| 信号 | 动作 |
|---|---|
| 数据丢失、泄露或无法恢复 | 立即停止相关自动动作，作为发布阻断修复 |
| 自己真实任务反复卡在同一步 | 优先修复，不需要等更多用户投票 |
| 多次独立反馈同一阻碍 | 提升优先级，先找共同根因 |
| 单条新功能建议 | 记录场景，暂不直接实现 |
| 用户导入后不再回来 | 检查找回价值、安装成本和入口，不先加通知 |
| 用户持续找回但不用主页 | 保留资料库方向，不强推新标签页 |

每轮真实使用/反馈回看只输出三个结论：**继续什么、修复什么、暂不做什么**。样本少时记录事实，不给百分比强加普遍意义。

## 10. 里程碑、验收与停止扩张条件

| 顺序 | 里程碑 | 必须交付 | 完成后动作 |
|---|---|---|---|
| M-A | 可信基础 | A1–A4，隐私/收件箱/恢复/快照阻断项关闭 | 开发者开始承载真实日常数据 |
| M-B | 核心自用版 | B1–B4，搜索与导航可持续使用 | 用真实任务记录问题，不加外围功能 |
| M-C | 可发布自建版 | C1–C2，干净环境安装与恢复演练 | 发布预览版本，附明确限制 |
| M-D | 反馈驱动增强 | 修复高频阻碍，选择一个扩展方向 | 决定完整本地或云端托管是否优先 |

### 发布最低门槛

- 所有已发现的数据安全、隐私和未授权访问阻断项关闭。
- 收藏、找回、整理确认/撤销、快照、备份恢复五条任务链完整。
- 服务端故障不摧毁已有导航入口；后台重试不制造重复数据。
- 已知限制对外可见；不宣称不存在的部署能力。
- 生产镜像、运行内存与 ARM64 按既有红线实测；报告包含并发、数据规模及峰值，而不只空闲内存。
- 无需等完整本地模式、支付或所有远期功能完成，即可发布自建预览版。

### 资源有限时的裁剪规则

可以先裁剪语义搜索、自动精修、浏览器镜像等增强能力；不能裁剪隐私检查、数据恢复和失败告知。若某能力未达到验收，降级并说明，不以“AI 已写完”维持完成标记。

## 11. 后续方向选择与云端门槛

**完整本地模式优先的信号**：用户想用但不愿部署；偏好隐私与 BYOK；没有强烈跨设备诉求。

**云端托管优先的信号**：用户持续使用并明确希望免部署、跨设备、代付模型；愿为这些便利付费。付费意向不等同于收入，最终仍以真实购买和续用观察。

云端上线前至少补齐：租户级访问控制及跨租户测试、账户与令牌生命周期、对象存储隔离、原子配额与计量、抓取网络隔离、备份删除策略、日志脱敏、滥用限制和基础运维。云端与自建共享领域逻辑，不要求运行能力完全等价。

定价保留 ¥99 早鸟/¥128 年费作为既有假设，暂不另做复杂套餐。成本记录包含模型、抓取、存储、流量和失败重试；“全库整理低于 ¥0.5”“缓存命中 90%”等只在有实测条件后对外使用。

## 12. 建议决策记录（待实施确认后追加至权威文档）

以下不覆盖 D1–D13，建议确认后以 D14 起追加：

1. 采用“AI 深度打磨 → 自用 → 发布观察 → 反馈迭代”，不把全面调研作为前置。
2. 下一轮优先交付可信的单用户自建版本，不同时完善三种部署形态。
3. 应用库为主数据；浏览器书签先作为导入源和可选镜像，明确同步边界。
4. 导航是入口之一，资料找回是长期核心价值；不强制更换新标签页。
5. 新标签页缓存与完整本地模式分开验收和宣传。
6. 以真实任务完成、搜索结果使用和持续自用观察为主，导航曝光为辅；小样本不追求统计显著性。

**本方案的完成标志不是新增多少功能，而是：开发者愿意把自己的真实资料交给它，别人能按文档独立用起来，遇到问题有办法恢复并反馈。**
