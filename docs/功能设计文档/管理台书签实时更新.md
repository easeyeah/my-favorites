## 1. 用户场景与范围

核心场景：用户保持管理台书签库页面打开，在浏览器收藏夹栏删除一个书签或目录；管理台对应行、目录树和计数自动更新。

覆盖：
- 书签新增、删除、标题与 URL 修改、跨目录移动。
- 目录新增、删除、改名、调整父子关系。
- 普通列表、筛选与搜索、多目录联合视图、已加载多页列表。
- 编辑期间变更、断线重连、后台切回前台。

边界：
- 以服务端已经提交的数据为准。扩展离线、删除等待确认、同步失败时，不在管理台提前假装删除成功。
- 本任务不改变同步冲突策略、删除保险丝、目录身份或库侧排序规则。
- 沿用 SSE + HTTP，无需引入 WebSocket 或新的数据状态管理框架。

## 2. 现状与缺口

| 现状 | 缺口 |
|---|---|
| `apps/web/src/lib/events.ts` 提供共享 SSE 连接与页面通知订阅 | 首次连接成功也需要补刷新，避免首次查询与订阅建立之间漏变更 |
| `library.tsx` 已订阅变更并刷新目录树、列表和徽章 | 编辑/弹窗/右键菜单打开时直接跳过通知，关闭后没有必然补刷 |
| `loadPage` 被手动加载和通知刷新共用 | 非追加加载会先清空列表；自动刷新退回第一页，影响滚动与已加载内容 |
| 目录树可重新获取 | 当前选中目录被删除后，需要修正选中位置与失效选择 |
| SSE 有断线重连 | 还需前台恢复校准，以及连接状态、刷新失败的可观测性 |

上述为设计时源码观察，不构成用户现场故障根因的复现结论。实现前需核对当前工作区。

## 3. 数据链路

```text
浏览器收藏夹操作
    → 扩展持久化并同步操作
    → 服务端事务提交、记录 changes
    → SSE 通知“数据已变化”
    → 管理台标记需刷新，合并重复通知
    → HTTP 查询当前视图、目录树与计数
    → 校验响应所属视图，统一更新 React 状态
```

SSE 只负责通知；列表内容仍由服务端查询提供，不在前端按通知猜测删除范围。服务端通知应对应已提交数据，避免前端查询到事务尚未提交的状态。

第一阶段使用“通知后重新查询”，复用现有 API；不要求增加逐条书签事件载荷或前端事件重放器。

## 4. 交互规则

| 事件 | 管理台行为 |
|---|---|
| 删除可见书签 | 行移除，列表与计数更新；从多选集合中移除该 ID |
| 新增书签 | 按当前过滤条件与既有排序出现在对应位置 |
| 修改标题、URL | 更新对应字段；搜索结果按当前关键词重新查询 |
| 移动书签 | 源目录移除、目标目录加入，各自计数更新 |
| 删除未选中目录 | 树中移除整棵子树，当前浏览位置不变 |
| 删除当前目录或其祖先 | 选择最近仍存在的原祖先；全部祖先都不存在则回“全部书签” |
| 目录改名或搬家 | 保持目录 ID 选中，更新名称、树位置及相关计数 |
| 删除正在查看详情的书签 | 非编辑态关闭失效详情，并轻提示一次 |
| 删除正在编辑的书签 | 保留草稿，标记“该书签已被删除”，阻止无效保存，允许复制草稿或关闭；不得自动重建 |
| 外部修改正在编辑的书签 | 不覆盖输入；标记外部变化，保存时沿用明确的冲突处理策略，不静默覆盖 |

无需每次同步弹 toast；正常更新安静完成。仅当前位置失效、编辑冲突和持续失败需要明确反馈。

### 4.1 编辑保护与延迟刷新

- 编辑、创建、改名、批量操作弹窗或右键菜单打开时，通知仍必须记录为 dirty，不能直接丢弃。
- 第一阶段可暂停影响交互的数据替换；全部阻塞交互关闭后立即补刷。
- 暂停期间同类通知合并，不累计无限通知队列。
- 对正在编辑的实体，可单独做存在性/版本校验，只更新冲突提示，不修改草稿。
- 保存遇到 404 或冲突响应时保留输入，按上表处理。

### 4.2 被删除目录的回退

使用刷新前的树记录选中目录的祖先链，在刷新后的树中寻找最近仍存在的祖先；不能从已删除的新树节点反推祖先。

多目录选择时剔除不存在的目录：剩余多个仍保持联合视图，剩余一个切换为单目录，无剩余则回“全部书签”。搜索模式下保留关键词，修正失效目录范围后重新查询。

## 5. 前端实现设计

### 5.1 共享通知与刷新调度

沿用 Shell 级单条 SSE 连接、页面订阅模式。刷新状态至少包含：

| 字段 | 用途 |
|---|---|
| `dirty` | 有变更尚未完成校准 |
| `refreshing` | 当前是否有刷新批次在执行 |
| `blocked` | 编辑或弹窗是否阻塞数据替换 |
| `viewKey` | 账号/服务端、目录、筛选、关键词等视图身份 |
| `requestEpoch` | 防止旧请求覆盖新状态 |
| `lastRefreshError` / `lastSuccessfulRefreshAt` | 失败提示与恢复校准 |

调度规则：
1. 收到通知先置 dirty，再以 200～500ms 合并触发；连续通知设置最大等待时间（建议 1 秒），避免一直防抖不执行。
2. 已有刷新在途时不启动另一批，保留 dirty；当前批次结束后若仍 dirty，再补一批。
3. blocked 时保留 dirty，解除阻塞后补刷。
4. 开始请求后到达的新通知不得被此次完成动作清掉；使用通知代数或在请求前消费 dirty 的方式保证补轮。
5. 视图、账号或服务端切换时取消旧请求并递增 epoch；旧响应无权写入新视图。
6. 目录树请求失败不得当作“全部目录已删除”，只有成功获取树后才能执行选中目录回退。

### 5.2 后台刷新与分页

区分首次/切换加载与后台刷新：
- 首次或切换目录可以显示加载状态。
- 自动刷新保留旧列表，不执行 `setItems(null)`；成功后替换，失败保留旧内容。
- 单目录普通列表重新获取当前已加载窗口，不能只刷新第一页；遵守 API 单页上限，必要时顺序分页。
- 多目录联合视图按各目录已加载窗口重新查询并去重；保留既有联合视图排序语义。
- 搜索、失效、重复等视图通过各自数据加载函数校准，不能仅刷新普通书签列表而留下旧结果。
- 目录树、列表与计数尽量按同一刷新批次发布；若目录回退改变查询范围，旧范围的响应作废。
- 同一时刻每个视图只允许一批刷新；避免 SSE 事件叠加造成请求洪水。

### 5.3 保持交互位置

- 使用稳定实体 ID 作为 React key。
- 保留仍存在的目录展开状态、关键词、有效筛选条件。
- 记录可见首行 ID 与相对视口偏移，刷新后优先恢复该锚点；锚点被删除时选择邻近仍存在的行。
- 仅因为当前目录被删除而回退视图时，允许重置列表位置。
- 清理已确认删除或已不在可操作范围的选中项；不能因某 ID 不在当前分页响应里就判定它已被删除。

## 6. 连接与失败恢复

- 首次 SSE 连接成功、每次重连成功：标记 dirty 并补刷新。
- 页面从隐藏恢复可见、网络恢复在线：标记 dirty；与既有在途刷新合并。
- SSE 断线期间，页面可见且在线时以低频校准兜底（建议 30 秒，走同一调度器）；连接恢复后停止该兜底。
- 页面隐藏时可延后视图查询，保留 dirty；恢复前台后立即校准。
- 刷新失败：保留当前数据和 dirty，显示安静的“更新失败，正在重试”状态；退避重试，允许手动重试。
- 401/403：交给现有认证处理，不持续高频重连。
- `?mock` 保持短路，不连接真实 SSE；通过模拟事件验证前端交互。
- 清理连接、监听、定时器和请求，避免卸载或切换账号后的残留刷新。

## 7. 时效目标与排障

目标分两段测量：

| 指标 | 建议目标 |
|---|---|
| 服务端提交成功 → 活跃管理台呈现 | 正常网络、普通单条操作下 P95 ≤2 秒 |
| 浏览器用户操作 → 管理台呈现 | 单独记录扩展等待、同步提交与前端呈现耗时；不得用前端指标替代端到端指标 |

当前扩展 8 秒防抖会增加端到端延迟，不能通过前端 SSE 改造消除。缩短扩展等待应在同步可靠性整改通过后独立验证。休眠、断网、编辑保护和删除待确认不计入普通活跃路径时效目标，需验证恢复行为。

排障顺序：
1. 查看 Docker 请求耗时与服务端是否已经收到删除。
2. 服务端已变但页面未变：核对 SSE 连接、收到通知、dirty 状态、刷新请求与响应应用。
3. 服务端未变：检查扩展队列、错误状态及删除保险丝。
4. 核对部署的 web 构建产物是否包含新逻辑，不能以源码已接入推断当前页面已更新。

诊断信息记录时间、状态和请求关联信息即可，不记录令牌及完整书签 URL。
