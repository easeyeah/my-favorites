## 1. 设计结论

**把“在旧目录中选落点”升级为“先识别用途，再按内容归类”：网站和工具入口留书签，文章/教程/报告等内容进入资料库自己的分类；两条路径在同一次可追踪、可撤销的整理任务内完成。**

核心区别：不仅判断“该放哪个文件夹”，还判断“它该不该继续作为书签”。资料分类不等于书签目录，也不把所有内容页塞进浏览器里的“资料”文件夹。

用户只需：

1. 打开一个目录，点击 **“整理此目录”**；目录右键保留相同入口，不增加“是否转资料”的设置开关。
2. 产品识别网站/工具入口与内容资料，必要时在隐私允许下补取正文以确认资料性质；证据不足则保留书签并解释。
3. 书签分支根据主题生成合理目录，复用合适旧目录或创建最多两层新分组；资料分支按内容主题匹配或生成资料分类。
4. 确认的资料在“资料内容有效 + 分类有效”后软转换，管理台书签面不再重复保留，原始关联和正文不物理删除；其他书签分批归位。
5. 任务详情持续展示“已移动到哪个书签目录 / 已收入哪个资料分类”，用户可以停止、查看原文或去向，并撤销本次调整。

保留：品牌靛蓝与 shadcn 结构、所选来源范围、书签分支的子树边界、既有实体身份与用户操作保护、点了就跑、直接生效 + 可撤销、隐私前置。

改变：旧树不再限定分类，目标也不再只有书签目录；新增内容驱动的用途判定、资料分类与软转换，以及新书签目录生成、完整范围、可见过程与真实结果。

不做：聊天框、整理参数向导、先预览再确认的审批流、为了显得有效而强行挪动、自动删除、独立任务中心。

## 2. 现有功能在重做之前的问题（设计依据，2026-11-24 实现前核对）

> 本节保留作设计来路与回归依据；其中列出的缺口已随 D92 修复。当前行为见技术方案 §8 6j。

### 2.1 重做之前的三个相近入口

| 当前入口 | 实际含义 | 不代表什么 |
| --- | --- | --- |
| 普通目录右键“AI 重新整理此目录” | 对该目录及子目录中的书签重新选择落点；目标原则上限定子树内，可以新建子目录 | 不是自动合并、改名、搬家全部目录，也不是资料提取 |
| 书签页功能区“全库重分类” | 对全库候选做重分类，不跟随当前所选目录 | 不是整理当前搜索结果、当前页或勾选项 |
| 收纳盒“AI 归位”及后台分类自检 | 处理新投递及满足条件的自动归位条目 | 不是定时重整所有已有目录 |

现有目录入口点击后关闭菜单，等待一个普通 JSON 请求；目录行仅有小转圈，最终通过约 3.8 秒的 toast 告知结果。没有任务过程、逐条去向、停止或重新打开本次结果的入口。目录操作的源码入口见 `apps/web/src/pages/library.tsx:899`；全库入口与结果见 `apps/web/src/components/TidyPanel.tsx:453`。

### 2.2 已核实的问题，不把推测当现场根因

以下是对 2026-11-24 当前工作区的静态核对，**没有执行真实目录整理、读取用户当次响应或调用模型，不能断言用户那一次操作的具体故障原因**。

| 代码事实 | 对用户的影响 | 依据 |
| --- | --- | --- |
| 目录任务没有阶段、逐条结果或停止；只刷新树、当前选中列表并弹 toast | 不知道是否在工作，结果消失后无法追溯 | `apps/web/src/pages/library.tsx:903`、`:1372`；`apps/web/src/components/shared.tsx:183` |
| 非审核类模型异常被空 catch 吞掉；零动作仍可能说明“分类结果与现有目录一致” | “模型没跑成”被包装成“无需调整” | `apps/server/src/organize.ts:468`、`:479` |
| 只读前 500 条，读取后再过滤归档；没有续扫游标或剩余数 | 大目录没覆盖完整；重复点不等于处理后面的书签 | `apps/server/src/organize.ts:31`、`:231`；`apps/server/src/store.ts:724` |
| 域名规则命中，但规则类别不在当前子树时直接跳过，不再进入模型候选 | 如“开发”目录需要细分，但粗规则落点不适用时，可能什么也不做 | `apps/server/src/organize.ts:398`、`:413` |
| 模型输出目录名称；同名当前目录不产移动，子树同名目录取第一个 | 同名不等于同一目录，名称匹配掩盖了身份歧义 | `apps/server/src/organize.ts:452`、`:507`、`:583` |
| applied 计版本动作，含建目录；返回 actions 是计划，不是实际成功回执 | “处理 N 项”不等于移动 N 条；冲突项也可能出现在结果清单 | `apps/server/src/organize.ts:323`、`:755`、`:826` |
| 行为主要是按标题、URL、已有摘要归类，不主动补抓正文，不生成摘要、不用向量 | 不能向用户承诺已经深入阅读或修好了所有目录结构 | `apps/server/src/organize.ts:507`、`:523` |
| 修订基线在模型返回后才收集；提交未完整核对是否仍在原子树 | 模型等待期间的用户改动，存在被旧计划覆盖的路径 | `apps/server/src/organize.ts:297`、`:432`、`:747` |

另有三个必须作为实现阻断项修正的边界：

- **私密输入风险**：候选预筛未完整排除 `is_private`；目录代表样本也未完整排除私密及隐私域。提交时拒绝私密项不能撤回已经发生的模型输入。这里确认的是可达代码路径，未验证实际发生过外发。见 `organize.ts:382`、`:523`、`store.ts:1889`。
- **子树例外**：供应商审核隔离可能调用全局“私人收藏”落点，不能声称现有所有动作都严格留在子树。见 `organize.ts:463`、`:563`。
- **资料生命周期竞争**：D91 已转资料条目的移动可能返回未写入，而旧 apply 仍计移动成功。新任务必须以真实写入回执计数。见 `store.ts:509`、`organize.ts:755`。

上述缺口不是本批 D91 导致的新体验；目录同步请求及主要分类路径原先就存在。当前代码没有 `maxOps` 配额，不能把零处理解释为“默认只允许移动几条”。

## 3. 产品边界：整理要做到什么

### 3.1 本次“整理”的明确承诺

> 检查此目录及全部子目录中的有效书签：网站/工具入口按内容主题在本子树内归位，确认的文章、教程、报告、文档、视频或图片收入资料库对应分类。旧目录与旧资料分类只作参考，不限制 AI 发现合理新分类。资料转换是明确的第二目标，不是移动到另一个普通书签目录；不物理删除收藏，所有实际调整均可撤销。

具体包括：

- 旧目录过于宽泛、混乱或名不副实时，可以重新归纳主题，不要求逐项对应旧目录名。
- 父目录散落的条目和多个旧子目录中的相近内容，可以汇入同一个新主题；旧子目录不会成为互不相通的分类围栏。
- 合适的旧目录按稳定 ID 复用，避免为了“显得智能”创建同义副本；但不能因为存在一个叫“工具”的目录，就拒绝创建语义更明确的“远程控制”。
- 新分类是正式规划结果，不是规则失败后的兜底。目录和父子层级可以一起生成，在所选目录内部形成最多两层新分组。
- 条目少、主题单一时可以保持简单；同主题只有两条也不因旧方案“至少三条”的门槛被一律拒绝。证据不足或受保护时保持原位，并解释。

**示例（合成演示，不是用户真实收藏或模型实测）**：

```text
整理前：常用收藏 / 常用、工具、其他（不同内容混放）

AI 按内容提出的有效分类分支：
常用收藏
├─ 开发
│  ├─ 前端开发     React、Vue、Vite
│  └─ 后端开发     Hono、SQLite
├─ 部署运维       Docker、Portainer、Nginx
├─ 远程控制       RustDesk、Sill、Tomaco
└─ 设计资源       Figma、Iconify
```

这不是预置分类模板，也不要求每次都产出这棵树。上例名称代表站点/工具入口，不代表这些产品下的每个教程页面也应留下做书签。示例仅展示书签分支；被迁空的旧“常用 / 工具 / 其他”仍保留，不能画成已自动删除。

同一次整理的资料分支示例（同样为合成演示）：

| 收藏内容 | 去向 | 理由 |
| --- | --- | --- |
| Docker 官网/管理入口 | 书签 → 本目录 / 部署运维 | 主要价值是反复访问服务或工具 |
| 《Docker Compose 部署教程》完整文章 | 资料 → 技术开发 / 容器部署 | 有可保存、检索和引用的正文，不再只是网站入口 |
| Figma 编辑器 | 书签 → 本目录 / 设计资源 | 交互工具入口 |
| Figma 自动布局教程、设计规范报告 | 资料 → 设计 / 界面设计 | 内容消费与知识沉淀用途 |
| 无法取得正文、用途不能确认的页面 | 保留原书签并说明原因 | 不凭“看起来像文章”的 URL 强行移走 |

### 3.2 不夹带的操作

- 不自动删除、归档或合并书签；查重、死链、归档建议继续走已有独立功能。
- 不自动重命名、合并、移动或删除既有目录；空目录不擅自清理。
- 不为了制造“整理成果”把所有条目重排一次，也不改标题、URL、备注和置顶状态。
- 快照、封面、摘要生成、favicon、向量化仍是增强任务，不作为成功前提；资料性质判断所需正文例外：没有有效证据就不转换，不能把取证与装饰回填混为一谈。
- 不启动无人值守的全库存量转换；仅处理用户本次显式圈定的目录。D91 新收纳盒增量自动处理保持独立来源，D89“提取资料”旧入口不被静默改成移出书签。
- 不新增全库巡检开关或周期调度。本功能是**用户发起的一次整理任务**，“自动”指执行无需逐条确认。

### 3.3 范围规则

| 情况 | 新规则 |
| --- | --- |
| 普通目录 | 来源包含全部后代目录，无需开关；书签目标限本子树，另允许确认的内容进入当前用户资料库的资料分类，不允许普通书签跨子树搬家 |
| 搜索、状态筛选、分页 | 不缩小整理范围；按钮文案固定“整理此目录（含子目录）”，详情首屏再次注明“不仅是当前列表” |
| 多选书签或多选目录 | 不出现语义不明的“整理所选”；本期不支持联合范围。批量工具条仍按 D74 顶替筛选区 |
| 全部书签 | 保留单独的“全库重分类”，不借目录按钮隐式扩大范围 |
| 收纳盒 | 保留“AI 归位”，不开放普通目录整理；不把系统收纳盒作为普通分类目标 |
| 已归档、合并软归档、已转资料 | 不参与，不占有效书签总数；范围检查给出排除说明 |
| 私密、隐私域、敏感旁路项 | 不进入普通模型输入或样本，也不由本任务搬家；仅给受保护的汇总，不展开标题、URL 或目录证据 |
| 任务发起前用户手动分类的条目 | 本次显式整理可重新评估；不更改后台 D77“手动意图不再自动复核”的资格规则 |
| 任务发起后的用户修改 | 用户优先，提交时跳过；不能用模型返回时的状态替换原始基线 |

## 4. 使用与交互设计

### 4.1 入口与一键启动

- **主入口**：单目录视图的目录标题操作区增加 `Sparkles` 图标 +“整理此目录”，不再要求用户知道右键入口。
- **快捷入口**：目录右键保留同名菜单项，两处进入同一任务。
- 点击即创建任务并打开详情，不增加确认向导、模式选择或参数页。点击前可见说明“整理目录，内容页会收入资料分类，必要时读取正文；均可撤销”，详情重复说明来源范围与两种去向，不能把资料转换藏在只有结果页才看得到的副作用里。
- 空目录禁用并说明“目录内没有可整理书签”；最终数量以服务端范围检查为准。
- 同一账号已有整理任务时，入口变为“查看整理进度”，不会连点创建并行任务。
- 请求失败保留可重试入口；用创建幂等键找回已被服务端接受的任务，不盲目新建。

### 4.2 任务详情：先告诉用户正在做什么

采用现有 Dialog，不增加侧栏壳、聊天框、独立页签或悬浮小窗。以下均为**示例数据，不是实测结果**：

```text
整理「开发」                                      [收起]
```

过程要求：

- 阶段来自真实执行状态，不以定时器模拟进度。
- 范围未读完时显示“正在检查范围”，不先显示假的总条数。
- 目录方案尚在生成时，明确显示“正在发现内容主题，尚未创建目录或移动书签”，并展示已归纳的条目数与当前批次；这是阶段工作量，不提前算作已检查或已移动。
- 方案校验通过后展示只读结构摘要：发现哪些主题、哪些分支拟新建/复用、预计承接多少条及简短理由。它是过程解释，不是新的确认审批；不要求用户逐个勾选目录。
- “计划新增 N 个”与“实际已创建 N 个”分开，节点显示拟新建/已创建/复用/未应用状态；完整目录变化明细分页查看，不能把模型提议当成目录已经存在。
- 逐批提交后更新已检查数、实际移动/转资料数及最近记录；单纯正文取得、模型返回或排队不算转换完成，不冒充逐条落库成功。
- 模型等待期间显示阶段、等待时间、重试次数；不承诺固定剩余秒数，不展示模型思维链或原始输出。
- 总进度以**已形成最终结果的书签数 / 固定范围总数**计算。分析数量可另作当前阶段信息，不能与已落库数量混用。
- `checked/total` 是检查覆盖率，不是成功率。只有每条都形成结果、剩余为 0 才能显示“检查完成”；存在失败时同时展示失败计数和异常终态，覆盖率即使达到 100% 也不是“全部整理成功”。停止或任务级失败仍有 remaining 时，绝不能把进度补成 100%。

### 4.3 收起不丢任务，停止才停止

| 用户动作 | 行为 |
| --- | --- |
| 收起详情、切目录、切页签、刷新页面 | 服务端任务继续；书签页既有整理功能区显示“正在整理「开发」· 42/112 · 查看” |
| 再次点击整理或任务状态入口 | 打开同一个任务，不重复执行 |
| 断网 / 任务观察连接断开 | 只中断观察，不等于停止任务；恢复后按任务 ID 查询真相 |
| 点击“停止整理” | 持久记录停止请求；停止发起下一批、取消可取消的模型请求，未提交计划不再提交；已提交结果保留且可撤销 |
| 服务端重启 | 从持久检查点接续尚未完成部分；已确认移动/转换/分类不重复执行，恢复前重验基线、证据、生命周期与隐私 |
| 任务因配置/进程故障不能继续 | 结束或停止状态必须可见，保留原因和剩余数，提供“继续剩余”或“重试失败项” |

关闭行为必须明示“收起，任务继续”；不能把“关闭对话框”同时设计成静默取消。D89 资料扫描仍沿用它自己的断开即停语义，不随本次改动。

### 4.4 结果不能只是一句“整理完成”

示例：

```text
检查完成，有 2 条处理失败
检查 112 条：书签移动 18 · 转资料 24 · 保持 62 · 跳过 6 · 失败 2
书签新建 2 个子目录；资料新增 3 个分类路径（均不计入处理条数）
转资料 24 条中，新建资料 20 条、复用既有资料 4 条

[书签移动 18] [转资料 24] [保持 62] [跳过 6] [失败 2]
标题                 原位置 → 新位置 / 具体原因
...
共 18 条 · 第 1 / 2 页              [上一页] [1] [2] [下一页]

[查看书签目录] [查看资料分类] [重试失败项] [撤销本次整理] [版本历史]
撤销会恢复书签归位/转换；资料内容仍保留，不会被删除
```

- “书签移动”与“转资料”分别只展示成功回执；行内去向必须带“书签 / …”或“资料 / …”前缀及简短理由，不能只显示一个同名分类让用户猜存在哪。
- 目标链接分别直达书签目录或资料页对应分类；资料分类深链/筛选状态作为本次 web 接线要求，不能因为资料已落库就省略去向入口。
- 结果默认先展示实际变化最多的分支，同时提供书签“目录变化”和“资料分类”：新建/复用及实际承接数；只有移动与转资料都为 0 时才进入零变更解释，不把“全部转资料”说成没处理。
- 被迁空的旧目录只标注“已空，仍保留”，不自动删除，也不假装目录树已经替换。必须检查真实完整关联，含子目录、受保护项或归档关联的目录不能误报为空。
- “保持”区分**当前位置合适 / 证据不足 / 规则未命中**，不能都写成“原分类很好”。
- “跳过”区分受保护、用户已修改、目录变化、已转资料、已删除等；敏感信息只聚合，不返回明细。若跳过 6 条中 2 条受保护，则说明“可查看 4 条，另 2 条受保护”，分页按可展示的 4 条计算，不制造空页。
- “失败”给人类可读原因、是否可重试；不能要求用户去 Docker 日志才知道模型没跑成。
- 停止时显示“已停止：已检查 42/112，剩余 70；已归位 8 条、转资料 6 条”，可继续剩余，不自动撤回已完成项；提交中的转换按同一停止屏障保护。
- 任务结果在刷新后可重新打开；零动作、规则降级、失败也有记录，不依赖是否生成 organize_version。
- **常驻找回入口**：书签页现有整理功能区保留“整理记录”，无论有没有活动任务都可打开最近任务列表，每页 10 条；点击某条只查看，不重新执行。任务结束并收起、刷新页面后，零动作和失败记录也能从这里找回。
- 任务详情与记录列表复用同一对话框，不建立新的任务中心或安全台账；“再次整理”与“查看记录”必须是两个明确动作。

### 4.5 零变更的标准文案

仅在 moved=0 且 converted=0 时使用下表；若只有转资料成功，正常报告转资料数与资料分类去向。

| 实际结果 | 必须展示 | 禁止展示 |
| --- | --- | --- |
| 全部被有效分析，明确保持原位 | “已检查 112 条，当前位置均合适，本次未移动” + 可查明细 | 无法证明分析完成时声称全部合适 |
| 模型未配置，规则未命中 | “未配置整理模型，本次仅检查本地规则；规则未命中，没有移动书签” + AI 设置入口 | “AI 整理完成”“库结构已经很好” |
| 有低置信度项 | “有 23 条证据不足，保留原位” | 把不确定说成无需调整 |
| 模型超时 / 鉴权失败 / 返回无效 | “模型处理失败，未完成 23 条判断；已提交结果保留” + 重试 | 吞掉异常后显示无需移动 |
| 范围为空 / 全部受保护 | “没有可自动整理的书签” + 范围或保护说明 | 成功处理 0 项 |
| 全部在提交前发生变化 | “本次未应用调整：条目或目录已变化，已保护你的最新操作” | “已整理 N 项”或假成功 |

## 5. 整理逻辑重设计

### 5.1 先完整盘点，再调用模型

1. 以所选 `folderId` 确认根目录身份，建立一次有限范围快照：根及后代目录 ID、有效书签 ID、原目录、内容修订、目录修订、URL 身份、隐私策略修订。
2. **在任何 await 模型调用之前**保存上述基线；生成计划时和提交时都不能重新采纳用户的新修订作为旧计划基线。
3. 候选按稳定 ID / keyset 分页写入持久任务项；不能使用移动后会变化的目录列表 OFFSET 来续扫，更不能每轮重读排序靠前 500 条。
4. 范围总数固定后，新收藏不混入本任务；后续修改、移出、转资料或删除作为提交冲突处理。范围构建本身也必须是短读事务/等价一致快照，不边调用模型边拼范围。
5. 私密与五动作隐私判定在**条目、目录代表样本、已有摘要**三处前置；模型返回后、持久化判断前与提交时再次重验策略及修订，过期证据丢弃/脱敏。隐藏开关不等于模型授权；不允许先送模型再在 apply 拒绝。
6. 书签归类使用已允许的标题、URL/域名、备注与已有摘要；资料性质判断优先复用同 URL/修订的有效授权正文，必要时限量补抓。不能用旧 URL 的正文或历史 active 资料代替本轮证据。
7. 全量授权元数据可先用于候选主题规划；正文取证只阻塞对应条目的资料转换，已具备证据的条目可继续各自批次。用途未定、正文不足或抓取失败的条目不提前移动后再转资料，也不因单个慢站阻塞管理台核心请求。

### 5.2 先定用途：网站入口与内容资料分两路

#### A. 判定用途，而不是只看是不是域名首页

- 网站主页、交互工具、工作台、搜索/导航入口等，主要价值是反复访问服务，保留为书签。功能位于 `/app` 等路径也可能是工具，不因非根路径就判资料。
- 文章、教程、报告、研究内容、具体文档篇章等，主要价值是保存、阅读、检索和引用，进入资料分支。文档导航首页与一篇实质文档要区分，不能按整站一刀切。
- 视频内容页、图片直链等沿用已核实的 URL 形态规则，不能把视频站主页/频道页当成具体资料；视频不下载本体。
- 普通网页的 URL 规则、标题和摘要只用于资料候选筛选；文章转换仍须当前有效正文达到候选门槛（沿用 ≥200 字）并由模型明确判为内容型。达到字数、URL 带 article、已有 material 行都不是充分证据；不用 D89 的 800 字无模型兜底自动移出。
- 首轮主题可依据全范围元数据形成候选方案，但只有用途与所需证据均确认后才能提交最终目标。分类不确定则保持；抓取/模型失败记失败并保留原书签，均有原因和可重试状态。

#### B. 必要正文取证必须受控

- 优先用 content_cache 中与当前 URL、修订及隐私授权匹配的正文；不足时才经 `server_fetch` 判定调用 guardedFetch，沿用总预算 25 秒、500KB 上限和 SSRF 守卫。
- 取证调用复用 `crawlOne({skipMaterialize:true,skipSummary:true,expected})` 一类受控入口；不能在正文刚抓到时就隐式建资料、触发转换或写分类。候选取证与最终提交彻底分开。
- 补抓队列全局并发 ≤1，与现有资料出站抓取预算协调；不为每行同时发请求。模型调用继续走统一出口、独立 call_model 判定和模型并发闸。
- 取证、类型判断、分类判断都在事务外，开始前、等待后、持久化前与提交时复核任务/URL/修订/隐私。抓取或模型被拒绝不重试绕过，临时证据随取消/隐私变更清理。
- 快照、封面、摘要重生成、向量化不参与“转换成功”的判断；失败不拖住已确认的内容与分类提交。

#### C. 资料必须进入自己的内容分类，不是书签“资料”目录

- 沿用 material.category 的独立路径体系：最多两级、每级规范化后最多 20 字。分类树来自 active 资料的路径聚合，没有要创建的 folders 实体，也不能把 bookmark folderId 填到 category 中。
- 根据内容主题匹配本用户既有资料分类，允许生成更合适的新路径；参考既有资料分类，不继承当前书签目录名，不仅填写 article/video/image 这类媒体类型。
- 例如“Docker 部署教程”可进入“技术开发 / 容器部署”，而同目录下 Docker 官网仍进书签“部署运维”；同主题跨来源资料可复用一个分类，不要求与书签树同构。
- 先规范化并校验完整路径，再复用/生成。长名需重拟短名，不能静默截断误并语义；不无限生成一文一类。资料方案拟新增完整路径的异常预算初值为每任务 64 条，与书签新节点预算分开；超预算重规划或明确停止，不能静默降级。
- 分类数量按规范化完整路径去重，聚合出的一级前缀不另冒充新分类记录。只给本任务实际转换/复用的资料赋值，不借分类规范化批量改写范围外资料。
- **成功条件 = 内容证据有效 + material active 可用 + 资料分类有效落库 + 书签软转换提交成功。** 不能先隐藏书签，再指望迟到摘要或分类回填填上“未分类”；不能只识别成 article 就算整理到资料分类。
- 无模型或无法可靠确定资料分类时，当前任务保留书签并说明资料分支未完成；不改变 D91 新收纳盒媒体规则的既有降级语义。

#### D. 复用生命周期内核，但新增显式任务资格

- 当前 D91 自动转换绑定“新收纳盒候选”；本任务是用户圈定的存量目录，需要独立来源 `organize_task`，绑定 taskId/itemId、用户、原目录、URL、内容/隐私修订、预期转换代际与资料分类修订。
- 不伪造 inbox 候选、entry_id 或 `undo=true` 来绕过资格。曾恢复为书签的内容，只有本次新的显式任务和新证据才可再次转换；自动队列仍不能自行复活旧意图。
- 资料不存在则创建，已有 active 则复用同一 material ID；两者都需本轮内容证据。历史 dismissed 资料不隐式复活，保留对应书签并给出“此前已移出资料库”的原因。
- 同一原书签只有一个最终主去向：`bookmark` 或 `material`。先判用途，再执行 move 或 convert；不能先移进 AI 新目录、再转换导致恢复位置和计数都错误。
- 转换复用软移出、隐藏行 FK 锚点、修订/代际/版本守卫与 materialize 事件；原目录取任务开始时的真实位置，非中间临时位置。禁止物理 DELETE 或借普通归档伪装转换。

### 5.3 书签分支：内容先行，发现主题 → 规划分类树 → 映射旧目录

以下目录图只服务最终保留为书签的分支；确认的资料走独立 material.category，不再为同一条内容创建书签落点。用途尚未确认的候选不能触发空目录创建。

**不能把完整旧目录名列表当成模型必须作答的标签集。先决定怎样分类才合理，再决定放到哪里。**

#### A. 先按内容发现主题，不让旧标签提前框住判断

- 用全范围经过授权的标题、URL/域名、备注、已有摘要分批归纳内容主题；首轮不提供旧子目录名作为可选答案，也不先按旧子目录分开聚类。
- 所选根目录名称、用户显式整理规则可以提供用途边界；原路径留作后续映射和用户习惯证据，不能当内容真值。
- 不按站点一刀切：同在 GitHub 的前端组件、运维项目和远控软件可以属于不同主题；相反，来自不同站点的相同用途内容可以聚在一起。
- 每批返回稳定的临时 topic key、简短语义定义、成员 ID 和可核对的代表证据；跨批汇总、合并同义主题，再形成任务共用分类方案。不是每批各造一套文件夹。
- 主题证据弱时明确标记不确定，不为完成任务而捏造分类。缺少正文时只承诺元数据/已有摘要层面的归纳。

#### B. 生成能找回内容的分类树，而不是无限细分

- 按主题之间的包含关系生成目录层级；同一级采用可比较的粒度，不把“前端开发”和“某个 React 小版本”平铺成并列大类。
- 新目录名短、通用、可持续收纳，避免照抄一条书签的长标题，也不硬编码固定的“开发 / 设计 / 工具”模板。
- 新目录可形成两层，例如“开发 → 前端开发 / 后端开发”。新节点距所选根最多两层，且兼容现有导入/同步路径的总深度约束；已有更深目录可以复用，但不能借复用继续无界加深。
- 不再固定“最多新增 8 个、每个至少 3 条”。两条语义很明确的远控软件也可以形成“远程控制”；条目少、主题单一时可以不建目录。少量离群项可留原位，不强制“一条一个目录”。
- 目录数量由内容规模与主题复杂度决定；执行前做碎片化、同义重复、无内容空节点、过深层级检查。服务端仍需异常安全预算，设计初值为每任务最多 64 个新节点；这是防失控上限，不是生成目标，也不是准确率结论。
- 超预算先做一次受限的主题合并/粗化重规划；仍不合理则明确停止于规划阶段，报告“目录方案过细，尚未应用”。不能静默退回旧目录分类或假装所有书签已检查。

#### C. 最后与旧目录做语义映射，决定复用还是新建

- 有了主题树后，才读取旧目录的稳定 ID、相对路径和经隐私筛选的内容样本，判断它能否承载某个主题。
- 旧目录语义和粒度都合适则复用，不要求名称完全相同；只有名称相似但内容混杂的“工具”不能自动吞掉“远程控制”。
- 没有合适落点就创建新目录，**新分类不必经过“先在旧目录匹配失败”才获得资格**。优化顺序是内容一致、容易找回、层次合理，其次才是减少变动。
- 已有同名目录分别保留 ID、路径、样本；同父同名也不折叠实体，不取第一项，不擅自合并。语义等价有多个候选时按稳定身份和上下文选择；仍有歧义则保留并解释。
- 反复整理相同内容时先识别既有等价主题和上次已建立的目录，尽量保持身份、命名和落点，避免每次重造同义树或来回搬动。
- 大目录的主题与旧目录匹配按预算分组处理；分页和候选召回不能重新退化成“只看前 500 条/目录”。

#### D. 目录方案必须是可验证、可恢复的图

- 方案节点明确区分 `reuse(existingFolderId)` 与 `create(plannedFolderKey)`，带语义说明、预计承接数；新节点的 parentRef 可以是所选根、合法既有目录 ID 或同任务的新父 key。
- 服务端验证所有父引用可解析、无环、无越界、无重复 key、层级和数量合法；按父先子后的拓扑顺序创建。不能把“开发/前端”字符串当成唯一身份或隐式多级创建命令。
- 临时 key 到真实目录 ID 的映射和创建回执随任务持久化，后续批次与重启复用；已经创建成功的父/子目录不能重复创建。
- 不自动改名、搬家或删除旧目录；通过书签归位形成新的有效分类分布。被迁空的旧目录在结果中列为“已空，仍保留”，由用户通过原有目录管理处理。
- 不因受保护/审核拒收项调用全局“私人收藏”搬家。书签分支严格不跨子树；资料分支只能进入当前用户资料分类，不能借此越权移动其他书签。敏感处理仍与已有独立旁路功能分开。

### 5.4 规则提供线索，不能绕过用途与主题规划

- 已配置模型时，域名规则命中的条目也参加主题发现；规则提供用途线索，不提前认定归类完成，更不能先提交到旧目录再补建新树。
- 规则只给出“开发”等上层粗分类，而当前正在整理“开发”内部时，继续按内容细分；不能因目标名字不在子树而跳过，也不能因为已经位于同名目录而停止分析。
- 所有普通候选都在共用主题方案确定后再作最终判断；未知规则、弱规则不要求用户先补目录或补规则。
- 无模型仍遵守现有规则降级，任务明确标记 `rule_only`：仅向**本子树内语义明确、身份可确定的已有目标**归位，不凭固定域名映射生成一棵号称智能的新树，其余保留并解释。界面注明“本次未进行 AI 主题发现或新目录规划”。
- 已配置模型但调用失败是失败，不冒充“无模型正常降级”；主题规划失败时不偷偷退回规则并宣称智能整理成功。已提交批次仍保留，失败部分单列。

### 5.5 每条必须有一个明确判断

逐条计划明确区分 `move(targetFolderId / plannedFolderKey, reason, confidence)`、`convert(materialType, categoryPath, evidenceRef, reason, confidence)` 与 `keep(reason, confidence)`，不再只返回一个模糊的“分类名”。convert 只有在内容证据和规范化资料分类都有效时才可提交。

- move 初始门槛建议统一 ≥0.80，且内容一致性/可找回性优于原位；新旧书签目录同标准。convert 更保守：资料用途及分类均明确，设计置信门槛 ≥0.85，并满足正文/媒体证据和分类校验；缺项或不确定不能转。上述均为待验证默认，不把模型自报置信度当正确率。
- 当前目录与目标是**同一 ID**时才是原位；名称相同不代表无需移动。若目录中的内容确实混杂，不能仅以减少移动数量为由拒绝更合理的新主题。
- 单条证据不足时明确记为 `unchanged: insufficient_evidence`，不塞进泛化的“其他”。目录图非法或方案超预算属于规划问题，不能伪装成每条书签都无需调整。
- 模型漏返回的 ID、重复 ID、非法书签目标、子树外书签落点、无效资料分类或 JSON 都是校验失败，不得默认为已检查/原位合适。
- 每条在一次任务中至多成功完成一次主动作：移动或转资料，二者互斥；方案确定后冻结书签目标与资料分类映射，避免多批之间反复搬动、转换或重复计数。

### 5.6 分批落库，但不把计划当成果

- 分析在事务外，提交是短事务；不在 SQLite 写事务里等网络。
- 默认模型批次最多 30 条，并按模型上下文预算进一步缩小；不能靠减少可见总范围来满足批次限制。
- 提交前共同重查：实体存在、URL 和内容修订未变、来源仍符合原始基线、未归档、未被其他动作转资料、隐私允许。move 另查目标仍在根子树及目录修订；convert 另查正文/判型证据、当前用户资料归属、分类路径、资料 status/分类修订及转换代际。
- 同一提交事务内核对任务停止标志、undoStatus、运行租约及执行代际；不能只在调用模型前或事务外检查一个内存标志。已经进入原子提交的批次可完成，“已停止”必须在提交屏障确认后才能返回。
- 用户已移动、修改或删除的条目跳过；根目录被删除/搬家导致范围变化则停止剩余，不按同名重建根目录。
- `moveBookmark` 等仓储方法必须返回真实写入结果；未写入、生命周期不符、影响行数为 0，不能追加成功动作或计移动。
- 只有至少一条已校验可提交的移动落到新节点或其后代，才在同一短事务中按拓扑创建必要祖先和目标目录，并保存 key→ID 映射；不提前批量建空壳。全批冲突不能留下空目录，重试不能重复建父/子节点。
- 既有节点按规划前基线校验；本任务新增节点按创建后的确认回执校验。父级创建失败时，其后代与依赖移动都不能绕过父级执行。
- 每批实际动作、organize_version、同步变更、任务项最终结果及计数同事务提交。convert 的 material 创建/复用、有效 category 与分类修订、书签软移出和版本归属必须在同一短事务，任一步失败就不隐藏书签、不计已转资料。
- 抽取 D91 共享转换效果与校验，而不是直接串联各自保存版本的旧入口。每批由统一协调器保存一份版本，包含成功 move/convert/category 效果并绑定转换 versionId；整个任务仍可有多批版本，但用户只看到一次整理及整次撤销。
- **分类写入守卫**：需要补齐 material 的 `category_revision` 与分类来源（auto / organize_task / manual）；本次记录旧/新分类、来源和写后修订。所有资料分类写者，包括迟到摘要、D65 回填，均须走同一 CAS/来源优先级入口，不得在显式任务分类后无条件覆写。
- **自动资格交接**：本次实际移动或转换成功视为用户发起的新意图，同事务退出旧 inbox_state/D77 自检资格，取消旧入口尚未完成的 D91 候选并清理临时证据。当前任务的显式转换来源独立保存，不能被当成旧自动候选一起误取消。保持、跳过、失败项不附带修改资格。
- 若 D91 先提交，整理按生命周期冲突跳过、不冒领转换成果；若本任务先提交，旧自动结果因基线/代际不符失效。撤销不复活旧自动候选或自检资格；未来再次投递或新的显式整理才建立新意图。

## 6. 计数与任务状态契约

### 6.1 一条来源收藏只算一次

```text
total = moved + converted + unchanged + skipped + failed + remaining
checked = moved + converted + unchanged + skipped + failed
converted = newMaterials + reusedMaterials
```

- `total`：范围快照内有效书签数；开始前已归档/已转资料等排除另列，不混进分母。
- `moved`：留在书签面且确认改变目录的条目数，不是动作数，不含资料转换时的内部隐藏锚点移动。
- `converted`：本任务确认完成软转换并具有有效资料分类的唯一条目数；资料判型、排队、抓取、预先存在 material 都不算成功转换。
- `newMaterials` / `reusedMaterials`：按本轮是否新建 material 行拆分；复用 active 行后转换仍计 converted，但不能宣称新增了一条资料。
- `unchanged`：已判断且保留原书签，包括合适、证据不足、规则未命中、尊重此前移出资料库意图；必须带原因。
- `skipped`：保护或并发变化导致不能处理；必须带原因。被其他任务先转换不能冒领到 converted。
- `failed`：取证、判型、分类或提交未成功且本次尝试结束，原书签保留；不能算保持已确认合适。
- `remaining`：还没形成最终结果，包括排队、取证、分析中或停止后未处理部分。
- `plannedNewFolders` / `createdFolders` / `reusedFolders` 只统计书签目录；资料另列 `plannedMaterialCategories` 和实际新出现/复用的分类路径数。资料分类不是 folders 节点，不能混计；这些结构数均不进入来源条目计数公式。
- 新父目录只承载子目录时也算一个实际新节点，不能当成空壳或移动书签；未提交/校验失败节点不计已创建。重试失败项时原记录转回待处理，不叠加新的“已检查次数”。

终态语义：

| status | 含义 |
| --- | --- |
| `queued` / `running` | 已持久接受 / 正在执行；phase 另标范围检查、用途/取证、双路规划、提交、汇总，取证与就绪批次可并行 |
| `stopping` / `stopped` | 已请求停止 / 确认不再提交新动作；保留已完成与 remaining |
| `completed` | remaining=0，全部形成有效结果，无失败或执行降级；零移动也必须解释 |
| `completed_with_issues` | remaining=0，本次检查结束，但有条目最终失败、规则降级或证据不足等需说明的问题；不代表每条分析成功 |
| `failed` | 任务级故障无法继续；未执行项保留 remaining，不能批量标失败或保持来制造 100% 完成 |

`executionMode=ai|rule_only` 与状态分开。规则检查结束不等于 AI 整理成功；任务是否完成、有没有移动、模型是否实际参与是三个不同维度。

### 6.2 失败与恢复

- 失败持久记录可读原因、内部 reason code、阶段、批次、时间、是否可重试；不记录 Key、令牌、完整 URL 查询参数或原始模型响应。
- 建议单次模型请求整体 deadline 45 秒，含一次受限重试的批次总预算不超过 90 秒；具体以现有 AI 客户端能力落实，不能串联多个无限等待。鉴权/无效配置不自动重复调用。
- 超时/暂时限流可最多自动重试一次，有可见提示；其他书签不因一条失败永久卡住。
- “继续剩余”只处理原快照未完成项；“重试失败项”只重试可恢复失败，已移动/已转换项不重复处理；均重验旧基线及证据，不吸收新的用户改动。已持久有效判型与分类可复用，不重复抓取；过期则重新取证但不刷新原实体基线。
- 模型配置变化、目录方案失效时作废尚未提交的旧计划；不能拿旧目录 ID 或旧授权继续写。需要扩大范围或重新评价已变化项时，明确新开一次任务。
- 已有明确且已持久化的分类结果、但提交遇暂时数据库故障时，从持久计划重试，不重新调用模型；计划、尝试与提交回执分开保存。
- 模型响应与本地落盘之间崩溃，无法保证供应商只执行/计费一次。恢复时允许受限重调并记录尝试，不许承诺模型调用 exactly-once；书签写入和版本仍必须幂等。

## 7. 实现设计：小而完整，不建设通用任务平台

以下均为**拟新增契约**，不是当前已存在的 API 或表。

### 7.1 持久化与运行器

复用 Node + Hono + node:sqlite、现有模型出口、组织版本及同步内核。不引入 Redis、队列框架、外部向量库或第二服务。

| 拟新增/扩展 | 最小职责 |
| --- | --- |
| `organize_task` | 创建幂等键、来源范围、status/phase/mode、结果计数、停止/运行租约与代际、双分支方案、目录 key→ID 映射、错误和时间；独立 undoStatus、撤销回执与执行锁 |
| `organize_task_item` | task/bookmark 身份、await 前基线、bookmark/material/undetermined 用途、受授权证据引用及修订、书签节点或资料 category、资料旧状态/分类修订、判断与原因、状态/尝试、成功版本与最终修订；同一来源唯一 |
| `material` 分类守卫扩展 | category_revision、category_source 及必要的任务来源引用；所有分类写入与回填共用 CAS，资料分类不能只依赖 bookmark 修订来保护 |
| `organize_version` 的任务关联 | taskId、批次顺序、成功 move/convert/category 效果及生命周期/分类前后状态；任务多批可聚合撤销，旧转换版本语义不被静默重写 |

约束：

- 任务和任务项落当前用户独立 SQLite；owner 与普通用户同规则，运行、查询和恢复必须固定租户上下文。不能只在 HTTP 鉴权时区分用户。
- 单账号最多一个活动整理/撤销执行；旧 `/organize/folder`、`/organize/sessions` 必须共用账号级准入，忙时明确拒绝或返回活动任务，不能因保留旧响应形态而绕过互斥。任务关联版本的单独 rollback 也进入同一协调器。
- 所有账号的本功能模型请求共用全局并发闸，初始 ≤1，批次间公平让出，不能每个任务各有一个“全局锁”。其他现有后台能力的资源预算需一并实测；账号级准入不阻塞用户手动编辑或新收藏，后者继续由修订守卫保护。
- 持久状态是真相，内存 Promise 只负责唤醒。启动补恢复，单个运行器推进；租约代际防止过期 worker 在恢复后继续提交。
- 不持久复制全文、摘要或原始模型思维链。必要标题/相对路径快照限于非受保护条目；隐私策略变更时应清理/脱敏已有任务证据，查询时再次判定。
- 终态逐条明细建议保留 30 天、每用户最多最近 20 次，先裁剪旧明细；活动任务不裁剪。含版本任务的最小摘要与版本关联必须保留，明细过期不能使撤销入口失效。
- 展示证据与恢复必需数据分开：原快照、基线、未完成集合、持久计划和回执在允许继续期间必须保留。恢复期限不超过上述明细保留范围；时间到期或按数量裁剪前，原子设置 `canContinue=false` 并注明“原快照已过期”。
- 到期后的 continue 返回 `409 task_snapshot_expired`，界面改为“基于最新状态重新整理”，明确新建任务，不能暗中重扫并刷新旧任务基线。撤销仍依赖版本事实，不因快照过期而失效。
- 任务无版本时也保留近期摘要，覆盖零动作和失败。裁剪纳入已有 retention，不新增无人管理的无限日志表。
- 需要前进式数据库迁移；实施时取下一可用编号并执行既有迁移前备份，不在设计阶段假定当前仍是 v17 或预占 v18。

### 7.2 拟定 API

| 接口 | 作用与关键返回 |
| --- | --- |
| `POST /api/v1/organize/tasks` | `{folderId, requestId}`，默认含后代；持久接受后立即 `202 {taskId,status}`；同幂等键回同任务，已有活动任务回其可查询 ID |
| `GET /api/v1/organize/tasks/:id` | 来源范围、双分支去向、状态/阶段/执行方式、moved/converted 等条目计数、目录与资料分类各自的计划/实际计数、错误、关联版本、canContinue/恢复期限、undoStatus/撤销计数与单调 revision |
| `GET /api/v1/organize/tasks/:id/items?result=&limit=10&offset=0` | 按 moved/converted/unchanged/skipped/failed 查明细；带目标类型及 folderId 或 materialId/categoryPath；total 为可展示数，protectedCount 为仅聚合保护数，两者不混用于分页 |
| `GET /api/v1/organize/tasks/:id/folders?state=&limit=10&offset=0` | 书签目录变化分页：稳定 key、相对路径、拟新建/已创建/复用/未应用、预计/实际承接数、理由；不返回受保护样本 |
| `GET /api/v1/organize/tasks/:id/material-categories?limit=10&offset=0` | 资料分类分页：规范化路径、拟新增/已使用/复用/未应用、预计/实际资料数；路径来自 category，不伪造 folderId |
| `GET /api/v1/organize/tasks?limit=10&offset=0` | 本账号最近任务、活动任务和总数；可按目录身份筛选 |
| `POST /api/v1/organize/tasks/:id/stop` | 幂等请求停止，响应 stopping 或已终态；真正停止由任务状态确认 |
| `POST /api/v1/organize/tasks/:id/continue` | `mode` 为 `remaining` 或 `failed`；只重开允许重试的原任务项，不能重复执行已提交项 |
| `POST /api/v1/organize/tasks/:id/undo` | 先停止仍在运行的任务，再协调既有版本逆放；返回可查询撤销状态与实际撤销/跳过数 |

统一错误：目录不存在、系统目录不支持、范围变化、任务不存在或无权访问、无可继续项等分别给明确代码；不能只回一个 `ok:true`。所有查询限当前用户，跨用户任务按不存在处理。

兼容：旧 `/organize/folder` 及 `/organize/sessions` 先保留响应形态，不能直接从同步结果改成 202 而破坏调用方。管理台目录入口切新 API 后，单独盘点旧消费者再决定退役策略。

### 7.3 进度通知与前端查询

- 复用共享 `/events/stream`，扩展不含内容的任务门铃，如 `{type:"organize.task_changed",taskId,revision}`；REST 任务快照是事实源。
- **书签变更门铃不是进度**：模型等待、失败、零动作、停止都应更新任务状态，即使没有任何书签变化。
- 任务通知和目录数据通知分流订阅；心跳不能每次触发全书签列表重查，不为每个任务单独占一条永久 SSE。
- 当前任务在途查询去重；断流时仅在前台以约 5 秒低频查询任务，重连补查，终态即停。等待时长由阶段起始时间计算，不每秒发请求。
- 查询使用账号/服务端/任务代数保护；切账号、退出、切服务后取消观察，旧结果不能写进新账号页面。
- 任务详情自身持续更新，不受 D82 的编辑/弹窗 blocked 误拦；背后列表沿 D82 保留旧数据和 dirty，允许在关闭详情后补刷。
- 完成后刷新当前视图与树，不强制跳到整理根目录；“查看目标目录”才主动导航。不能清空搜索、勾选、滚动位置来制造变化感。

### 7.4 同步不另起一套写者

- 普通 move 走现有仓储与 changes；convert 发送 D91 同形的 bookmark.materialize，恢复发送完整 upsert，不伪装普通 delete。已启双向同步的设备不额外投递镜像 ops。
- 管理台提交成功不等于浏览器节点已移动或撤下。无设备回执时仅说明“管理台已生效，浏览器按同步设置收敛”，不虚报全部设备完成。
- 同步关闭时，本任务可在管理台软转换，但浏览器普通目录原项仍保留；明确说明，不扩用 D91 仅清理收纳盒的兜底去删除普通目录节点，也不擅自开启同步。启用后通过既有事件/快照及身份守卫收敛。
- 开始前已转资料项排除；提交前被其他任务转换的项按冲突处理。隐藏行、转换回声和恢复都不被当成普通 move/create/delete 强行复活或物理删除。
- 资料 category 落库后供现有资料筛选、分面、MCP 与导出消费，不新增第二份正文或公开投影；管理台资料页与书签页都需接收到对应变更并校准。

## 8. 撤销：仍以组织版本为唯一安全面

- 一次任务可以多批提交，但对用户是**一次整理**。每批真实 move/convert/category 效果写 organize_version，关联有序版本，不额外保存第二套可写回滚真相。
- 结果页“撤销本次整理”和版本历史分组调用同一协调器：先停止任务、等待提交屏障，再按批逆序撤销。需扩展 category 效果及守卫，不能宣称旧 rollback 已能还原资料分类。
- 撤销有持久进度与幂等恢复，只撤成功动作，不撤失败计划，不重复逆放。转换+本次分类是同条目的成组效果：核验书签修订、转换代际/versionId、资料身份/status/分类修订，冲突则该组整体保留并说明。
- 书签 move 回本任务前目录；convert 撤销恢复为普通书签，优先原目录，已不存在则沿 D91 回“未整理”。资料、正文和快照仍保留，**不是物理删除资料或严格恢复所有缓存到任务前**；界面在撤销入口旁明确这一点。
- 已有 active 资料被本任务改分类时，成组撤销将 category/source 恢复旧值并递增分类修订，不覆盖后续用户改动；本次新建资料没有既存分类可还原，资料与有效分类一起保留，不为撤销制造两面都不可见的内容。
- 资料页单独“恢复为书签”继续沿 D91（资料与当前分类保留）；它不等于撤销整个任务。之后任务撤销应识别用户已恢复，不重复计数或改写该项分类。
- 先恢复书签归位/转换，再按新目录图叶→父顺序清理由本任务创建且仍为空、未被用户修改的目录；用户原目录和含新内容的目录保留。不能因父下有待撤子目录而漏回收，也不能先删父导致依赖失败。
- 新建目录动作的版本事实必须保存创建后的目录 ID、parent/root/revision。回收前逐项比较，用户已改名或搬家则即使为空也保留；不能只调用旧 deleteFolderIfEmpty。上述守卫留在不可随任务明细裁剪的版本数据中。
- 从旧版本历史单独撤销某个关联批次时也先进入任务协调器，锁定并停止该任务，按该批逆放后标记任务“部分撤销”；其他批次可继续撤销，但整个旧任务不能再继续整理。不能绕过任务锁直接调用旧 rollback。
- 后续被用户修改、移动、恢复、再次转换或改资料分类的条目按守卫跳过，不覆盖新意图；任务自己的转换不属于此处的“外部变化”，不能把本应撤销的 convert 全部跳过。
- 必须显示实际恢复/保留数，并拆分撤回 move 与恢复 convert；资料保留数、分类恢复数、回收空目录数另列。目录未实际删除不能计回收，也不能增加恢复条目数，不一律说“全部回到原目录”。
- 零实际变更不生成空版本，撤销按钮禁用并说明；任务明细仍然可查。
- 停止不等于撤销；撤销也不依赖用户是否曾打开结果页。

撤销生命周期与互斥：

- 原始整理 `status` 和结果计数保留作历史事实，独立 `undoStatus=none / pending / running / completed / partial / failed` 表示撤销进度，不把原移动数减成 0。
- 接受撤销请求即持久锁定旧任务执行，先停止并排空在途提交，再逆放。此后“继续剩余”和“重试失败项”返回 `409 task_undo_started`；即使只是部分撤销，也不能沿旧计划重新前进。
- 撤销占用同一账号整理执行槽，与新整理互斥；模型结果晚到、重复请求或旧 worker 都不能绕过执行锁重新移动。
- 暂时失败可用同一 undo 接口继续尚未完成的撤销，读取已完成版本/动作回执，不重复逆放；用户后改等不可撤项只记录保留，不自动反复尝试覆盖。
- 结果同时展示“原归位/转换 42 条 / 已恢复 35 条 / 后续改动保留 7 条”，资料保留、分类恢复与回收目录另列；逐条标明已恢复或保留，原始去向仍是历史事实而非当前现状。
- `completed` 或 `partial` 后旧任务永久不能继续整理；需要重新整理时明确新建任务，以最新状态建立新基线。本期不增加整任务一键重做。

## 9. UI 约束与信息层级

- 沿用 `#4F46E5` 主色、zinc 中性结构、现有窄栏；图标使用 lucide，不新增装饰 emoji 或自创配色。
- 标题采用同款图标 `size-4` + `text-lg font-bold`，副标题 `text-[13px]`；说明一句话，失败原因按需展开。
- 层次用 shadow / bg-muted，不用框中框。Dialog、输入等功能边界除外，不添加无意义分割边框。
- 活动状态复用目录操作区与已有整理功能区，不把进度浮条插入多选工具栏或挤动列表；不复活被否的首页待办清单。
- 任务明细、最近任务都用 `NumberedPagination`，默认每页 10 条，显示总条数/当前页/总页数/首尾窗口页码；筛选回首页，刷新校准合法页码，加载中禁重复请求。
- 数据行用 `.data-row` 整行 hover / focus-within；行内及分页按钮 `size="xs"`，独立分隔元素；信息按“标题 / 去向或原因 / 状态 / 操作”至多四位。
- 最近完成只显示少量摘要，完整记录用分页，不做无限追加日志淹没界面。
- 对话框可键盘关闭、返回原焦点；状态以节制的 `aria-live` 宣告阶段/终态，不逐条打断读屏。Esc 等价收起，不等价停止；停止按钮必须可键盘到达。

验收方式：

1. server 集成：临时 SQLite、可捕获输入的模型替身、慢响应/失败/并发/崩溃恢复故障注入；先验证错误能被测试抓到，再修正通过。
2. web：类型检查、构建、`?mock` 覆盖运行/零动作/降级/失败/停止/部分撤销，逐场景浏览器截图自检。mock 不可只模拟永远成功的动效。
3. 隔离 E2E：沿用现有 fixture 与真实扩展，不打 3000 真实收藏库；按可查询任务状态等待收敛，不用 reload 或强制刷新促成通过。
4. 记录创建受理→首次可见状态、模型等待、首批提交→呈现、总耗时；目标为正常本机环境首次状态 ≤1 秒、提交后前台进度 P95 ≤2 秒，均为目标而非已测值；不承诺模型固定秒数完成。
5. 生产镜像冒烟与资源测量独立报告；未运行必须明确，不用 mock 截图替代真实提交、同步或资源证明。
