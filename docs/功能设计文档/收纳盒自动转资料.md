# 收纳盒自动转资料 · D91

> 2026-11-24 · 已实现并经隔离测试验收。功能与边界以本文和活文档为准；早期「直接复用 delete 事件、只加一个软状态」方案已在本轮评审中修正。
> 范围：server / web / extension / e2e；不变更技术栈、扩展权限或真实开发库。

## 1. 用户决定

- 收藏入口仍是**唯一收纳盒**，不增加「资料收纳盒」或第二套收藏流程。
- 根据网页内容识别资料，成功后只在资料库呈现，不在书签库和浏览器收藏夹重复保留。
- **文章、视频、图片均参与**；不新增用户配置开关。
- 自动处理直接生效，但必须去向可见、可撤销；不物理自动删除任何收藏内容。

非目标：存量收藏自动回溯转换、批量导入转换、把 D89 用户手动目录扫描改成自动移出。直接指定普通目录的历史捕获/资料消费语义保留。

## 2. 最终处理流程

```text
新收藏 → 唯一收纳盒 → 原子登记持久识别候选
  ├─ 视频/图片 URL 形态命中：直接异步资料分流，不先创建普通书签目录
  └─ 其他页面：书签归位照常，独立识别任务复用已授权正文或经隐私校验补抓
        ├─ 正文不足 / 非内容型：保留书签
        ├─ 无模型 / 抓取或模型失败：保留书签，持久记录原因并可补扫
        └─ 以实际正文判为内容型：资料物化 + 书签软移出 + 转换版本同事务
                 ↓
       资料库 / MCP / 导出正常可用；书签列表、搜索、统计、公开投影和同步快照排除
                 ↓
       资料页恢复 / 转换版本撤销 → 回到原普通目录（不存在则未整理）
                               → 资料保留，取消自动再次转换资格
```

文章判定不是“标题像教程”或“字数多就是文章”：至少有 200 字正文才进入内容判定，模型获得正文片段，区分文章/教程/报告/文档与工具首页/登录页/导航等内容壳。自动移出**不使用 D89 的 800 字兜底**，模型漏判也不视为肯定。视频/图片按已知 URL 形态识别，是可恢复的规则判断，不承诺零误判；视频不下载本体。

`processInbox` 的 `moved` 仅报告已提交的普通归位；媒体等异步工作返回 `queued` IDs，不提前宣称“已收入资料库”。成功以资料列表、去向历史及版本为准。

## 3. 数据与生命周期

迁移 **v17 `material_convert`**，仅前进；部署时沿用迁移前备份。没有存量自动转换脚本。

| 数据 | 作用 |
| --- | --- |
| bookmarks.materialized_at | 非空表示资料专属呈现，书签面隐藏，物理行保留以维持 material/content_cache/snapshot 关联 |
| bookmarks.materialized_from_folder_id | 原目录 ID，无外键；原目录删除后仍能恢复到「未整理」 |
| bookmarks.materialized_generation | 转换代际，防止旧版本撤销后续转换 |
| bookmarks.materialized_version_id | 当前生命周期所属版本，和 revision/generation 一起校验撤销 |
| organize_version.label | `material_convert` 表示自动转资料，首页/版本历史/popup 使用可读文案 |
| inbox_state.convert_version_id | 最近归位行的转换撤销入口 |
| material_conversion_candidate | 新入口持久任务：entry_id、URL、实体/隐私修订、状态、授权正文临时证据、判定、重试计数/原因/下次时间 |

### 为什么不能直接删书签或套用归档

`material.bookmark_id` 是 UNIQUE、NOT NULL、ON DELETE CASCADE；正文又引用 content_cache。物理删除书签会销毁资料，不能实现本需求。普通归档/重复合并也不是资料生命周期，不能借用 `status` 或 `archived_into`。

**隐藏行以现有系统收纳盒作为内部 FK 锚点**，保存原目录但从盒内待处理列表和计数排除；没有新增可见目录或第二个收纳盒。因此删除原先“看似空”的普通目录不会级联删除资料。用户显式删除仍是独立动作；浏览器旧删除意图/系统撤节点回声不能物理删除隐藏资料。

转换、恢复都递增 content_revision。版本 undo/redo 同时核验修订、代际和当前版本归属；用户已编辑/恢复、任务入口已变化或旧归位被撤销时，不覆盖新意图。恢复默认回原普通目录，原目录消失或本就是收纳盒则回「未整理」。

临时授权正文仅供待处理任务恢复；进入 done/cancelled 即清空，隐私规则存量清理同步清空并取消任务，避免留下第二份长期正文。资料正文仍以 content_cache 为单一引用源。

## 4. 异步、隐私与失败恢复

- 新入口书签和候选在同一 SAVEPOINT 登记；导入/旧存量不靠遍历补登记。
- SQLite 候选是任务真相，Promise 仅负责唤醒；全局串行闸跨 Pipeline/用户生效，去重键含 uid/bookmark/入口代际。
- 启动及每分钟补扫 pending/retry/ready；进程重启、模型暂不可用不会永久遗失任务。
- 任务绑定 URL、content_revision、privacy_revision、entry_id；抓取/模型前、返回后与短事务提交时重查。历史 active 资料不算本轮成功证据。
- 抓取沿用 guardedFetch、隐私 server_fetch 判定、500KB/整体25s预算；模型 call_model 独立校验。私密、隐私域、策略过期或用户手动意图优先保守保留。
- 模型无效返回、抓取失败和封面失败有持久原因；一条失败不毒化其他用户的串行队列。
- 摘要补扫属于内容面任务，已转资料仍可补摘要/分类，不因书签面隐藏而失去 D63 兜底。

## 5. 同步与投递口

### 启用全量同步

转换发送完整 **bookmark.materialize** 事件，恢复发送完整 upsert，不把转换伪装成真实 delete。扩展按事件顺序撤下/重建受管节点；较旧修订重试不覆盖已恢复状态。系统撤节点同时剪掉已确认与开局存在性基线，不能反向推为用户删除。真实删除的积压执行前重查当前状态，网络失败不能当作 404。

隐藏行的 `/sync/apply bookmark.delete` 为安全 noop，`DELETE /bookmarks/:id?ifInbox=1` 返回409；身份接口 app_exists 采用书签可同步可见性，另带 materialized 与 url_raw。设备漏拉事件后也能按快照/身份恢复收敛。

### 默认未启用全量同步

`reconcileInboxMaterials` 复用已有启动/每分钟收纳盒 alarm，**不以服务端盒 count>0 为闸**：只撤下浏览器投递口内、服务端身份已绑定且已转资料、URL一致、用户尚未移走/修改的叶子。不搜索并删除用户的另存副本，不动普通目录，不绕过普通同步删除开关。

读取身份请求设5s预算，不在浏览器写锁内等待网络；写前复核账号/地址/投递口配置，用既有执行器串行写入；取消回声由服务端隐藏态守卫拒绝，不开全局镜像时间窗以免漏掉紧接着的新投递。失败持久记录 `mfInboxMaterialError`，后续 alarm 重试。关闭全量同步时恢复只恢复管理台书签；浏览器节点待开启同步后重建，不能假报已同步。

## 6. API 与界面

| 接口 | 契约 |
| --- | --- |
| GET /materials?limit=10&offset=&type=&q=&category= | `{items,counts,total}`；total是当前筛选分页前总数，counts是全库类型计数，materialized为数字0/1 |
| POST /materials/:id/restore | `{ok:true}`；404不存在，409已是书签；资料保留 |
| DELETE /materials/:id | 普通资料沿用dismiss；资料专属呈现时409 restore_first，防止两面均不可见 |
| GET /inbox/items?placedLimit=10&placedOffset= | 保留items/placed，增加placedTotal；去向行有materialized/convert_version_id |
| GET /organize/versions?limit=&offset= | `{versions,total}`；默认limit50兼容旧调用，管理台请求10 |
| GET /browser/identities?deviceId= | 受管身份，增加materialized/url_raw，app_exists排隐藏行 |

- 资料页：转换条目显示“恢复为书签”，普通双份资料显示“移出资料库”；成功恢复后资料行保留，按钮切换。
- 收纳盒历史与popup：转换成功去向为「资料库」，撤销对应转换版本，不误撤之前归位。
- 首页/版本历史：显示“自动收入资料库”，撤销数为0时明确未覆盖后续改动，不虚报成功。
- 资料、归位历史、版本历史按NumberedPagination每页10条；筛选归首页、删末条校准、加载/写入防重，data-row整行hover/focus-within，行内按钮xs、独立分隔。
- mock实现相同分页/计数/恢复/错误契约，不拿HTTP200或模拟成功代替真实浏览器闭环。

## 7. 验收与边界

已覆盖：目录删除不毁资料、删除回声保护、隐藏更新不复活、旧修订/旧版本/旧入口不覆盖新意图、正文内容壳不转、规则文章也识别、无LLM图片分流、持久任务跨重启/跨用户、隐私变化、临时证据清理与三类分页。

真实扩展E2E：视频与图片从原生收纳盒创建→资料出现且书签/同步快照排除→浏览器节点消失→资料页恢复→启用同步设备节点重建；另验证默认关闭同步时仍清理投递口，恢复不越过同步开关。原资料消费/导出/移出断言保留，以普通目录样本隔离新入口行为。

开发验收阶段使用临时库/隔离fixture、合成正文与测试替身，未清理真实收藏、未提交；当时 Docker 不可连接，因此未运行生产镜像冒烟。

随后用户明确确认部署到本机3000：在容器停止状态完整备份原数据卷（压缩文件约71MiB，gzip/SHA-256校验通过）后，恢复原服务端和LLM mock容器。58个数据库均由v16升级v17并通过完整性/外键检查；主库2100条书签、5条资料保持不变，历史自动转换和新候选均为0。真实健康接口、新版静态资源和分页API验证通过，开发容器实测约231MiB。扩展产物已更新，已安装的开发版扩展仍需在浏览器扩展管理页重新加载；未把生产镜像大小或真实浏览器扩展自动更新声明为已验证。

验收汇总：server336、extension94、shared96、ai7项单元/集成通过（shared/ai为Turbo缓存命中）。80项E2E首轮76通过/3失败/1跳过；3个旧mock测试因依赖未启动的3000端口失败，已改接隔离fixture，连同资料6项复验9/9通过，分批汇总79通过/1跳过。没有把首轮失败隐藏为一次全绿。
